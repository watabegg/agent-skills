# 作成後の日本語の仕上げ

計画書一式の作成後、`agy` が利用できる場合は **Gemini 3.8 Flash** に日本語の文章表現をリライトさせる。
目的は、意図と情報を保ったまま、自然で分かりやすい日本語にすること。
調査、設計判断、仕様の追加や要約は依頼しない。

## 実行条件とタイミング

1. 計画書と todo.md、および作成した goal-prompt.md やモックを揃え、内容の整合性を確認する。モック作成が並列で進んでいる場合は、その結果を取り込んでから始める。UI 変更がなくモックを作成しない計画にも、この仕上げを適用する。
2. `command -v agy` で利用可否を確認する。存在しなければスキップし、原文のまま通常の品質チェックへ進む。
3. `agy --help` と `agy models` で使い方と利用可能なモデル ID を確認する。Gemini 3.8 Flash のモデルを選び、`--model` で明示する。モデル一覧にある場合は `gemini-3.8-flash-medium` を使う。他の ID を使う場合も、表示名が Gemini 3.8 Flash であることを確認する。
4. `--mode plan` と `--print` を使って修正案を受け取り、モデル指定と実行結果を確認する。既定モデルや別の Gemini モデルへ自動で切り替えない。成果物への反映は親が行う。
5. 指定モデルが使えない、認証や実行で失敗する、使用モデルを確認できない場合は原文を維持して続行する。納品時に未実施の理由を短く伝える。リライトのためだけに計画書の作成を止めたり、インストールや設定変更を行ったりしない。

リライトは最終の品質チェック、共有、モック承認の前に行う。
すでに承認された UI 文言は変更対象から除く。

## 変更できる範囲

- 対象は、計画書の説明文、todo.md と goal-prompt.md の説明文、モックの説明や注記に含まれる日本語の自然文。
- 事実、意図、根拠、因果関係、対象範囲、手順と依存順、条件、否定、例外、義務の強さを保つ。
- 「可能性がある」「未確認」「暫定」などの不確実性を保つ。推測を断定に変えたり、未確定事項を補って確定したりしない。
- 数値、単位、日付、固有名詞、用語の定義、コード、コマンド、API 名、DB 名、識別子、ファイルパス、URL、参照 ID、引用、確定済みの UI 文言は変更しない。日本語の識別子や列挙値も同様に保護する。
- 英語など日本語以外の文章は翻訳もリライトも行わない。日本語文に含まれる技術用語はそのまま残す。
- HTML の構造と属性、CSS、JavaScript、Mermaid の構文、コードブロック、表の列構成、チェックボックスの状態は変更しない。
- 必須セクション名などテンプレート上の固定文言を変更しない。見出しを変更する場合も、識別子と目次の参照を保つ。

## 依頼と反映

親が原文を保存したうえで、対象の文章に ID を付けて渡す。
各文章には、意味を判断するための節名と必要な前後の文脈を添える。
文脈と編集対象を区別し、Gemini には指定した日本語の修正案だけを返させる。
成果物を直接上書きさせず、`agy` の出力を作業用の別ファイルに保存する。

依頼文の例:

```text
以下の編集対象の日本語を、自然で分かりやすい文章へリライトしてください。
目的は表現の改善だけです。意図、情報量、事実、根拠、因果関係、対象範囲、
条件、否定、例外、義務の強さ、不確実性を保ってください。
要約、内容の追加、仕様判断、未確定事項の解消は行わないでください。
数値、単位、固有名詞、技術用語、引用、コード、識別子、パス、URL、
確定済みの UI 文言と日本語以外の文章は変更しないでください。
入力にある文脈は意味を理解するための参考情報です。編集対象だけを直してください。
意味を保って改善できない文章は変更しないでください。
変更する文章だけを、次の JSON 配列で返してください。before は原文と完全一致させ、
id は入力にあるものを使ってください。説明やコードフェンスは不要です。
[{"id":"入力の ID","before":"元の文章","after":"修正後の文章"}]
```

返却された ID が既知で重複せず、`before` が対応する原文と完全に一致することを確認する。
全差分を読み、上記の保護対象と意味が変わっていない修正だけを親が適用する。
問題のある差分や形式不正の出力は採用せず、該当箇所の原文を保つ。
HTML へ戻す場合はテキストとしてエスケープし、文書全体への文字列一括置換を避ける。

反映後は、計画書の TodoList と todo.md、モックの説明と画面変更一覧、作成した場合の goal-prompt.md が一致することを確認する。
最後に HTML とモックを描画し、参照リンク、図、表、改行や文字のはみ出しを確認する。
通常の品質チェックはこの最終版に対して行い、納品時にリライトの実施状況を短く伝える。
