# Create Implementation Plan

実装計画書を作る前に、既存実装の理解と事前調査を完了させる。

成果物は次のファイルとする。

- `<topic>-plan.html`: 計画書の正本。`references/plan-template.html` を複製して全セクションを埋める。
- `<topic>-todo.md`: 実装中に更新する進捗台帳。`references/todo-template.md` の形式。
- `<topic>-assets/mock/<screen>-mock.html`: 新 UI の静的モック。フロントエンドの変更がある場合は必須。ユーザーが指定したモデルで作成し、計画書の執筆と並列で進める。モデルが未指定なら作成前に質問し、回答を待つ。ユーザーの承認後に `画面変更一覧` の表示の正にする。作り方は `references/ui-mock.md`。

goal-prompt.md（`references/goal-prompt-template.md`）は、ユーザーが求めた場合か、別セッション・クラウド環境へ実装を引き継ぐ場合に作る。

## 必須ルール

1. 推測だけで計画を書かない。
2. 既存コードの主要経路を読んでから計画を書く。
3. 今この場で実行可能な調査を先にやり切る。
4. 不明点をゼロ化できない場合は、必ず `Unclear Points` を列挙する。
5. ジュニアエンジニアがそのまま実装できる粒度まで分解する。
6. 計画書に `TodoList` セクションを必ず含める（todo.md と同内容）。
7. 複数コンポーネントが関わる実装 Step では、その Step の詳細内に Sequence Diagram または処理フロー図を置く。独立した図だけのセクションには分けない。
8. 計画書に `Hard Gate`（進行停止条件）を必ず含め、本文の流れを妨げない末尾 Appendix に置く。
9. フロントエンドの変更がある場合、`画面変更一覧` を必ず含める。既存ページのどこがどう変わるかを書く。
10. `セキュリティ・プライバシー・可観測性` と `ロールアウト` は、該当なしでも判定理由を1行書く。無言で省略しない。
11. `画面変更一覧`、`API仕様の変更`、`データモデル・DB変更`、`ステータス・ライフサイクル変更` の順に独立セクションを並べる。該当なしでも理由を1行書く。
12. API変更は定義差分と互換性、DB変更はER図とmigration安全性、状態変更はstateDiagramと遷移表で見せる。
13. HTMLはPR俯瞰レポートと同じ情報設計（追従目次、要約タイル、セクションカード、横スクロール表）を使う。
14. 変更対象の既存画面へ安全にアクセスできる場合、実画面スクリーンショットを取得し、`既存実装の理解` と `画面変更一覧` で、元画像を改変せず HTML/CSS の番号付き赤入れとコメントを使う。
15. `既存実装の理解` と `設計判断と代替案` の間に、Problem と Solution を AS-IS / TO-BE でやさしく説明する独立セクションを置く。UI が関係する場合は実画面の赤入れを使う。
16. 実装ステップは概要カードや全体依存図で重複させず、各 Step の目的、変更ファイル、変更手順、データの流れ、DoD、切り分け、Hard Gate を一つの詳細カードへまとめる。
17. フロントエンドの変更がある場合、計画書の執筆と並列で新 UI の静的モックを作る。ユーザー指定のモデルで作成する。未指定なら使用モデルを質問し、回答を待つ。モックは既存アプリの見た目に合わせ、変更後の状態を番号付き注記で示し、ユーザーの承認を得てから `画面変更一覧` の表示の正にする。実装はモックの承認前に始めない。
18. 計画書一式の作成後、`agy` コマンドが利用できる場合は Gemini 3.8 Flash に日本語の文章表現だけをリライトさせる。意図、仕様、根拠、不確実性を保ち、自然で分かりやすい日本語に整える。適用前に差分を確認する。実行条件と対象範囲は [references/japanese-rewrite.md](references/japanese-rewrite.md) に従う。

## 実行フロー

### 1. 要件を固定する

1. ユーザー要求を1-3文で言い換える。
2. 背景（なぜ今この変更が必要か、現状どうなっているか）を書く。
3. In scope / Out of scope を明示する。
4. リポジトリの docs 規約に従って成果物パスを決める。規約がなければ `docs/plans/` を使う。

### 2. 既存実装を把握する

1. `rg --files` と `rg -n` で関連ファイルを洗い出す。
2. 影響範囲のファイルは全文を読む。
3. 次をメモ化する。
- 既存の入口（API, handler, UI action）
- 実処理の流れ（どこで何をしているか）
- 既存の制約（タイムアウト、上限、保存形式、依存ライブラリ）
- 既存テストと欠けているテスト

4. 「読んだファイル一覧」を計画書に残す。
5. UI が関係する場合、現行フローの説明そのものを実スクリーンショットと番号付き注釈で構成し、操作入口、現在値、履歴、保存境界を説明する。説明後に別のスクリーンショット小節を追加しない。
6. `既存実装の理解` の注釈は「今どう動くか」を説明し、`画面変更一覧` の注釈は「どこがどう変わるか」を説明する。同じ画像を使う場合もコメントの役割を混ぜない。

### 3. 今できる調査をやり切る

可能な範囲で次を実行する。

1. ベースライン健全性確認
- `go test ./...` / `npm run build` など

2. 外部依存の実測
- 対象URL/APIの正常系・異常系・境界系を最低1件ずつ確認
- ステータスコード、レスポンス形、ページング、エンコード差異を確認

3. データ永続化が絡む場合
- 保存先パス候補
- スキーマ草案
- 既存データ移行要否

実行できなかった調査がある場合は、理由を記録する。
secret、token、個人データを実測記録へ書かない。
調査結果の本文は計画書末尾の `Appendix A. 事前調査結果` にまとめる。
本文では必要な結論だけを参照し、読み始めにコマンド結果を並べない。

### 3.5 Problem と Solution を説明する

`既存実装の理解` の直後に、実装詳細を知らない読者でも変更理由を理解できる説明を置く。

1. Problem をユーザー操作またはデータの不整合として平易に書く。
2. AS-IS では、今何が起きるか、なぜ困るかを1組で書く。
3. TO-BE では、変更後にどうなるか、利用者がどう感じるかを1組で書く。
4. UI が関係する場合は、実画面の該当箇所へ赤入れし、AS-IS / TO-BE の説明と同じ番号で対応させる。
5. API 名、関数名、DB 列名は理解に必要な最小限に留め、詳細は後続の設計・API・DB セクションへ送る。
6. Problem と Solution を一対一に対応させる。複数の問題を一つの抽象語へまとめない。

### 4. 設計判断を固定する

以下を「採用/非採用 + 理由」で書く。

1. API/関数シグネチャ
2. データモデル・DBスキーマ
3. エラー時挙動
4. マイグレーション方針
5. テスト戦略

次の契約変更は、設計判断の文章へ埋め込まず独立した表と図へ分ける。

1. API仕様: 追加/変更/削除、request、response、null/任意値、validation、認可、エラー、副作用、互換性、呼び出し元。
2. データモデル・DB: 変更後ER図、table/column/index/unique/relation/削除/監査、migrationのlock/backfill/可逆性/適用順。
3. ステータス・ライフサイクル: 変更前後、遷移操作、guard、終端状態、禁止遷移、再実行時の扱い。

検討した代替案は、却下理由とともに残す（実在する案だけを書く。帳票を埋めるための対案を捏造しない）。
曖昧な選択肢を残さない。迷う部分は `Unclear Points` に送る。

### 4.5 Hard Gate を定義する

計画の「やり切り」を保証するため、以下を必ず定義する。

1. 着手前 Gate（Definition of Ready）
- 未確定仕様が何か
- 何が確定しないと実装着手不可か

2. Step 完了 Gate（機械判定）
- 実行コマンド（例: `rg -n ...`, `go test ./...`）
- 期待結果（例: `0` 件、exit code `0`）

3. 失敗時の扱い
- Gate 不通過時は次 Step に進まないことを明記
- 台帳/Unclear Points を更新して再実施することを明記

Hard Gate の一覧は末尾の `Appendix B. Hard Gate` に置く。
各 Step の詳細カードには、その Step に対応する Gate の短い参照を残す。

### 4.6 画面変更一覧を作る（フロントエンドの変更がある場合）

既存ページの変更を、ページ単位の表で書く。

1. 対象は既存ページの変更のみ。新規ページは変更対象ファイルと実装ステップで扱う。
2. 各行に、ページ名と URL パス、変更する箇所（コンポーネント）、現状の表示・挙動、変更後の表示・挙動、表示条件（権限・状態）を書く。
3. 実際にコードを読んで書く。ページ名やコンポーネント名を推測で書かない。
4. 対象画面へ安全にアクセスできる場合、同一 SHA の Preview、ローカル fixture、既存 QA 証跡の順で実画面を取得する。
5. スクリーンショットは `<topic>-assets/screenshots/` に置き、環境、取得日時、URL path、対象 SHA をキャプションへ記録する。認証 token を URL や HTML に残さない。
6. 画像上の変更箇所は、番号付きマーカー、赤枠、対応コメントを HTML/CSS で重ねる。色だけに依存せず、コメントにも対象 UI 名を書く。元画像ファイルへ直接描画しない。
7. 実画面を取得できない場合は、理由を明記して表だけで閉じる。別画面や架空 UI を実画面として代用しない。
8. 詳細な配置と capture 方針は [references/visual-planning.md](references/visual-planning.md) を読む。

### 4.6.5 新 UI のモックを並列で作る（フロントエンドの変更がある場合）

計画書だけでは新 UI のイメージが読み手と揃わない。設計判断（4.）と画面変更一覧の下書き（4.6）が固まった時点で、ユーザーが指定したモデルでモック作成を依頼し、残りのセクションを書き進める。モデルの指定がなければ「UI モックの作成にはどのモデルを使いますか？」と質問する。利用可能と確認できた具体的なモデルを候補として示してよいが、選択を自動確定しない。

同じタスクで既に指定されたモデルは再確認しない。「おまかせ」だけで具体的なモデルが確定していなければ候補を提示して選択を求める。回答待ちの間はコード調査や計画書などモデル選択に依存しない作業を続け、モックの生成は開始しない。無回答や時間経過を承認とみなさない。

モデル ID と実行経路を確認し、CLI のモデル引数または Agent ツールの model 引数に明示する。指定モデルが利用できない場合やモデルを確認できない場合は事情を伝え、代替モデルの指定を求める。既定モデル、別名、自分自身への自動切り替えは禁止する。親自身で作成する場合も、現在のモデルをユーザーが明示的に選んだ場合に限る。詳細は [references/ui-mock.md](references/ui-mock.md) に従う。

1. 委ねる入力: 対象画面の実スクリーンショット（4.6 で取得済みのもの）、設計判断、画面変更一覧の下書き、seed データ（架空データ）、既存のデザイン部品（shadcn 等）の見た目。
2. モックの中身: 変更後の主要な状態を 3〜4 枠（例: 変更後の一覧、操作中のモーダル、保存後、確認ダイアログ）縦に並べ、各枠に番号付きの注記を添える。末尾に「齟齬がないか見てほしい点」として、実装前に決めたい判断を列挙する。
3. 置き場所: `<topic>-assets/mock/<screen>-mock.html`。実データ、token、個人名を入れない。既存アプリがライトテーマならモックもライト固定でよい。
4. 完了後、計画書の `画面変更一覧` 冒頭に「モック案 `<path>`（承認待ち）」と書いてリンクする。日本語リライトを行う場合はその反映を待ち、実施の有無によらず最終版のモックを描画して崩れを直す。レビュー用の公開は `納品と実装フェーズ` に従い、納品メッセージで承認を求める。
5. 承認で決まった表示仕様（文言、配置、色、状態）は計画書の `画面変更一覧` と該当 Step に反映し、改訂履歴に 1 行残す。実装はその後に始める。

詳細な構成と HTML の骨格は [references/ui-mock.md](references/ui-mock.md) を読む。

### 4.7 セキュリティ・プライバシー・可観測性・ロールアウトを判定する

Google の Design Doc と同様に、次の横断的関心事を確認する。該当がなければ「該当なし: 理由」を1行書く。

1. セキュリティ: 認証・認可への影響、入力検証、新しい攻撃面。
2. プライバシー: 個人データの追加・移動・表示・ログ出力の有無。
3. 可観測性: 追加・変更すべきログ、メトリクス、アラート。障害時に何を見て切り分けるか。
4. ロールアウト: リリース手順、フィーチャーフラグや段階公開の要否、migration の適用順、ロールバック手順。

### 5. 実装ステップに分解する

ステップごとに以下を固定する。

1. 変更ファイル（新規/更新）
2. 実装内容
3. 完了条件（DoD）
4. 実行コマンド
5. 失敗時の切り分け観点
6. Hard Gate（その Step を完了とみなす機械判定）

ステップは依存順に並べる。

各 Step は一つの詳細カードとして書く。

1. ヘッダーに Step 番号、名前、対象レイヤー、目的を書く。
2. 変更ファイルを「ファイル / 変更内容 / 理由」の表で列挙する。
3. 実装手順をコード上の実行順に番号で書く。
4. 複数コンポーネント、transaction、非同期処理、エラー分岐が関わる場合、その Step 内に Sequence Diagram または flowchart を置く。
5. DoD、失敗時の切り分け、Appendix B の Hard Gate 参照をカード末尾に置く。
6. 全 Step を要約した依存図やステップサマリーを別に置かない。詳細カードと内容が重複するため。

### 6. Unclear Points を列挙する

不明点が1つでも残る場合、以下形式で必ず列挙する。

1. `Point`: 何が不明か
2. `Why`: なぜ決められないか（不足情報/外部依存/仕様未確定）
3. `Impact`: 実装への影響（ブロッカーか、後回し可能か）
4. `Need`: ユーザーへ確認したい具体質問
5. `Fallback`: 回答がない場合の暫定方針

不明点が無い場合は `Unclear Points: None` と明記する。

### 7. TodoList を作成する

チェックボックスで、実装順にタスクを列挙する。

1. 各タスクは `1タスク=1成果` にする。
2. 各タスクに対象ファイルを含める。
3. 実装・テスト・検証・ドキュメント反映を漏らさない。
4. 同じ内容を todo.md（進捗の正本）にも書き出す。

### 8. 図を該当箇所へ配置する

1. シーケンス図は実装 Step の詳細内に置き、その Step の変更手順と対応させる。
2. オフライン閲覧が必要な場合だけ `scripts/render_mermaid_svg.sh` で SVG を生成して埋め込む。
3. システム構成が変わる場合は、関連する設計判断または実装 Step にコンテキスト図を置く。
4. DBスキーマが変わる場合は `erDiagram`、状態遷移が変わる場合は `stateDiagram-v2` を該当セクションへ置く。

### 9. 作成後に日本語を整える（agy が利用できる場合）

計画書と todo.md、および作成した goal-prompt.md やモックが揃ってから、最終の品質チェック前に [references/japanese-rewrite.md](references/japanese-rewrite.md) を実行する。
`agy` 経由で Gemini 3.8 Flash を明示し、日本語の自然文だけの修正案を受け取る。
仕様やコード、図の構文、HTML/CSS、識別子、確定済みの UI 文言は変更対象に含めない。
意図と条件が保たれた差分だけを反映し、関連文書の整合性と描画を確認する。
`agy` がない場合や指定モデルで実行できない場合は原文を維持して通常の品質チェックへ進み、納品時に未実施の理由を短く伝える。

## 出力フォーマット

計画書は `references/plan-template.html` を複製して作る。markdown の計画書は作らない。

最低限、以下セクションを含める。

1. 目的と背景
2. 既存実装の理解（現行フローのスクリーンショット説明、読了ファイル一覧付き）
3. Problem と Solution（AS-IS / TO-BE）
4. 設計判断と代替案（採用/非採用/理由）
5. 画面変更一覧（フロントエンド変更時。承認済みモックを表示の正として参照）
6. API仕様の変更
7. データモデル・DB変更
8. ステータス・ライフサイクル変更
9. 変更対象ファイル
10. 実装ステップ（各 Step の詳細、必要な Sequence Diagram、DoDつき）
11. テスト計画
12. セキュリティ・プライバシー・可観測性
13. ロールアウト
14. リスクと対策
15. Unclear Points
16. TodoList
17. Definition of Done
18. Appendix A. 事前調査結果
19. Appendix B. Hard Gate

## 品質チェック

計画書を出す前に確認する。

1. 変更ファイルが具体パスで書かれているか。
2. 各ステップに完了条件があるか。
3. 調査結果が実測ベースか（推測だけでないか）。
4. 不明点が隠れていないか。
5. ジュニアが読んで「次に何をするか」が1つに定まるか。
6. `TodoList` が実装順で具体化され、todo.md と一致しているか。
7. Hard Gate が「コマンド + 期待結果」まで具体化されているか。
8. Gate 不通過時に次 Step へ進まない運用が明記されているか。
9. フロントエンド変更があるのに画面変更一覧が無い、という状態になっていないか。
10. セキュリティ・プライバシー・可観測性・ロールアウトに判定が書かれているか。
11. HTML をブラウザで開き、Mermaid 図と表が崩れず描画されるか。
12. 日本語の設計書は `agy-writer` で執筆し、内容を事実・設計判断と照合したか。
13. 画面変更一覧、API、DB、ステータスの順に並び、該当なしの場合も理由があるか。
14. API定義差分、ER図、状態遷移図が実装予定と一致しているか。
15. 追従目次、要約タイル、セクションカード、モバイル幅、印刷表示が崩れていないか。
16. 実画面を使った場合、画像の出所と SHA があり、認証 token や個人データを持ち込まず、`既存実装の理解` と `画面変更一覧` の番号付き注釈がそれぞれの役割でコメントと対応しているか。
17. Problem と Solution が AS-IS / TO-BE で一対一に対応し、専門用語を知らない読者にも変更理由が分かるか。
18. 現行フローの説明がスクリーンショットと一体化され、別の画像小節として重複していないか。
19. 各 Step が詳細カードとして完結し、必要な Sequence Diagram または flowchart がその Step 内に置かれているか。
20. 事前調査結果と Hard Gate が末尾 Appendix にあり、各 Step の Gate 参照と一致しているか。
21. フロントエンド変更があるのにモックが無い、またはモックと `画面変更一覧` の文言・配置・状態が食い違う状態になっていないか。モックは実データを含まず、既存のデザイン部品と見た目が揃っているか。
22. モック作成モデルをユーザーが指定したか。未指定なら質問して回答を待ったか。実行時に指定を明示し、使用モデルを確認・記録したか。利用できない場合に別モデルへ自動で切り替えていないか。
23. `agy` が利用できる場合に Gemini 3.8 Flash で日本語の仕上げを行ったか。差分は日本語の表現だけで、意図、仕様、条件、不確実性、技術的な記述が保たれているか。未実施の場合は理由を記録したか。

## 納品と実装フェーズ

1. 納品メッセージには成果物パスと Unclear Points を含める。
2. 計画書一式を単独 commit する提案を添える。未コミットの計画は別 checkout やクラウド環境の実装エージェントに届かない。
3. 共有が必要な場合は、ユーザーが指定した公開先とプロジェクトの手順に従う。公開先の指定がなければローカルの成果物パスを渡す。
4. 実装は `$codex-impl` に委ねる。進捗は todo.md だけを更新し、設計変更時は計画書 HTML を改訂して改訂履歴に1行残す。
5. フロントエンドの変更がある場合、納品メッセージにモックのパスと、公開した場合はその URL を含め、実装前にモックの承認を求める。承認で変わった表示仕様は計画書へ反映してから実装に渡す。
