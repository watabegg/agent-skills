## 結論

直近2回が長引いた主因は、Workerの実装そのものより、実装後に同じ流れを何度も直列に繰り返したことだった。

```text
実装
  ↓
全体検証
  ↓
Gap Audit / Review
  ↓
指摘を修正するWorker
  ↓
全体検証をやり直す
  ↓
新しいSHAへGap Audit / Reviewをやり直す
```

レビューを省略すれば短くなる、という話ではない。実際に後段のレビューは複数の不具合を見つけており、品質面では役立っていた。問題は、同じSHAに対する複数の監査結果を全部集める前に修正を始めること、受入条件の確認が後段へずれること、修正のたびに同じ全体検証を複数roleが実行すること、そして通常のGap/Reviewer経路が修正round上限の外にあることである。

0.5.3では、次を採用する。

1. Managerが最初にリポジトリ全体の変更影響と守るべき不変条件を整理し、その情報からtask graphを作る。
2. 最初のdispatch前に独立したPlan Gap Checkを行い、要件、task、test、最終確認の抜けを先に見つける。
3. Workerへ実装、局所検証、回帰確認、自己レビュー、残存リスク報告までを一つの完了契約として要求する。
4. 中〜高リスクtaskだけは統合前に小さなPatch Reviewerを通し、task単位の回帰をintegration branchへ入れない。
5. 同じSHAに対するReviewerとGap Auditorを、それぞれ1 Coordinatorと複数の視点別subAgentで実行し、一つの「review epoch」に集約する。`codex-review-multi-v2`はReviewer実行が満たすprotocolであり、別の監査sourceとして二重計上しない。
6. `max_fix_rounds`をpre-final convergenceだけでなく、Gap/Reviewerから作られるすべての修正batchへ適用する。
7. 全体検証の実行者をManagerへ寄せ、同じSHAの証拠をReviewerとGap Auditorが再利用できるようにする。
8. Git metadataが書けないWorkerを起動直後からhandoff modeにし、ACK配送と最終証拠の手作業を減らす。

モデルは、通常Workerを`gpt-5.6-terra`の`max`、ReviewerとGap Auditorを`gpt-5.6-sol`の`xhigh`とする。狭い機械的変更だけ`gpt-5.6-luna`の`max`へ下げ、回帰リスクが高い実装とreview remediationは`gpt-5.6-sol`の`xhigh`へ上げる。Managerと最終Coordinatorは`gpt-5.6-sol`の`max`を推奨する。

この方針は、scope外の問題まで直してreview findingを0件にするものではない。現在のrelease scope、semantic fingerprint、finding dispositionを引き続き使い、scope内と確認できたfindingだけを修正候補にする。同じfingerprintへ異なるscope判定またはdispositionが付いた場合は、都合のよい候補を選ばず`classification_conflict`として停止する。

## 過去履歴で繰り返していた問題

### 1. ReviewとGapがtaskを増幅する

0.5.0の大規模runでは、STATEが53 task、16 batch、9 Review、8 Gapに達した。当初taskはT001〜T015で、T016〜T053の多くがreview、gap、remediation由来だった。当時はscope外findingをfirst-classなfollow-upへ逃がす経路が弱く、P0/P1をそのままfix taskへ変換しやすかった。

0.5.2はrelease scopeとfollow-upを導入し、scope外増幅をかなり抑えた。ただし、scope内findingが複数監査roundに分かれて見つかる問題は残った。今回の24 task中15件が後追加だったことがその例である。

### 2. `max_fix_rounds`がすべての修正経路を数えていない

現在の`review convergence record`は、`max_fix_rounds`を読み、上限へ達したら`review_convergence_exhausted`で止める。これは`hloop`の8036〜8118行付近で実装されている。

一方、通常のReviewerを`fix-tasks-created`でcloseする経路は19323〜19365行付近、Gap Auditorの同経路は19720〜19764行付近にあり、どちらもphaseを`dispatching`へ戻すだけでround上限を確認しない。`hloop triage --create-tasks`も20593〜20682行付近でtaskを作るが、convergence roundの予算を消費しない。

したがって0.5.2が上限を設けたのは「正式なpre-final convergence」であり、その前にnative Gap、native Reviewer、手動triageから何回修正batchを作れるかはまだ上限がない。これが、設計上の最も大きな抜けである。

### 3. 同じSHAの監査結果を一つに集約するbarrierがない

ReviewerとGap Auditorはそれぞれ独立にharvest、triage、closeできる。片方が`fix-tasks-created`になれば、もう片方や外部multi-reviewが完了していなくてもdispatchへ戻れる。

この形では、遅いlaneから追加findingが出るたびにtask contractの更新、再ACK、追加修正が発生する。また、別roleが同じ原因を異なる表現で報告したとき、semantic fingerprintを横断して重複排除する単一の確定地点がない。

### 4. 受入条件の確認が最後へ寄りやすい

`databook-accuracy2`ではG001時点でproduction caller、永続化、後続phaseのartifact不足が見つかり、最終的にT030後のG011で0 gapになった。0.5.2初回でもG001、G002、G003と段階的に別のplan接続不足が見つかった。

Gap Auditorが毎回全MISSION、PLAN、DECISIONS、task、resultを読み直すこと自体は正しい。しかし、同じ確認を毎roundゼロから行うと、監査時間が増え、確認の深さにもばらつきが出る。要件ごとのcoverage台帳を最初から持ち、前回の結論と変更された行だけを明示できれば、完全性を保ちながら再監査を短くできる。

### 5. validationの証拠は再利用可能だが、role運用が再利用していない

0.5.2には、target SHA、command列、lockfile、toolchain、resolved configが一致した場合のvalidation reuseが実装されている。`hloop`の1926〜1984行付近と18636〜18657行付近がその経路である。

それでも直近runでは、Worker、Manager、Gap Auditor、Reviewerが同じfull suiteをそれぞれ実行した。HLoopのreuseはManagerのintegration validationには効くが、role prompt上の「独立確認」と、HLoopが保証する「同一SHAの既存証拠」の役割分担が定義されていない。

### 6. Git metadata制約が毎taskで再発する

0.3.0調査では21 Worker中11件でGit metadataへ書けず、Managerがcommitまたはfinalizeを代行していた。0.5.2には正式なhandoffとsealがあり、安全な復旧はできるようになった。しかし直近2 runでも、Workerが通常finalizeを試し、read-only errorを確認し、Managerが追加指示してhandoffへ切り替える流れが繰り返された。

復旧経路は直ったが、起動前の経路選択はまだ直っていない。

### 7. ACKとpane監視にManager操作が多い

0.3.0調査では、一方のrunでManager messageが25件pendingのまま残り、Herdr server log 18,343行中16,225行が閉じたpaneへの`pane.get`失敗だった。現在はmessage identity、ACK、event wakeが追加されているが、直近runでもTUIのEnter送信、sleep lease owner、`unknown`配送状態の確認が発生した。

昔のclosed-pane probe問題は大きく改善している。残っているのは、Managerの承認がdurable stateでは完了していても、role側へその事実を届ける最後の操作がpane inputに依存する部分である。

### 8. 完了artifactとSTATEが実作業に追随しない

過去には、review artifactがworktreeにあるだけでharvestされていない、`phase: paused`とbranch HEADがずれる、cleanup flagが残ってfinishできない、という問題があった。0.4.0以降のnamespace、harvest、finish gateで多くは防げるようになった。

直近runでは、最終review manifestとrequirement progressの転記が最後に残った。安全なfail-closedではあるが、実装と検証が終わったあとにManagerが同じ証拠を別形式へ手で写す時間が発生している。

### 9. 0.5.1 releaseでも7回の再レビューが起きた

0.5.1 releaseでは、最初のGap PASSと4-lane reviewを2026-07-15 16:47 UTCごろに開始し、finding 0になったのは18:19 UTCだった。この間、候補SHAを修正してはGapと4 laneを再実行する流れが約7回あった。

各roundは、`rg` errorのfail-open、`git status` error、FIFO、固定SHA入力、可変ref、symlink、`noclobber`、evidence manifest、部分一致など、実際に有効なrelease blockerを見つけた。したがって「最初のreview以外をやめる」は不適切である。

一方で、release evidenceの脅威モデルと受入条件を最初の修正batch前に一覧化できていれば、後続roundで1〜2件ずつ見つかった問題の一部は最初のbatchへまとめられた可能性が高い。

## 0.5.2ですでに直っていること

0.5.3では、次を作り直さない。

- namespaceごとのSTATEとlocal-only persistence
- release scope lockとamendment
- scope外findingのfollow-up化
- semantic fingerprintとfinding disposition
- batch review cadence
- 同一SHA、同一command、同一依存関係に対するvalidation reuse
- `worker finalize --handoff`とManager seal
- fixed-target convergenceとmanual-final certification
- `max_fix_rounds = 2`というpolicy値
- worker runtime、batch wall time、validation time、review wait time、effective parallelismの基本メトリクス

今回必要なのは、これらを通常のGap、Reviewer、triage、role運用まで一貫してつなぐことである。

## 0.5.3で採用する設計

### P0：review epochをSHAごとの不変な証拠単位にする

**review epoch**は、同じtarget SHAを調べるGap実行とReviewer実行の結果を一つに集める単位である。1つのepochは作成時にtarget SHAと監査条件を固定し、修正後の新SHAを同じepochへ入れない。

```text
collecting
  ├─ Gap execution Gxxx
  └─ Reviewer execution Rxxx
        └─ required protocol artifact
             ↓ 全required executionがterminal
ready_to_triage
             ↓ fingerprintでgroup化し、classification conflictを解決
clean または remediation_batch_authorized
             ↓
closed

修正後の新SHA
  ↓
新しいepochを作成
```

epoch作成時に、次を一つのimmutable plan digestへ固定する。epochは`epoch_id`と単調増加する`epoch_revision`で識別し、作成済みrevisionのplanを上書きしない。

- epoch ID、base SHA、target SHA
- `scope_revision`、`source_snapshot_revision`、scope digest、source refs
- review policyと監査topologyのdigest
- required execution、lane、agent label、model、effort
- 公式validation identity

各artifactはepoch ID、epoch revision、execution ID、attempt ID、plan digestを持つ。release-scope amendment、review policy変更、監査topology変更、target SHA変更のいずれかが起きた場合は、active epoch、convergence draft、manual-final draft、accepted-risk projectionを同じstate transactionで無効化する。

同じSHAへ不足laneまたは追加verificationが必要になった場合も、作成済みrevisionへexecutionを追記しない。HLoopは同じ`epoch_id`のsuccessor revisionを作り、`parent_plan_digest`、追加するexecution、前revisionから継承するartifact digestを固定する。継承できるのは、target SHA、scope snapshot、policy、validation identity、execution identityが一致し、新revisionのrequired executionへ明示的に列挙されたartifactだけである。前revisionは`superseded_for_completion`として読み取り専用にし、新revisionのcompletenessだけをtriage gateに使う。

`reviewer close --verdict candidates-recorded`と`gap close --verdict candidates-recorded`は、個別に`dispatching`へ戻さない。finding candidateをepochへ登録し、required executionが全部terminalになるまで`collecting`に留まる。required executionが失敗またはtimeoutした場合はepochを`incomplete`にし、再実行、user-authorized exclusion、停止のいずれかを記録する。失敗したsourceをfindingなしとして扱うことはできない。

Reviewer executionが`codex-review-multi-v2`を使う場合、そのmanifestはReviewer executionのrequired protocol artifactである。Reviewerとexternal reviewという2件の独立sourceには数えない。epoch schemaは`source_kind`、`protocol`、`execution_id`、`artifact_ref`、`independence_key`を持ち、同じ`execution_id`または`independence_key`を複数の独立executionとして受理しない。

すべて揃ったらManagerが1回だけtriageする。semantic fingerprintは同じ問題の候補をgroup化するために使う。`fact_status`、`contract_relation`、`decision_requirement`、`disposition`、`release_effect`のいずれかが候補間で食い違う場合は`classification_conflict`としてfail-closedにし、Managerがcanonical classificationを記録するまでfix candidateまたはcleanへ進めない。accepted-risk authorizationはcanonical classificationを確定した後に同じfingerprintとtarget SHAへ再解決する。

### P0：ReviewerとGap Auditorを別々のCoordinator swarmにする

ReviewerとGap Auditorは目的が異なるため、一つの汎用swarmへ混ぜない。両方を同じtarget SHAへ固定して並列実行し、それぞれのCoordinatorが専門subAgentをまとめる。

```text
review epoch（同じtarget SHA）
  ├─ Reviewer Coordinator
  │    ├─ integration contract
  │    ├─ product correctness
  │    ├─ security / privacy / authorization
  │    ├─ data integrity / concurrency / failure recovery
  │    ├─ validation / observability
  │    └─ UX / accessibility または repository-specific risk
  │         ↓ candidateごとの独立verifier
  └─ Gap Coordinator
       ├─ requirement / PLAN coverage
       ├─ task / result / 実装 / caller / consumerの対応
       ├─ validation / migration / 運用証拠
       └─ scope / non-goal / decision / deferred item
            ↓ coverage challenge verifier
```

Reviewer側は0.5.2にすでに、swarm modeでは1 Coordinatorが4〜8個のprovider-native discovery laneと独立verifierを動かす契約がある。0.5.3では`codex-review-multi-v2`へ**externally planned mode**を追加する。HLoopがhead SHA、lane数、lane purpose、agent label、model、effortを渡した場合、skillは自身の既定4 laneや別Coordinatorを作らず、指定されたlaneだけを起動する。各lane resultはHLoopのlane identityへ一対一で対応し、lane自身は子Agentを起動しない。

`codex-review-multi-v2`のsourceはこのrepositoryに含まれないため、HLoopのPRからinstalled copyを暗黙に変更しない。ただし、0.5.3でこのprotocolを既定にするには、`externally-planned-v1`を提供するcompanion skillを0.5.3の明示的release dependencyへ含める。`release-dependencies.json`は配布元、skill version、content digest、required capability、最低互換versionを固定し、HLoop本体より先に対応版を配布する。CodexとClaudeのfresh sessionでcapability handshakeを実行し、install parityを確認できるまで0.5.3をreleaseしない。

HLoop側は機械可読なcapability manifestを読むadapterを実装する。required protocolが`externally-planned-v1`を要求するのにinstalled skillが対応していない場合は、4 laneへ黙って減らしたり二重Coordinatorを起動したりせずfail-closedにする。policyがnative Reviewerへのfallbackを明示している場合だけ、同じHLoop lane planをnative protocolで実行する。companion skillの更新はHLoopのproduct write scopeへ混ぜず、別repositoryまたは配布元をrelease dependencyとして追跡する。

Gap側はReviewerのgroup実行基盤を再利用するが、promptと出力schemaを要件監査専用に分ける。Gap subAgentへ通常のcode reviewをさせず、各要件の実装証拠、呼び出し経路、未完artifact、scope境界を確認させる。保存形式は次とする。

```text
gaps/Gxxx/
  PLAN.json
  lanes/<lane-id>.json
  challenge/<challenge-id>.json
  MANIFEST.json
  FINAL.md
```

`gap harvest`は全planned lane、coverage challenge、target SHA、epoch plan digest、agent identity、artifact completenessを検査する。欠けたlaneまたはchallengeがあるGapはterminal successにならない。`gap start`にはtopology、lane count、agent budgetを指定できるようにする。

既定はReviewer 6 discovery lane、Gap 4 discovery laneとする。二つのCoordinatorを含むdiscovery時の同時Agent数は12である。discovery laneが終了してslotを解放してから、独立verifierとcoverage challengeを起動する。

review epochは全roleを合わせた`audit_agent_budget`を持つ。HLoopはCoordinatorを起動する前に、epoch ID、execution ID、attempt ID、plan digest、予約slot数、有効期限を持つ`starting` leaseをSTATEへ保存する。起動成功で`running`へ遷移し、terminal、起動失敗でprocessが存在しないと確認できた場合、またはabort完了時にslotを解放する。

有効期限を過ぎただけではslotを解放しない。timeoutしたleaseは`expired_quarantined`へ移し、credentialを失効させる。Coordinatorと配下Agentの終了確認または強制停止のackが揃った後にだけterminalへ移してslotを返す。processを回収できない場合は、同じexecutionだけでなく、そのepochの新しいrole起動を止める。providerごとのcapacity checkや時刻経過だけでepoch全体の上限を代用しない。

同一SHAに対して同じpromptのReviewerやGapを無条件に何回も起動することは既定動作にしない。最初のepoch revision内で、独立した視点別discoveryとcandidate verifierを並列実行する。次のいずれかがある場合だけ、同じSHAへsuccessor revisionを作り、不足laneまたはchallenge passを追加する。

- planned laneが失敗、timeout、または未完だった
- Coordinator間で同じ事実への結論が矛盾した
- P0/P1候補の独立verificationが足りない
- coverage ledgerに未証明の必須要件が残った
- 新しいfingerprintが出続け、Coordinatorが探索不足を具体的に示した

修正後は新しいSHAなので、Review→fix→Review自体は残す。ただし、修正前に両Coordinatorの結果を全部集めて1 batchへ束ね、修正後は新しいepochで変更されたsurfaceを優先したdelta verificationと必須final reviewを行う。これにより、「1件見つけるたびに修正して全監査を再起動する」直列化を減らす。

### P0：すべての修正batchをround上限へ含める

roundは「Reviewerを何回起動したか」ではなく、「review findingから作った修正batchを何回自動実行へ進めたか」で数える。新しいSHAができた後に数えると上限を事前に強制できないため、Managerがcanonical candidate集合を承認し、batchが初めてdispatch可能になるstate transactionで1回消費する。

各batchは`remediation_batch_id`と次のledgerを持つ。

```text
candidate_registered
  ↓ 全required executionがterminalになり、classification conflictを解決
ready_to_triage
  ↓ Managerがcandidate集合とscopeを承認
authorized
  ↓ counterを1回だけ消費し、task作成planをwrite-ahead保存
materializing
  ↓ 全planned taskをSTATEとartifactへ永続化
dispatched
  ├─ product_changed → completed
  ├─ no_change → completed
  └─ aborted
```

同じ`remediation_batch_id`へのretry、task再開、idempotent recordはroundを再消費しない。複数sourceが同じbatchへcandidateを登録しても1回だけ数える。`no_change`または`aborted`を消費済みのままにするか返却するかはpolicyで曖昧にせず、0.5.3では自動実行へ進めた時点で消費済みとする。失敗した自動修正も計算量と回帰リスクを使うためである。

commandごとの責務を次へ固定する。

- `review convergence record`、`reviewer close`、`gap close`：candidateをepochへ登録する。roundを消費せず、taskも作らない。`fix-tasks-created`という、作成済みに見えるverdictは廃止して`candidates-recorded`へ置き換える。
- manual-finalからuser authorization付きでreopenした修正：candidateとauthorization refを登録する。roundを消費せず、taskも作らない。
- `triage epoch --approve-batch`：canonical candidate集合、scope、candidate-set digestを承認し、`remediation_batch_id`を予約する。同じtransactionでcounterを1回消費し、決定的task IDとtask contract digestを含むmaterialization planをSTATEへwrite-ahead保存する。roundを消費できる唯一のcommandにする。
- `triage epoch --materialize-batch`：保存済みplanだけを使ってtaskを作る。各taskのSTATE projectionとartifact digestを記録し、全件がdurableになった後にだけ`dispatched`へ進める。counterは変更しない。

materialization途中でcrashした場合、再実行は決定的task ID、task file、STATE projection、sourceの`created_fix_tasks`を照合し、欠けたものだけを補う。candidate-set digestまたは既存task contractがplanと違う場合は自動修復せず`remediation_reconcile_required`で停止する。これにより、taskの重複、欠落、roundの二重消費を防ぐ。

`max_fix_rounds`へ達したら、未完findingを表示して停止する。taskを自動追加しない。追加roundは既存どおりuser input IDと`authorized_extra_rounds`を必要とし、authorization refを特定の`remediation_batch_id`へ一度だけ結び付ける。

この変更により、native reviewを何度も回してからpre-final convergenceのroundを別に2回使う抜け道をなくす。

0.5.2 stateからのmigrationでは、`created_fix_tasks`、batch、source artifact、target SHA lineageから既に自動実行へ進めたremediation batchを決定的に復元する。複数taskを一つのbatchへ束ねた履歴を一意に復元できない場合は、小さい値へ推測せず`migration_decision_required`で停止する。既存のextra-round authorization refも新ledgerへ一度だけ移す。

### P0：ManagerがRepository Impact MapとTask Risk Graphを先に作る

Managerはtaskを切る前に、リポジトリを俯瞰した`Repository Impact Map`を作る。すべてのファイルを読むという意味ではなく、要求された変更から辿れる次の面を明示する。

- 変更対象のmodule、entry point、caller、consumer
- public API、schema、CLI、永続化、生成物、migration、互換性境界
- success pathとfail-closed path
- 変更してはいけない既存挙動とscope外のnon-goal
- 関連test、fixture、validation command、運用証拠
- task間で共有されるfile、symbol、invariant、merge順序

Repository Impact Mapは`planning/IMPACT.json`、Task Risk Graphは`planning/TASK-GRAPH.json`へ保存する。両artifactはrun ID、plan revision、release-scope identity、source digestを持つ。PLAN、Requirement、release scopeの変更時にはstaleにし、Plan Gap Checkと最初のdispatchを止める。

このmapから`Task Risk Graph`を作り、各taskへ少なくとも次を持たせる。

- `changes`：何を変えるか
- `preserved_invariants`：何を壊してはいけないか
- `write_allow`と`non_goals`
- `acceptance`と`regression_checks`
- `depends_on`と、同じsurfaceへ触れるtask
- `risk_class = mechanical | normal | high`
- `required_gates`：`patch_review`と`full_suite`を独立に指定できる集合

Managerは単に実装箇所でtaskを分けず、独立して検証できる単位と共有invariantで分ける。互いに同じ契約を変更するtaskは、並列化できそうでも依存関係を付けるか一つへまとめる。これにより、Workerが自分の局所受入条件だけを満たして隣接taskの前提を壊す回帰を減らす。

### P0：受入条件coverageとPlan Gap Checkをdispatch前に確認する

新しい汎用issue trackerは作らない。既存のRequirement、PLAN item、Task、Validation、Review laneを次の形で結ぶ薄い台帳を作る。

| 受入条件 | 実装task | 主な変更面 | 必須回帰test | 最終確認 |
| --- | --- | --- | --- | --- |
| REQ / PLAN ref | Txxx | path / component | command / test id | Gap / Reviewer lane |

台帳は`planning/COVERAGE.json`へ保存し、Impact Mapと同じidentityへ結び付ける。implementation loopでは、最初のbatchを開く前に次を検査する。

- すべての必須受入条件にtaskがある
- taskの`write_allow`が想定変更面を含む
- success pathだけでなくfail-closed pathのtest担当がある
- CLI、schema、docs、fixtureのような横断面に監査担当がある
- Manager-ownedの最終作業とWorker-ownedの実装が混ざっていない

この台帳とTask Risk Graphを、実装を担当しないPlan Gap Checkerが1回確認する。新しい汎用role lifecycleは増やさず、既存Specification Scoutへ`coverage` modeを追加し、そのmodeをPlan Gap Checkerとして使う。通常のSpecification Scoutは未決仕様の抽出を担当し、coverage modeはtask割当と検証証拠の不足だけを担当する。artifactは`planning/PLAN-GAP.json`へ保存し、`gpt-5.6-sol`の`xhigh`を使い、codeを変更せず次を検査する。

- requirementまたはPLAN itemに担当taskがない
- caller、consumer、migration、docs、fixture、failure pathがtaskから抜けている
- task間の依存順、共有invariant、write scopeが矛盾している
- 受入条件を証明できるtestまたは最終evidenceがない
- scope外の改善がtaskへ混入している

Plan Gap Checkで見つかった不足は最初のdispatch前にtask graphへ反映する。task graphを変更するとPlan Gap artifactはstaleになるため、修正後のrevisionへもう一度実行してcleanを記録する。実装後のGap Auditorの代わりにはしないが、受入条件の大きな抜けを後段まで持ち越さない。

修正後のauditでは、この台帳と前回epochとの差分を最初に渡す。Auditorは全体を確認できるが、変更された受入条件と未証明箇所から優先して調べられる。

### P0：Workerの完了契約に回帰確認と自己レビューを含める

Workerはcodeを書いた時点では完了しない。taskごとに次の順序を要求する。

1. task contract、近傍のcaller / consumer、関連testを読んで前提を確認する。
2. 最小の変更を実装する。
3. 変更箇所のtargeted testを実行する。
4. `preserved_invariants`と`regression_checks`を実行またはコード上の証拠で確認する。
5. task branchのdiffだけを自己レビューし、scope外変更、error path、互換性、test不足を確認する。
6. candidate artifactへ、変更内容、検証結果、守ったinvariant、残存リスク、未実行検証を記録して提出する。
7. required Patch Reviewとvalidation gateが完了した後に、同じ証拠をfinal resultへ投影する。

task schema、`task new/update`、STATE task projection、Worker promptへ、`contract_schema_revision`、`preserved_invariants`、`regression_checks`、`risk_class`、`required_gates`、`worker_agent_effort`、`investigation_goal`、`implementation_ready_evidence`、`exploration_budget_minutes`、`history_search_allowed`を追加する。candidateとresult schemaには`contract_schema_revision`、`invariant_evidence`、`regression_evidence`、`self_review_summary`、`residual_risks`、`unrun_checks`を追加する。

`preserved_invariants`または必須`regression_checks`の証拠がないtaskは`implementation_complete`へ進めない。検証できない場合は成功扱いにせず、`blocked`またはManager-owned gateへ渡す。`additionalProperties: true`による手書きfieldの通過を契約実装と見なさず、schema、CLI、state projection、finalize、harvest、mergeのすべてで型と必須性を検査する。

### P0：中〜高リスクtaskへ統合前Patch Reviewerを置く

`risk_class = high`、または共通CLI、schema、認証、永続化、migration、並行処理、public APIへ触れるtaskは、`required_gates`へ`patch_review`を含める。cross-cuttingなfull suiteも必要なら`patch_review`と`full_suite`の両方を含める。通常taskでも、ManagerがTask Risk Graphから複数consumerへの影響を認めた場合は対象にする。

Patch Reviewerは`gpt-5.6-sol`の`xhigh`を使い、task branchの差分、task contract、`preserved_invariants`、関連callerとtestだけを見る。ここでrepository-wideな最終reviewを繰り返さない。目的は、Workerが作った局所回帰を安い段階で止めることである。

Patch Reviewはcandidate提出とfinalizeを分ける。commit modeとhandoff modeのどちらでも、Patch Reviewerが読む変更を含むexact candidate SHAを先に作り、この段階では`merge_ready: false`を保つ。

```text
running
  ↓ Workerが実装とL1 evidenceを提出
implementation_complete
  ↓ commit mode: Worker candidate commit
  ↓ handoff mode: Manager candidate seal
candidate_sealed（merge_ready = false、exact candidate SHAを固定）
  ↓ exact candidate SHAへPatch Reviewを実行
patch_review_pending
  ├─ passed → required validation gate → worker finalize → result_reported
  └─ fix_required → patch_fix_running → candidate再提出 → patch_review_pending
```

`worker submit`は`implementation-candidates/<task-id>/<attempt-id>/<candidate-revision>.json`へL1 evidenceとcandidate tree identityを書き、terminal resultやcompletion sentinelを出さない。commit modeではWorkerがcandidate artifactとproduct changeをcommitする。handoff modeではManagerがWorker paneをquiesceし、`worker candidate-seal`でdirty product、candidate artifact、task contractを一つのcommitへ固定する。candidate sealはpane、attempt credential、semantic ACKを維持し、Manager validationを成功扱いにせず、`merge_ready`を必ずfalseにする。

Patch Review artifactは`patch-reviews/<task-id>/<attempt-id>/<review-attempt-id>.json`へ保存し、task ID、attempt ID、task contract digest、base SHA、exact candidate SHA、candidate artifact digest、finding fingerprint、verdictを持つ。candidate SHAまたはcontractが変われば古いartifactを無効化する。`fix_required`では同じtask attemptを`patch_fix_running`へ戻し、Workerは新しいcandidate revisionを提出する。handoff modeでもManagerが作ったcandidate commitをbranch HEADとしてWorker worktreeへ反映してからpaneを再開する。credentialを失効させたりpaneをcleanupしたりしない。

`worker finalize`は最新candidateのrequired Patch Reviewとfull suiteが完了した後にだけfinal result、completion sentinel、`merge_ready: true`を出す。handoff modeの最終sealも同じgateを検査する。`worker harvest`と`merge`はcandidate SHA、Patch Review、validation identity、final resultの対応を再検査する。

指摘は同じtaskの修正として扱い、release全体の`max_fix_rounds`は消費しない。ただし`max_patch_review_rounds_per_task = 2`を既定とし、上限へ達したら未解決findingと最後のcandidate SHAを保存してuser decisionへ止める。同一review attemptのidempotent recordは二重計上しない。Patch Reviewerから新しいscopeのtaskを自動作成せず、scope外またはtask外の問題はfollow-up候補としてManagerへ返す。

### P0：validationの役割を3段階に分ける

| 段階 | 実行者 | 内容 |
| --- | --- | --- |
| L1 | Worker | 変更箇所のtargeted test、lint、self-review |
| L2 | cross-cutting WorkerまたはManager seal | 中央CLI、schema、共通fixtureを変えるtaskのfull suite |
| L3 | Manager | integration SHAに固定した公式full validation |

ReviewerとGap Auditorは、同じSHAへ固定されたL3 evidenceがfreshなら、一般的なfull suiteを再実行しない。代わりにfindingの再現、変更箇所のtargeted test、artifact identityの確認を行う。

独立性が必要なvalidationは`independent_verification`として別に指定する。すべてのroleが同じcommandを何となく再実行するのではなく、どのsuiteだけ独立実行が必要かをplanで明示する。

公式validation command列はepoch開始前に確定する。quick validatorのような追加commandは`auxiliary_validation`として別枠に記録し、公式command列を変えて既存証拠を無効にしない。

現行validation identityは`resolved_config`全体を含むため、roleのmodel、effort、lane数を変えただけでも証拠が失効する。0.5.3ではidentityを次へ分ける。

- `validation_identity`：target SHA、ordered command列、lockfile、toolchain、setup command、productまたはtestへ影響する設定
- `audit_identity`：review policy、role model、effort、lane topology、epoch plan digest

role routingだけの変更はL3 evidenceを無効化しない。一方、audit artifactは`audit_identity`が一致しなければ再利用しない。config schemaの全keyを、`validation-affecting`または`audit-only`のどちらかへ分類するregistryを正本にし、`resolved_config`全体のdigestをそのまま使わない。registry versionをvalidation identityへ含める。schema-validなkeyが未分類、未知schema revision、registry version不一致のいずれかなら、そのkeyを除外せずvalidation evidenceをstaleにする。schemaの全leaf keyが一度だけ分類されることをtestで検査する。

### P1：roleとriskに応じてmodelを固定する

modelは一律に最上位へ上げず、判断の難しさと回帰コストで選ぶ。

| role / task | model | effort | 理由 |
| --- | --- | --- | --- |
| Manager | `gpt-5.6-sol` | `max` | リポジトリ俯瞰、task分解、scopeと品質の最終判断を担う |
| Plan Gap Checker | `gpt-5.6-sol` | `xhigh` | 実装前に横断的な要件抜けと依存矛盾を探す |
| 通常Worker | `gpt-5.6-terra` | `max` | 実装品質と速度の標準バランス |
| 狭い機械的Worker | `gpt-5.6-luna` | `max` | 変更手順と期待diffが明確な場合だけ使う |
| 高リスクWorker / review remediation | `gpt-5.6-sol` | `xhigh` | 複数契約、failure path、回帰を同時に扱う |
| Patch Reviewer | `gpt-5.6-sol` | `xhigh` | task単位の回帰を統合前に検出する |
| Reviewer Coordinator / discovery / verifier | `gpt-5.6-sol` | `xhigh` | 高い発見率と候補の独立事実確認を優先する |
| Gap Coordinator / discovery / verifier | `gpt-5.6-sol` | `xhigh` | 要件と実装の横断照合を優先する |
| Final Coordinator | `gpt-5.6-sol` | `max` | 全証拠、scope、残存findingを最終統合する |
| Advisor | `gpt-5.6-luna` | `max` | opt-inの相談を担当し、gateや最終判断は持たない |

既定WorkerはTerraにするが、Managerは`risk_class`からtask単位でLunaまたはSolへ上書きする。Lunaを通常Workerの既定にはしない。過去runから、遅さの主因がLunaだけだったとは断定できないが、review remediationのように既存契約を同時に守るtaskで弱いmodelを使うと、安価な1回の実装が高価な再監査roundを生むためである。

現行0.5.2の階層configが直接設定できるroleはWorkerとReviewerだけである。0.5.3では`manager`、`gap`、`plan_gap`、`patch_reviewer`、`final_coordinator`、`advisor`と`audit`を追加する。各roleは`provider`、`model`、`effort`を持ち、Coordinator型roleは`coordinator`、`lane`、`verifier`の既定値を個別に持てるようにする。Advisor dialogueではparticipant overrideをtask/start override相当の最上位layerとして記録する。設定不能なroleを暗黙にReviewer設定へ寄せない。

Reviewer lane数の正本は`reviewer.lane_count`に統一する。0.5.2の`review.lane_count`、`reviewer.probe_count`、`reviewer.probes_per_provider`はmigration aliasとして読み取るが、resolved configにはcanonical keyだけを残す。各layerの中でaliasをcanonical keyへ正規化し、同じlayerに異なる値が併記された場合だけconfig errorにする。異なるlayerでは、上位layerのcanonical値が下位layerを通常どおり上書きする。`auto`とlegacy probe値のfallbackも同じ正規化規則へ含める。Gapも`gap.lane_count`を正本とする。

Manager configは新しいManagerを起動する設定ではない。HLoopを呼び出しているManagerの期待identityを表し、起動環境から観測できたprovider、model、effortと照合するpreflight assertionである。identityを観測できない環境では、config値を実測値として記録せず`unavailable`を残す。strict modeでは開始を止め、compatibility modeでは警告と未証明attestationを記録する。

各manifestは`requested`、`observed`、`attested`を分けてmodelとeffortを記録する。providerがplanned subAgentの実値を返さない場合、設定値を観測値として扱わない。required attestationが欠けた場合にfail-closedにするroleをconfigで指定する。

### P1：Worker起動時にcompletion modeを決める

Manager processからGit metadataへ書けるか調べても、Workerの実際のsandbox能力は分からない。Worker agentのsandbox内で、material workとsemantic ACKの前に専用capability preflightを実行し、そのWorkerのGit common dirとworktree metadataへ衝突しない一意な一時fileをcreate、fsync、deleteできるか確認する。共有`index.lock`は使わず、cleanup失敗も記録する。

- 書き込み可能：`completion_mode = commit`
- read-only：`completion_mode = handoff`

preflight結果はattempt identityへ固定し、Workerがsemantic ACKと一緒に報告する。Managerが承認した後にmaterial workを始める。handoff modeのWorker promptでは、通常commitや代替indexを試さず、最初からcandidate artifactとvalidated diffをManagerへ渡す。Patch Reviewが必要ならManager candidate seal、合格後はfinal sealをtask contractに含まれる標準経路として扱う。probeが実行不能または結果不明なら安全側のhandoff modeにする。

これにより安全性は変えず、毎taskの「commit失敗を確認してからhandoffへ切り替える」往復をなくす。

### P1：ACK承認をpane inputから切り離す

semantic ACKとManager approvalの正本はbroker / STATEに置く。Managerが承認したあと、paneへの文字入力が失敗してもroleが`ack status`またはwake eventから承認を取得できるようにする。

semantic decisionとroleへの承認通知は、別の状態機械として記録する。

- semantic decision：`awaiting_ack | approved | rejected | timed_out | superseded`
- approval application：`pending | delivered | acknowledged | applied | undelivered | unknown | superseded`

`rejected`は訂正ACKを要求する状態、`superseded`は別contractへ置き換えられた状態なので統合しない。contract変更時は古いsemantic decisionとapproval applicationをsupersedeし、新しいcontract digestへbarrierを作る。

`agent ack resolve`はsemantic decisionの永続化が成功した時点でその結果を返し、通知の成否を同じ成功条件へ混ぜない。roleはbrokerから承認を取得し、`acknowledged`または`applied`を返す。pane inputはwakeの補助に限定し、Enter配送の失敗だけで承認済みroleが止まり続けないようにする。

### P1：最終証拠の転記を自動化する

同じepoch plan digestで、Reviewerのrequired protocol manifest、Gap manifest、Manager validationが揃っている場合、HLoopがconvergence用manifestの下書きを生成する。

ただし、通常Reviewer artifactから独立manual-finalを捏造してはならない。manual-finalが独立executionを要求するpolicyなら、通常epochとは異なる`execution_id`と`independence_key`を持つ実artifactが必要である。通常Reviewerがmanual-finalも兼ねるpolicyなら、その事実をepoch planで先に固定し、同じ実行を二つの独立sourceとして数えない。

Requirement progressは自動で`verified`にしない。`requirements reconcile --dry-run`で、merged task、validation、Gap、Reviewerに基づく推奨transitionとevidence refを表示し、Managerが`--apply`して確定する。これならfinish直前の9回の手入力を減らしつつ、証拠のない自動完了を防げる。

### P1：Workerの調査時間にfocus gateを設ける

T006は、Managerが「調査は十分、最小patchへ進む」と伝えるまで既存コードとtestの照合を続けた。難しいtaskでは調査が必要なので、一律の短いtimeoutにはしない。

代わりにtaskへ次を持たせる。

- `investigation_goal`
- `implementation_ready_evidence`
- `exploration_budget_minutes`
- `history_search_allowed`

Managerが`implementation-ready`を記録した後は、新しいblocking evidenceがない限り、過去commitの追加探索ではなく実装へ進む。budget超過時は自動中断ではなくattentionを上げる。

### P2：時間メトリクスを実際のボトルネックへ合わせる

既存メトリクスへ次を追加する。

- run全体のwall time
- Manager active / waiting / user-blockedの区別
- review epoch数とepochごとのtarget SHA
- planned task数とreview由来task数の比率
- remediation batch数
- SHAごとのfull validation実行回数とreuse回数
- ACK待ち時間
- commit modeとhandoff modeの件数
- artifact reconcileとfinish準備に使った時間
- epochごとのplanned、reserved、peak live Agent数
- laneごとのruntime、timeout、finding候補数、verified finding数
- fingerprint重複率と`classification_conflict`件数
- provider capacity待ち時間
- Patch Review round数、統合前に防いだfinding数、最終reviewへ漏れたfinding数
- tokenまたはcostをproviderから取得できる場合のrole別使用量

Outcome reportでは「13時間45分の壁時計」と「active time」を別に表示する。これにより、UIで見えた約9時間とSTATEの13時間40分のような差を次回から説明できる。速度だけでなく、verified finding yield、escaped finding、scope外task化件数を同時に測り、Agent数を増やして品質が変わらず費用だけ増えた場合も判別できるようにする。

## 0.5.2から0.5.3への移行

0.5.3は`state_format_version: 3`を維持し、`schema_revision: 3`へ上げる。migrationはrepositoryとnamespaceのlock下で二段階transactionとして実行する。最初に元のSTATE、namespaced artifact index、変更対象artifactのbytesとdigestをarchiveし、`migration_generation`、archive digest、予定出力digestを持つ`prepared` markerをfsyncする。その後、3.3出力を一時pathへ書いてfsyncし、決めた順序でatomic renameしてから`committed` markerを保存する。起動時に`prepared`だけが残っていた場合は、各digestを照合してapplyを再開するかarchiveへrollbackし、3.2と3.3を混在させない。

dry-runは変更点、復元したremediation round、停止理由、rollback eligibilityを表示する。最初の0.5.3 material commandは同じstate transactionで`first_v053_mutation_at`とcommand identityを保存する。このmarkerが空で、migration transactionが`committed`の場合だけ3.2へrollbackできる。marker保存後のrollback要求、archive digest不一致、partial transactionを解決できない場合はfail-closedで停止する。rollback自体も一時path、fsync、atomic rename、完了markerを使う。

既存taskはstatusごとに扱いを分ける。

- terminalまたはmerged task：`contract_schema_revision = 2`の履歴として保持し、0.5.3の新gateを遡及適用しない
- queued task：`contract_schema_revision = 2`と`migration_blocker = risk-classification-required`を持たせ、`risk_class`には移行専用値を書かない。Managerが3値のrisk class、invariant、regression check、required gate、effortを補い、revision 3へ変換するまでstartしない
- running task：`contract_schema_revision = 2`のまま自動でcontractを書き換えない。Managerが0.5.2 contractで完了させるか、revision 3へ原子的にrebindして新しいsemantic ACKを要求するか選ぶ。requeueまたは新attemptはrevision 3を必須にし、legacy completionを継承しない
- result reportedかつ未merge task：resultにも`contract_schema_revision = 2`を記録して既存evidenceを保持し、Managerがlegacy acceptanceを記録するかrevision 3のgateを追加するまでmergeしない

task、candidate、result schemaは`contract_schema_revision`をdiscriminatorにしたversioned unionとする。revision 2のlegacy completionは既存0.5.2 gateだけを通り、revision 3のtaskだけが`risk_class = mechanical | normal | high`と新しいevidence fieldを必須にする。legacy用optional fieldをrevision 3のfail-open経路として使わない。

active Reviewer、Gap、convergence、manual-finalは新epochへ暗黙に変換しない。migration dry-runはactive roleを列挙し、harvestしてlegacy artifactとして閉じるかabortするまで新epoch開始を止める。legacy artifactはfollow-upや調査証拠として保持できるが、0.5.3 epochのrequired executionには数えない。

remediation ledgerは既存sourceの`created_fix_tasks`、batch、task origin、target SHA lineage、convergence round、extra-round authorizationから復元する。復元結果が一意でない場合は`migration_decision_required`へ止め、候補となる消費roundと根拠を表示する。Managerまたはユーザーが明示した値とinput refを記録するまでdispatchを再開しない。

config migrationは既存Worker、Reviewer、Advisorの設定を保持し、新roleのdefaultを追加する。通常Reviewerは既存`review_protocol`、pre-finalとmanual-finalは既存review policyをそれぞれのcanonical keyへ移し、`manual_final_execution = independent`を追加する。lane aliasはlayerごとに正規化してから通常のhierarchical precedenceを適用する。Manager identityやplanned subAgentの実測値が取得できない場合は`unavailable`とし、設定値を観測結果へコピーしない。

config変更によってvalidation evidenceを一律に失効させず、classification registryで`validation-affecting`と判定したkeyだけをidentityへ含める。ただし、未分類key、未知schema revision、registry version不一致は安全側にvalidationをstaleにする。

## 期待できる短縮幅

次の数値は実装前の仮説であり、受入条件には使わない。Plan Gap、Patch Review、Reviewer 6 lane、Gap 4 laneが増えるため、総Agent時間または費用は増える可能性がある。評価ではwall time、active time、品質、Agent使用量を分ける。

### 15件修正run

約3時間56分から、3時間10分以下を暫定目標とする。2時間40分〜3時間10分という従来推定は参考値として残すが、0.5.3の実測が揃うまで25〜35%短縮を確定値として扱わない。

主な短縮元は、T006へfull suiteを含めてT007を独立taskにしないこと、同一SHAのfull suiteをManager証拠として再利用すること、ACK / handoff / manifest / requirement転記の往復を減らすことである。R13のように修正後に初めて現れる実害findingは残るため、T008と最終確認まで消えるとは見積もらない。

### 0.5.2初回実装run

13時間45分の壁時計から、9時間以下を暫定目標とする。約7〜9時間という従来推定は参考値として残すが、0.5.3の実測が揃うまで35〜50%短縮を確定値として扱わない。

最初の2時間38分の実装を大幅に削る想定ではない。後段11時間のうち、G001、G002、G003で分割された受入条件確認をdispatch前coverageとreview epochで1〜2個のまとまった修正batchへ寄せる。修正が新しい不具合を作った場合の再監査は維持する。

ユーザー観測の約9時間をactive timeと仮定するなら、active timeの参考目標は約5時間30分〜7時間である。ただし、現行ログから9時間という分母を再現できないため、実装後は新しいwall / active metricで比較する。

release後の最初の3 runを評価期間とする。既存0.5.2 baselineに対して、P0/P1 escaped finding、scope外task化、manual-finalの安全性が悪化していないことを確認したうえで、中央値のwall timeとactive timeを比較する。速度が改善しても品質指標が悪化した場合は成功扱いにしない。

## 受入条件

0.5.3は、少なくとも次を満たす必要がある。

1. 最初のdispatch前に、release-scope identityへ結び付いたRepository Impact Map、Task Risk Graph、acceptance coverage ledgerが存在する。
2. PLAN、Requirement、release scopeが変わるとplanning artifactがstaleになり、再生成とPlan Gap Checkが終わるまでdispatchできない。
3. Specification Scoutのcoverage modeが、必須Requirement、PLAN item、caller、consumer、failure path、test、最終evidenceの未割当をfail-closedで検出する。
4. revision 3のtaskが`preserved_invariants`、`regression_checks`、`risk_class`、`required_gates`、`worker_agent_effort`をschema-validなfieldとして持つ。
5. task、candidate、resultが`contract_schema_revision`を持ち、revision 2のlegacy契約とrevision 3の契約をversioned unionとして検証する。
6. queued legacy taskはrisk classを3値のいずれかへ再分類してrevision 3へ変換するまでstartできず、running legacy taskは明示的なlegacy completionまたはfresh semantic ACK付きrebindだけを選べる。
7. Workerはinvariant、regression check、self-review、残存risk、未実行checkの証拠なしに`implementation_complete`へ進めない。
8. `required_gates`はPatch Reviewとfull suiteの同時必須を表現できる。
9. `worker submit`はterminal resultを出さず、commit modeとhandoff modeのどちらでも`merge_ready: false`のexact candidate SHAを作れる。
10. handoff candidate sealはpane、attempt credential、semantic ACKを維持し、`fix_required`後に同じattemptで新candidateを提出できる。
11. Patch Reviewはexact candidate SHA、candidate artifact digest、attempt ID、task contract digestへ固定され、candidateまたはcontract変更でstaleになる。
12. Patch Review findingの修正後はvalidationとPatch Reviewを再実行し、古いartifactだけでfinalizeまたはmergeできない。
13. `max_patch_review_rounds_per_task`到達後は自動修正せず、未解決findingを保持してuser decisionへ停止する。
14. Patch Reviewerはtask外findingから新しいscope内taskを自動作成しない。
15. Reviewer swarmは1 Coordinatorと6 discovery laneを使い、`codex-review-multi-v2`のexternally planned modeが同じlaneだけを起動する。required capabilityがないinstalled skillではfail-closedになり、暗黙の4 lane化または二重Coordinatorを起こさない。
16. `externally-planned-v1`対応版の配布元、version、content digestをrelease dependencyへ固定し、CodexとClaudeのfresh sessionでcapability handshakeが通るまで0.5.3をreleaseしない。
17. Reviewer executionと、そのexecutionが生成した`codex-review-multi-v2` artifactを二つの独立sourceとして数えない。
18. Gap swarmは1 Coordinator、4要件監査lane、1 coverage challengeを使い、PLAN、lane result、challenge result、MANIFEST、FINALを保存する。
19. Gap harvestはplanned lane、challenge、target SHA、epoch plan digest、agent identityの不足をfail-closedで検出する。
20. review epoch全体のreservedおよびlive Agent数が`audit_agent_budget`を超えず、lane subAgentは子Agentを起動しない。
21. timeoutしたslot leaseはprocess終了または強制abort確認まで`expired_quarantined`としてcapacityを保持し、回収不能ならepochの新規起動を止める。
22. epoch revisionはtarget SHA、scope snapshot、policy、topology、validation identityへ固定され、作成後にrequired executionを変更しない。

## 判断

0.5.3では、上流の品質gateと下流の収束gateを一つのrelease scopeで実装する。Repository Impact Map、Plan Gap Check、Worker invariant、Patch Reviewerは、最終reviewへ流れ込むfindingを減らす。ReviewerとGapのCoordinator swarm、SHAごとのreview epoch、共通remediation ledgerは、残ったfindingを一度に集めて少ない修正batchへ束ねる。

ReviewerはすでにCoordinator swarmの土台を持つため、`codex-review-multi-v2`を別の監査sourceとして重ねない。externally planned modeでHLoopのlane planをそのまま実行し、Gapへ要件監査専用のgroup artifactとchallengeを追加する。

`max_fix_rounds`は同じrelease scopeで自動修正を続ける上限である。上限へ達した時点でもfindingは捨てず、未解決一覧と証拠を保ったままuser decisionへ止める。Patch Reviewにもtask単位の別上限を設ける。scope外findingはfinding数を減らすために実装せず、follow-upへ分離する。

validation identityの分離、Worker sandbox内handoff判定、broker基準のACK、最終artifact投影は、重複実行と操作待ちを減らす。reviewの観点数、独立verification、final gateを維持しながら直列のReview→fix往復を減らし、品質と速度を別々の指標で検証する。
