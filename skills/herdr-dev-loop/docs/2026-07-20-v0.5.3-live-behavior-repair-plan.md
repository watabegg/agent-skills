# herdr-dev-loop 0.5.3 live behavior repair plan

Status: implemented on the closeout branch; release validation remains hold

## 目的

2026-07-20 の live Herdr/Codex TUI QA で確認した三つの問題を、0.5.3 の release 前に修正する。対象は semantic ACK の candidate gate、Codex TUI への Manager message 送信、role から canonical Manager repo を参照する経路である。

この修正は 0.5.4 の新機能ではない。0.5.3 がすでに宣言している contract re-ACK、pane に依存しない承認取得、revision-3 candidate completion を成立させるための closeout fix とする。

## 確認済みの事実

### Contract-changing barrier と candidate gate

`rebind_contract_changing_manager_message()` は、`arm_semantic_ack_barrier()` の既定値を使って `kind=message` の barrier を作る。一方、`approved_semantic_ack_event_id()` は revision 3 で `initial` と `task-contract` だけを許可する。

live QA では current barrier の decision が `approved`、application が `applied` であり、attempt、digest、ACK event、application event も一致していた。それでも `worker submit` は次のエラーで停止した。

```text
hloop: candidate gate blocked for T001: legacy unstructured ACK is forbidden
```

これは state divergence ではない。canonical Manager state を正しく発見した後に、正規の `kind=message` を candidate gate 自身が拒否している。

### Codex TUI の Enter

Manager message の本文は一回だけ Codex TUI の入力欄へ入った。しかし、現行の可視性判定は本文の先頭と末尾を同じ pane snapshot で要求するため、長い message を確認できず `delivery=unknown` になった。その経路では Enter を送らない。追試では、長い multiline input が欠落したのではなく、Codex TUI の表示領域が入力の先頭側に留まり、末尾 marker が隠れることも確認した。`Ctrl+E` で論理的な末尾へ移動すると、本文を変えずに末尾 marker を確認できる。

pane を直接確認して本文を再送せず Enter だけを送ると、最初の Enter では turn が始まらず、二回目の遅延 Enter で `agent_status=working` へ遷移した。

現行の `manager_message_submitted()` には、pane text が変化し、同じ message が見えていれば submit 済みとする分岐もある。この条件は、Enter が改行になっただけの状態を成功と誤認する可能性がある。

### Canonical Manager repo

live Worker の初回 `agent ack exchange` command には、生成 prompt の時点から `--manager-repo /tmp/hloop-live-qa-3165cf4` が含まれていた。初回 Worker ACK が環境変数の欠落だけで失敗した、という診断は正しくない。

実際の不足は次の二点である。

1. Worker と Patch Reviewer の prompt は `--manager-repo` を含むが、Reviewer、Gap Auditor、Advisor、decision Scout、coverage Scout、Liaison の prompt renderer は canonical repo を固定していない。
2. `agent ack status` の実装は `args.manager_repo` を読めるが、CLI parser に `--manager-repo` がなく、生成 prompt の compatibility command にも絶対 path がない。Codex の内部 shell が `HLOOP_MANAGER_REPO` を保持しない場合、Worker worktree の古い state を読む。

したがって、修正対象は環境変数の継承そのものではない。全 role command が canonical Manager repo を明示し、環境変数を routing の正本にしないことが修正方針になる。

## Release 判定

三件を同じ重要度では扱わない。

| ID | 問題 | 優先度 | Release への影響 |
| --- | --- | --- | --- |
| LB-01 | `kind=message` を candidate gate が拒否する | P0 | 0.5.3 release blocker |
| LB-02 | TUI message が入力済みのまま submit されない | P1 | live canary blocker |
| LB-03 | 一部 role と `ack status` が Manager repo を明示しない | P1 | multi-role canary blocker |

LB-01 を直すだけでは release しない。LB-02 と LB-03 を含む live canary が完了するまで、release recommendation は `hold` のままにする。

## 保持する不変条件

1. current attempt、message、digest、ACK event、application event が完全一致し、application が Manager state に適用されるまで material work を許可しない。
2. legacy scalar ACK、fallback spool、pane input、古い ACK、古い application を承認証跡にしない。
3. Manager message の本文を構成する各 byte は一回だけ `send-text` する。start、body、end は分割送信してよいが、body を再送しない。Enter retry は本文送信と分離する。
4. delivery が判定不能なら body を自動再送しない。
5. Enter-only retry は同じ run、role、attempt、pane session、message ID が確認できる場合に限る。
6. role の command は canonical Manager repo を絶対 path で固定する。`HLOOP_MANAGER_REPO` は accidental misuse guard の補助に留める。
7. 既存の `kind=message` を持つ 0.5.3 state を、正しい structured binding がある場合に限って継続可能にする。

## Task graph

中央の `scripts/hloop` を三 task が変更するため、実装は直列にする。別 Worker に同時編集させない。

```text
LB-01 candidate gate repair
  -> LB-03 canonical Manager repo pinning
  -> LB-02 TUI submit and Enter-only recovery
  -> exact-SHA pre-canary validation
  -> LQ-01 disposable live canary
  -> one review epoch on the unchanged canary SHA
```

LB-01 と LB-03 は小さい protocol consistency fix である。LB-02 は transport state と CLI を変更するため、前二件を固定してから扱う。

## LB-01: structured `message` barrier を candidate gate へ接続する

### 実装方針

新しい schema kind は増やさない。0.5.3 の `arm_semantic_ack_barrier()` は `message` を contract-changing Manager message としてすでに生成しているため、revision-3 の structured kind 集合を次の三つとして一か所に定義する。

```python
REVISION_THREE_STRUCTURED_ACK_KINDS = {
    "initial",
    "task-contract",
    "message",
}
```

`approved_semantic_ack_event_id()` は kind だけで承認しない。既存の `semantic_ack_barrier_blocking()` が要求する exact application binding に加えて、次を検査する。

- `kind=message` には UUID の `message_id` がある。
- barrier の `report_identity_status` が `bound` である。
- `active_report_contract_digest` と barrier digest が一致する。
- ACK sequence が `required_reack_after_sequence` より後である。
- decision と application が同じ ACK event を指す。

candidate authorization を `manager_messages` の transport record には結び付けない。role が current digest の authenticated ACK を送り、Manager が exact application を適用した事実は broker と barrier が証明する。pane delivery record は監査証跡であり、承認 authority ではない。

既存の legacy barrier は kind がないか、separate decision/application record がないため、引き続き拒否される。エラー文は「legacy unstructured ACK」と「unsupported structured barrier kind」を分ける。

### Test-first cases

1. 完全に bind された `kind=message` は candidate submit を通す。
2. UUID でない `message_id`、未boundの report identity、active digest mismatch を拒否する。
3. old ACK、old application、digest mismatch、sequence floor 以下を拒否する。
4. kind なしの legacy barrier を拒否する。
5. unknown kind を拒否する。
6. 初回 ACK で決まった completion mode を replacement ACK が変更できない。
7. commit mode と handoff mode の双方で submit、seal、finalize、harvest、merge まで通す。

### 完了条件

contract-changing message の replacement ACK を適用した Worker が、同じ exact ACK event を candidate artifact に記録し、通常の completion lifecycle を最後まで通れる。

## LB-03: canonical Manager repo を全 role command へ固定する

### 実装方針

`report_contract_text()` は credential を含む live prompt を生成するとき、`manager_repo` の省略を許さない。省略した renderer は prompt 生成時に失敗させる。

次の全 renderer と start path に canonical repo を渡す。

- Worker
- Patch Reviewer
- Reviewer
- Gap Auditor
- Advisor
- decision-mode Specification Scout
- coverage-mode Specification Scout
- Decision Liaison

`agent ack status` に `--manager-repo` を追加し、Worker prompt の compatibility command は絶対 runtime path、明示 namespace、絶対 Manager repo path を固定する。`agent ack exchange` と `agent ack status` は、role repo と Manager repo が同じ Git common directory に属し、run、role、attempt が一致することを検証する。

`HLOOP_MANAGER_REPO` は残す。ただし、routing は生成 command の明示引数を正本とし、環境変数は手動 command の fallback と subordinate guard に限定する。

### Test-first cases

1. 全 role prompt の exchange command に `--manager-repo <absolute-path>` が一回だけ含まれる。
2. `HLOOP_MANAGER_REPO` を unset した subprocess でも、生成 command から ACK exchange が成功する。
3. standalone `ack status --manager-repo` が Worker worktree から current Manager state を読む。
4. 別 Git repository、別 run、別 attempt の Manager repo を拒否する。
5. renderer が credential を受け取ったのに Manager repo がない場合は fail-fast する。

### 完了条件

全 role が environment inheritance に依存せず、生成 prompt の command だけで ACK exchange と status recovery を実行できる。

## LB-02: TUI submit と Enter retry を分離する

### Message envelope

Manager message の先頭に短い transport fingerprint を持つ start marker を置き、末尾には transport fingerprint と payload fingerprint を持つ end marker を置く。完全な run、role、attempt、message ID は本文内の context 行に保持し、fingerprint の計算へ結び付ける。

```text
HERDR_LOOP_MESSAGE_START:<transport-fingerprint>
...
HERDR_LOOP_MESSAGE_END:<transport-fingerprint>:<payload-fingerprint>
```

Codex には start marker、body、end marker を順に分けて送り、三つを連結すると元の envelope と byte 単位で一致するようにする。start を確認してから body を一回だけ送り、end を送った後は `Ctrl+E` で長い入力の末尾を表示して end marker を確認する。各 control key の直前に pane metadata、pane text、pane metadata の順で読み、同じ non-empty provider、pane session、idle 状態と exact staged message が維持されていることを確認する。途中で判定不能になった場合は control key を送らず、body も自動再送しない。Claude と旧形式の message は既存の一括送信経路を維持する。

### Submit verification

既定 settle delay は live canary で再測定する。初期値は 2,000 ms とし、次の順で一回ずつ Enter を送る。

1. start marker、body、end marker を順に一回ずつ送り、`Ctrl+E` 後に end marker を確認する。
2. settle delay を待つ。
3. Enter を一回送る。
4. `agent_status=working`、assistant output、または exact `HERDR_LOOP_MESSAGE_ACK` を待つ。
5. Agent が idle のままで同じ message が staged されている場合だけ、もう一度 settle delay を置いて Enter を送る。

pane text が変わっただけでは submit 成功にしない。改行だけでも snapshot は変わるためである。`• Working` や `esc to interrupt`、ACK marker などの文字列は、canonical end marker より後のUI領域に現れた場合だけ証拠にする。Manager payload 内の例示文字列は証拠にしない。

### Durable transport stage

既存の delivery status を壊さず、Manager message record に次の補助情報を加える。

- `transport_stage`: `send-text-started|typed-confirmed|submit-confirmed|unknown`
- `pane_session_id`
- `enter_attempts`
- `start_marker`
- `end_marker`
- `end_marker_staged`
- `payload_digest`

`typed-confirmed` の本文は自動再送しない。submit を確認できなかった場合は `delivery_status=unknown` のままにし、body retry と Enter retry を区別できる証拠を残す。`end_marker_staged=true` のときだけ Enter-only recovery を案内し、false の場合は実際の結果を確認してから `message resolve` するよう案内する。

### Enter-only recovery

次の明示 command を追加する。

```text
hloop message submit <role-id> <message-id>
```

この command は `send-text` を実行しない。同じ pane session、attempt、message marker が入力待ちとして確認でき、Agent が working ではない場合にだけ Enter を一回送る。すでに assistant output または `HERDR_LOOP_MESSAGE_ACK` があれば追加 Enter を拒否し、message を acknowledged へ進める。

自動 `message drain` は引き続き `undelivered` の body だけを対象とし、実行中 role にだけ再送する。終了済み role は exact identity を確認した `message resolve ... --status superseded` で閉じる。drain 中に `unknown` へ遷移した場合は nonzero で停止し、`unknown` や `typed-confirmed` の body を再送しない。orphan/malformed pending marker も完了ゲートで blocking とする。

### Test-first cases

1. 長い multi-line message でも `Ctrl+E` 後に compact end marker を確認できる。
2. 最初の Enter が改行になり、二回目で working へ移る。body の送信 count は1、Enter count は2になる。
3. pane text の変化だけでは submit-confirmed にならない。
4. working、assistant output、exact message ACK の各証拠で submit-confirmed になる。
5. typed-confirmed 後に body を再送しない。
6. `message submit` は同じ session、attempt、message の場合だけ Enter を送る。
7. すでに submit 済み、別 session、別 attempt、superseded message では追加 Enter を拒否する。
8. busy pane は undelivered として保全し、idle 後の drain でも body を一回だけ送る。
9. contract-changing message の barrier は `send-text` より前に blocking となり、unknown、newline、retry のどの状態でも解除されない。

### 完了条件

通常経路では本文一回と最大二回の delayed Enter で Codex turn が始まる。自動判定できない場合も、Manager は本文を再送せず Enter-only recovery を一回ずつ実行できる。

## LQ-01: disposable live canary

unit test だけでは Enter timing と pane status を証明できないため、exact candidate SHA で実 Herdr/Codex TUI canary を一回実行する。

fixture は Manager state と Worker marker の参照先を分ける。

```text
assert_live_ack_state.py \
  --state-repo <manager-repo> \
  --marker-repo <worker-worktree> \
  ...
```

canary は一つの Worker と一つの contract-changing message だけを使い、次を時系列で保存する。

1. initial ACK awaiting、approved/pending、approved/applied の各状態で marker absent。
2. contract message の本文 send count が1。
3. Codex turn が自動 Enter で開始する。失敗時は Enter-only recovery が body resend なしで成功する。
4. old ACK が replacement barrier を解除しない。
5. replacement ACK awaiting、approved/pending、approved/applied の各状態で marker absent。
6. application 後だけ marker を作成する。
7. `worker submit`、candidate seal、finalize、harvest、merge が成功する。
8. merge 後の Manager checkout で original validation が成功する。

canary が一度失敗した場合は、同じ fixture を手作業で継ぎ足さない。pane、state、broker event、message record を保存し、原因を修正した fresh namespace で一回だけ再実行する。

## Review と修正 round

三 task の途中で broad review を繰り返さない。各 task は自己レビューと targeted tests を通し、pre-canary full validation と LQ-01 に合格した同じ統合 SHA に対して一度だけ review epoch を実行する。

review finding は次の三分類に限定する。

- 三件の修正による regression
- 保持する不変条件の欠落
- live canary を成立させない adjacent consumer

base-existing finding や 0.5.4 feature は同じ remediation batch に入れない。修正後は known finding closure と三件に対応する fresh regression challenge を同じ SHA で一回実行する。

## Rollback

- LB-01 は kind allowlist と追加 validation を一 commit に閉じる。rollback 後は candidate submit が fail-closed に戻る。
- LB-03 は prompt routing と parser を一 commit に閉じる。rollback 後も環境変数 fallback は残る。
- LB-02 は envelope、transport-stage、Enter-only CLI を一 commit に閉じる。state の追加 field は optional とし、旧 runtime が無視できる形にする。
- live canary は使い捨て namespace と worktreeだけで行い、製品 branch へ fixture artifact を混ぜない。

## 非目標

- Herdr server や Codex TUI 自体を作り直さない。
- arbitrary human conversation を broker-only transport に置き換えない。
- repository memory、Manager rotation、review convergence をこの修正へ混ぜない。
- 既存 review finding をゼロにするための scope 外実装を行わない。
- live fixture の validation path 問題を product runtime の変更理由にしない。
- Codex と Claude の installed copy は、三件の修正と exact-SHA canary が通る前に更新しない。
