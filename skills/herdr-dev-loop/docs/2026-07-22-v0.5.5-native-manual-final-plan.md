# herdr-dev-loop 0.5.5 native manual-final と companion 任意化計画

## 目的

0.5.5では、HLoopをinstallしてrelease gateを完了するための必須条件から`codex-review-multi-v2`を外す。ordinary review、pre-final、manual-finalの全execution kindにHLoop native protocolを用意し、新規loopはcompanionなしでもcomplete-zero certificationまで到達できるようにする。

これはreview品質を下げる変更ではない。固定target、lane completeness、Reviewer identity、独立verification、artifact digest、remediation convergence、verified actionable finding 0件という0.5.3の安全条件はnative実装にも同じ強さで適用する。外部companionは互換性と明示選択のために残すが、HLoop本体のpublicationをblockするrelease dependencyにはしない。

## 現状と解消する結合

0.5.3では、fresh loopのordinary review、pre-final、manual-finalが`codex-review-multi-v2`を既定値とする。native ordinary reviewとnative pre-finalは存在するが、manual-finalのschemaとconfigはexternal protocolだけを受理する。そのため、HLoop本体のコードが正常でも次の条件がreleaseと実行を止める。

- immutable companion distributionがrepository、Codex、Claudeの三者で一致しない
- `externally-planned-v1` capability manifestが欠落またはdriftする
- external adapterのsource、version、payload digestがrelease pinと一致しない
- manual-finalでnative protocolを選択できない

0.5.5の完了時には、nativeだけを選択したloopはこれらのcompanion条件を参照しない。external protocolを明示的に選んだexecutionだけが、従来どおりexact capability validationを要求する。

## 設計原則

**Protocol selection**はexecution kindごとに一つのcanonical keyから決める。ordinary reviewは`reviewer.protocol`、pre-finalは`review.pre_final_protocol`、manual-finalは`review.manual_final_protocol`を使い、別kindの設定へfallbackしない。

**Conditional dependency**はexternal protocolが選択された場合だけ成立する依存である。native executionではcompanionのinstall、manifest、distribution digestをgateに含めない。external executionではpin検証を省略せず、nativeへ黙ってfallbackしない。

**Certification parity**はnativeとexternalの双方が同じ完成条件を満たすことを意味する。protocol固有の起動方法は異なっても、PLAN、MANIFEST、fixed target、execution identity、lane result、verification、finding classification、complete-zero判定は共通のcanonical modelへ正規化する。

## 対象範囲

0.5.5に含める変更は次のとおりとする。

1. `manual_final_protocol = "native"`のconfig、state、schema、CLI対応
2. native manual-finalのPLAN/MANIFEST生成、record、status、finish gate対応
3. native Reviewerのcanonical six-lane topologyとexecution identityの固定
4. release dependencyを必須単一dependencyから条件付きexternal adapter catalogへ変更
5. 0.5.3と0.5.4の保存済みexternal policyを維持するmigration
6. native-only install、external opt-in install、両provider installの検証経路分離
7. exact-SHA synthetic E2Eとmigration rollback matrix

0.5.5ではreview lane削減、finding severity変更、automatic fix round上限変更、Agent budget拡大、外部protocolの削除は行わない。中央CLIのmodule分割と同時にbehaviorを変える場合は、抽出commitとfeature commitを分離する。

## 目標状態

新規0.5.5 loopの既定値は次の形を候補とし、実装前のconfiguration migration testで最終確定する。

```toml
[defaults.reviewer]
protocol = "native"
lane_count = 6

[defaults.review]
pre_final_protocol = "native"
manual_final_protocol = "native"
manual_final_execution = "independent"
```

external互換pathは明示選択で維持する。

```toml
[defaults.reviewer]
protocol = "codex-review-multi-v2"

[defaults.review]
pre_final_protocol = "codex-review-multi-v2"
manual_final_protocol = "codex-review-multi-v2"
```

一つでもexternalを選んだ場合、そのexecution作成時にだけpinned adapterを要求する。native ordinary reviewとexternal manual-finalのような混在も許可するが、それぞれのPLANに選択元canonical keyとprotocol identityを保存する。

## 実装slice

### 0.5.5-P1: protocol modelの分離

review policyから「manual-finalはexternalのみ」という制約を外し、execution kind、protocol、capability requirementを別フィールドとして表現する。`native`と`codex-review-multi-v2`の許可集合を一か所に集約し、config、state migration、CLI validation、schemaが同じ定義を参照する。

このsliceは挙動を変えず、0.5.3相当の保存済み設定を読み書きしたときのgolden outputを固定する。新しいnative値は後続sliceが完成するまでfeature flagまたはinternal guardの後ろに置く。

### 0.5.5-P2: native manual-final execution

native Reviewer CoordinatorがHLoopのPLANを直接受け取り、canonical six-lane topologyを実行する。Coordinator自身をlaneとして数えず、各laneは同じtarget SHA、scope snapshot、execution ID、lane IDへ固定する。required verificationがあるlaneは別identityのverification resultをMANIFESTへ記録する。

`final-review prepare`はnative選択時にprotocol capability引数を要求しない。`record`と`status`はnative manifestをcanonical certification modelへ正規化し、external pathと同じcompleteness、artifact drift、duplicate source、complete-zero gateを適用する。

### 0.5.5-P3: release dependencyの条件付き化

`release-dependencies.json`をHLoop publication全体の必須companion recordとして扱う設計を終了する。native-only distributionはHLoop単体でrelease-readyになり、required release evidenceはHLoopのCodex/Claude parityとfresh-session discoveryに限定する。

external adapter catalogは次の情報を保持する。

- protocol名
- immutable source identity
- exact adapter version
- payload digest algorithmとdigest
- capability manifest path
- required capabilities
- install destinations

外部protocolを選んだ実行はcatalog entryとruntime manifestの完全一致を要求する。catalog entryがない、distributionが未install、digestが異なる場合は、そのexternal executionだけをfail-closedで止める。native executionやHLoop本体のpublicationへ影響を伝播させない。

manifestの単独コピーをdistribution evidenceとして受理しない。execution作成時、role起動直前、artifact record時に、providerが実際にdiscoverするcompanion rootを再ハッシュし、検証済みrootの絶対path、payload digest、manifest identityをPLAN/MANIFESTへ固定する。Python bytecode cache、symlink、VCS metadataを実行treeで検出した場合もexternal executionだけを停止する。

### 0.5.5-P4: migrationと互換性

0.5.3または0.5.4の保存済みloopは、migration後も保存済みexternal protocolを維持する。新規既定値をnativeへ変えても、既存loopを暗黙にnativeへ切り替えない。companionなしで既存external loopを開いた場合は、必要なpinとinstall destinationを示して停止する。

externalからnativeへ変更する操作は、対象executionが未開始で、userまたはconfig migration policyによる明示変更があり、stateへprotocol amendmentを記録できる場合だけ許可する。開始済みepochやmanual-final PLANのprotocolを書き換えず、新しいsuccessorまたはcertification generationを作成する。

### 0.5.5-P5: install、文書、release gate

標準installはHLoop本体だけで成立させる。companion installはexternal protocolを使う利用者向けのopt-in手順へ移す。fresh-session handshakeはnative-onlyとexternal-opt-inを別scenarioとして記録し、native-only gateがcompanion discoveryを要求しないことをtestする。

0.5.3のpinとinstall runbookはhistorical release contractとして保持する。0.5.5の文書は、default変更、既存loopの互換性、external opt-in、rollbackを独立した節で説明する。

## 検証計画

unit testは少なくとも次のmatrixを持つ。

| ordinary | pre-final | manual-final | companion | 期待結果 |
| --- | --- | --- | --- | --- |
| native | native | native | なし | complete-zeroまで成功 |
| native | native | external | valid | manual-finalのみadapter検証後に成功 |
| external | native | native | valid | ordinaryのみadapter検証後に成功 |
| external | external | external | valid | 全external executionが同じpinへ固定 |
| native | native | external | なし | manual-final prepareだけ失敗 |
| external | native | native | digest drift | ordinary execution作成だけ失敗 |
| native | native | native | digest drift | companionを参照せず成功 |

schema testはnative/externalのconditional field、unknown field、protocol key drift、capabilityの過不足を確認する。migration testは0.5.3 external snapshot、0.5.4 snapshot、fresh 0.5.5、partial migration、resume、rollbackを対象にする。install matrixにはCodex/Claudeのskills rootが別parent、同一parent、同一canonical root、custom `CLAUDE_CONFIG_DIR`の各構成を含め、provider別backup namespaceとsame-root fail-closedを検証する。

synthetic E2Eはnative-onlyをrelease必須scenarioとし、external-allとmixed protocolを追加scenarioにする。どのscenarioもfixed target変更、lane欠落、verification欠落、duplicate source、artifact digest drift、actionable finding残存を成功へ読み替えない。

## 受入条件

0.5.5は次をすべて満たしたときに完了とする。

1. companionをrepositoryにもinstalled skill rootにも置かないclean環境で、HLoop selftestとnative-only synthetic E2Eが成功する。
2. native manual-finalがcanonical six-lane completion、required verification、fixed target、complete-zeroを証明する。
3. external protocolを明示選択した場合は、0.5.3と同等のsource、version、digest、capability validationが維持される。
4. external adapter failureがnative executionまたはHLoop publicationをblockしない。
5. 0.5.3と0.5.4の保存済みexternal policyがmigrationで暗黙変更されない。
6. CodexとClaudeのfresh sessionがHLoop単体をdiscoverし、native manual-final対応を報告できる。
7. companion opt-in install後は両providerが同じimmutable adapterをdiscoverする。
8. full unit suite、schema validation、formatter、exact-SHA synthetic suite、rollback matrixが成功する。
9. external PLAN/MANIFESTが検証済みcompanion rootを保持し、manifest単独コピーや実行可能cacheでpinを迂回できない。

## 主なriskと対策

最も大きいriskは、native pathだけcomplete-zero条件が弱くなることである。protocol固有実装から直接`finish`判定を行わず、両protocolを同じcanonical certification modelへ変換してから一つのgateで検査する。

次のriskは、新規default変更が既存loopへ混入することである。config resolutionはfresh defaultとsaved snapshotを区別し、migration testで既存external値のbyte-level golden recordを保持する。

もう一つのriskは、optional dependency化を「adapter検証の削除」と誤解することである。release dependencyを条件付きcatalogへ移しても、external executionではexact pinを必須のまま残す。missing companionからnativeへの自動fallbackは実装しない。

## rolloutとrollback

release candidateは最初にnative-only canaryを行い、その後external-all、mixed protocolの順で検証する。native-onlyでcompanion参照が一度でも観測された場合はrelease blockerとする。external canaryでpin検証が弱くなった場合もrelease blockerとする。

rollback時は0.5.5 runtimeを停止し、保存済みloopのschema revisionとfirst 0.5.5 mutation boundaryを確認する。mutation前なら0.5.4または0.5.3 runtimeと保存済みconfigへ戻す。mutation後は旧runtimeでstateを書き換えず、0.5.5のresumeまたはforward repairを使う。external adapter catalogとcompanion snapshotはHLoop本体とは別に復元できるようbackup identityを分離する。
