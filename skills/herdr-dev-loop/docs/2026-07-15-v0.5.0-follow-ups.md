## F001 同一UIDの信頼境界

- **重要度**：P1
- **関連状態**：`D001`はpending、`T047`は未起動
- **根拠**：attempt単位のcredential fileとartifact identity gateは、誤配送、古いattempt、異なるroleからのreportを拒否できる。一方、同じOSユーザーで動くAgentはcredential file、loop state、自己申告のprovenanceへ同じ権限でアクセスできる。T048が追加したLiaison provenanceも、悪意ある同一UID Agentを暗号学的に証明するものではない。
- **影響**：現行0.5.0は、同一UIDのAgentを非悪意的な協調主体として信頼する場合に限り、reportとdecision artifactの境界を保証する。同一UID Agent間の秘密分離やstate改変耐性は保証しない。
- **推奨対応**：0.5.0で同一UIDを信頼することを明示する、0.5.0をexperimentalとして0.6で隔離する、0.5.0の時点で別UID、sandbox、Manager専用control planeを導入する、という既存の三案から利用者が選ぶ。HLoopはこの判断を自動選択しない。
- **今回見送る理由**：利用者判断が未了であり、`U0001`がT047の起動と追加ハードニングを禁止したため。

## F002 Report配信のidempotency

- **重要度**：P1
- **関連状態**：`T050`は未起動
- **根拠**：brokerへの書込みが成功した後、CLIが成功応答を返す前にprocessが停止すると、呼出側が同じreportを再送する可能性がある。broker側のevent identityだけでは、別event IDとして再送された同一呼出しを識別できない。
- **影響**：同じ意味のreportとManager wakeが重複し、Managerが同一節目へ複数回対応する可能性がある。通常の後続reportまで重複扱いすると進捗を失うため、payload一致だけによる排除では足りない。
- **推奨対応**：呼出側がretry間で維持するinvocation IDまたはidempotency keyを導入し、brokerがそのkey単位で最初の受理結果を再利用する。通常の新しいreportは新しいkeyを持たせる。
- **今回見送る理由**：`U0001`がT050の起動を禁止し、T048と最終検証の収束を優先したため。

## F003 ACK承認前の書込み防止

- **重要度**：P1
- **根拠**：実セッションでは、Claude Workerがsemantic ACKの承認前にworktreeを編集した例があった。現在のruntimeは未承認attemptのfinalize、harvest、mergeを拒否できるが、Agent toolによる最初のfilesystem書込み自体はprompt遵守に依存する。
- **影響**：未承認の方針で作られた差分はintegrationへ入らないものの、role worktreeを汚し、修正、requeue、証跡確認を必要にする。ManagerがACKで理解違いを検出する前に作業が進むため、早期訂正の効果も弱くなる。
- **推奨対応**：ACK承認まではrole worktreeをread-onlyにし、承認時にwrite権限を切り替える仕組みを検討する。provider hookで実現する場合も、CodexとClaude Codeの双方で同じfail-closed条件を満たす必要がある。
- **今回見送る理由**：T048の受入条件を越えるruntime権限制御であり、`U0001`が新規taskと追加ハードニングを禁止したため。

## F004 統合HEADのrelease gate更新

- **重要度**：P1
- **根拠**：収束時の`hloop status`は、review、gap、validationのresume gateが現在の統合HEADと一致しないことを報告している。review queueとgap queueも閾値を超えているが、`U0001`はそれを新規role起動の理由にしないよう指定した。
- **影響**：ローカルの実装検証は成功しているが、0.5.0のrelease checklistが要求する最終review、gap確認、provider E2E、install parityは完了していない。したがって、現時点の状態をrelease完了またはHLoopの`finish`として扱えない。
- **推奨対応**：利用者がrelease作業を再開した時点のHEADを固定し、そのHEADに対して必要なreview、gap、provider E2E、install parityを一度ずつ取得する。古いartifactを現在HEADの証跡として再利用しない。
- **今回見送る理由**：新規Reviewer、Gap Auditor、Advisorの起動、push、installが`U0001`で禁止されたため。final gateはarmせず、loopをpauseした。

## F005 SQLite connectionのテスト警告

- **重要度**：P3
- **根拠**：収束時の369 unit testsは成功したが、`sqlite3.Connection`がcloseされていないことを示す`ResourceWarning`が1件出力された。
- **影響**：確認できた範囲ではテスト結果と製品動作に失敗はない。ただし、長時間processや反復テストで同じ経路が積み重なる場合、connectionとfile descriptorの解放が遅れる可能性がある。
- **推奨対応**：warningを発生させたtest fixtureまたはbroker storageの生成箇所を特定し、context managerか明示的な`close()`でライフサイクルを閉じる。修正後はwarningをerrorとして扱う対象テストを限定実行する。
- **今回見送る理由**：明白な0.5.0の機能回帰ではなく、T048のscope外だったため。

## 再開時の確認順序

再開時は、未解決項目を一括して実装へ戻さない。まず`D001`について利用者の選択を記録し、同一UIDを信頼する範囲を確定する。次にF002とF003を0.5.xで扱うか0.6へ送るかを決める。その判断後に対象HEADを固定し、F004のrelease gateを更新する。F005はreleaseを止める問題とは扱わず、独立した小さいcleanupとして実施できる。

pushとinstallを再開する場合は、repository、Codex install、Claude Code installのversion、selftest、quick validation、`diff -qr`を同じHEADで確認する。現在のpause状態や古いinstall結果を、再開後のrelease証跡として流用しない。0.5.1をreleaseするまでは、installed 0.5.0 snapshotを既存0.4.0 backupへ戻すか、repository内の明示pathだけを検証に使う。
