# herdr-dev-loop 0.5.3 closeout plan

Status: implementation proposal

## 目的

0.5.3 の残作業を、旧 run の不整合を持ち込まず、scope を増やさず、review と fix の直列往復を抑えて完了させる。

この計画は [recovery inventory](2026-07-19-v0.5.3-recovery-inventory.md) を入力とし、[acceptance matrix](2026-07-19-v0.5.3-closeout-acceptance-matrix.md) を完了判定に使う。

2026-07-20 の live Herdr/Codex TUI QA で、contract-changing message 後の candidate gate、TUI submit、canonical Manager repo routing に未解決の blocker が確認された。release gate へ進む前に [0.5.3 live behavior repair plan](2026-07-20-v0.5.3-live-behavior-repair-plan.md) の LB-01、LB-03、LB-02、LQ-01 をこの順で完了する。この addendum は三件以外の closeout scope を増やさない。

## 完了の定義

0.5.3 は、次をすべて満たすまで release しない。

1. 元計画の57受入条件が exact release SHA の evidence へ結び付いている。
2. R005、G053、T050 R002、T051 R003 の in-scope finding が resolved である。
3. task-lifetime Patch Review history、single-use extra-round authorization、semantic ACK history が requeue を跨いで残る。
4. ACK 承認取得が pane の Enter 配送に依存しない。
5. exact SHA の full suite、selftest、quick validation、21-scenario synthetic、migration crash matrix が成功する。
6. Reviewer swarm と Gap swarm が同じ exact SHA を監査し、必須 lane と challenge の artifact が完全である。
7. remediation 上限後に未解決 finding を隠さず、user decision へ停止する。
8. Codex と Claude の install parity と required companion handshake が release policy を満たす。

## 実行原則

### 旧 run を直接 resume しない

旧 namespace は 0.5.2 runtime で作られ、T050/T051 が `running` のまま pane を失っている。旧 role、credential、ACK application を復活させない。候補 code と artifact digest だけを recovery manifest 経由で新 run へ参照させる。

### bootstrap の control runtime と product baseline を分ける

bootstrap の制御には commit `043eb92` の immutable `hloop` を使い、product branch は T051 candidate `3bbdb54` から作る。T051 の7 finding は open のまま recovery manifest へ登録し、候補内 runtime を制御用に実行しない。

現行の `exec` runner は一回の provider process で終わる一方、role prompt は ACK 後の停止と Manager notice 待ちを要求する。したがって bootstrap は TUI の1 Workerだけを使う。現行 pane notice を使うのは ACK seed の一度だけとし、配送が不明なら再送せず停止する。

### finding を先に統合する

既知 finding は実装前に一つの remediation ledger へ集める。Worker が自分の task の review だけを見て局所修正しないよう、原因、影響 surface、preserved invariant、required regression を同じ contract に含める。

### review は exact SHA の epoch とする

同じ code 状態を複数回直列に review しない。Coordinator 内の lane と verifier は並行実行し、全 artifact が揃ってから一度だけ triage する。修正後は known-finding closure と fresh regression challenge を同時に行う。

### 上限で品質を落とさない

上限到達時に review を省略したり finding を deferred 扱いに変えたりしない。未解決 finding、候補 SHA、試した修正、残る選択肢を保存してユーザーへ相談する。

## Phase 0: freeze と recovery manifest

### 作業

1. 旧 namespace の phase が `paused` であることを確認する。
2. T050/T051 の branch、HEAD、tree、candidate artifact、Patch Review digest を検証する。
3. R005、G053、D005 から D008、A001、A002 の digest を固定する。
4. T050/T051 worktree の clean status を確認する。
5. `RECOVERY-MANIFEST.json` と人間向け `RECOVERY-MANIFEST.md` を作る。
6. successor 側 manifest に `evidence-only` と `do-not-resume-role-state` を記録する。旧 run 自体は変更しない。

### gate

- manifest の全 Git object と artifact digest が再検証できる。
- product code は変更されていない。
- 旧 run の task、review、decision history が削除されていない。

## Phase 1: one-task bootstrap

### Task SB01: broker-native ACK seed

[ACK transport fast fix](2026-07-19-ack-transport-fast-fix.md) の最小部分だけを実装する。

- ACK report と承認待ちを一つの blocking command で実行する。
- Manager resolve は broker/STATE を commit した時点で成功する。
- role の待機 command は exact run、role、attempt、message、contract digest、ACK event ID を照合し、pane message なしで返る。
- reject、timeout、supersede は material work を開始させない。
- approval notification の TUI 送信は既定で行わない。

bootstrap namespace には SB01 以外の code task を作らない。Patch Review history、metrics、review epoch、Gap、remediation、recovery guard は successor namespace で扱う。

### bootstrap validation

- ACK exchange の subprocess integration test
- busy pane でも Manager resolve が成功する test
- pane API を呼ばず role が approval を取得する negative/positive test
- full test discovery

SB01 の exact SHA から fresh canary namespace を作り直す。bootstrap namespace の継続使用はしない。

## Phase 2: successor guard と candidate union

### Checkpoint C000: fresh successor initialization

SB01 合格 SHA の runtime で fresh namespace を init する。bootstrap STATE、credential、role attempt は migrate しない。T051 baseline の source evidence と7 finding は recovery manifest から引き継ぐ。

### Task PG01: pre-mutation recovery guard

- runtime identity と deterministic brief
- runtime digest drift の mutation refusal
- active write-scope conflict と missing pane の dispatch refusal
- start 後 contract mutation の refusal
- 同じ transport/lifecycle failure の2回目での circuit break

repository memory、repository UUID、中央 CLI 分割は0.5.4へ送り、PG01に含めない。

### Task RI01: T050 candidate union and source identity

T050 branch `98cd118` を取り込み、`run_synthetic_e2e.py` の content conflict を union として解決する。同じ write surface にある T050 R002 finding `a0cf5844` も閉じる。

解決時に release feature を追加しない。T050/T051 の双方が要求する scenario と identity binding を失わず、test-only companion と production dependency を区別する。

### gate

- recovery integration の diff が、T050 と T051 の union と source identity fix 以外を失っていない。
- production dependency は `release_ready: false` のままである。
- full discovery が起動できる。失敗しても既知 finding と新しい merge regression を区別できる。

## Phase 3: known finding と残機能の closure

作業は中央 `hloop` の競合が大きいため、最大1 Workerずつ直列にする。review と Gap はまだ開始しない。

### Task SC01: Scout cleanup durability

対象:

- T051 finding 1
- coverage Scout の旧 attempt 保全

preserved invariant:

- decision-mode Scout の既存 lifecycle を壊さない。
- cleanup failure は replacement start を跨いで finish を遮断する。

### Task ID01: legacy/canonical schema parity

対象:

- T051 finding 2、3
- review epoch legacy/canonical schema parity
- final review plan/manifest legacy/canonical schema parity

preserved invariant:

- canonical record の strict validation を弱めない。
- complete legacy または complete canonical のどちらかだけを許し、one-sided record を拒否する。

### Task DA01: authorization decision and input binding

対象:

- T051 finding 4、5
- exact user input binding

preserved invariant:

- blocking decision の authorizing option だけが追加 round を開く。
- stop option、advisory decision、別 input、別 task、別 fingerprint を拒否する。

### Task LH01: task-lifetime history and metrics

対象:

- T051 finding 6、7
- task-lifetime Patch Review cap
- one-time extra-round authorization
- finalize/harvest revalidation
- pause、supersede、requeue を含む outcome metrics

preserved invariant:

- 通常上限は task 単位で2回、追加許可は1回だけとする。
- requeue は履歴と consume record を消さない。
- terminal timestamp 後に duration を増やさない。

### Task GP01: Gap swarm artifact and harvest

旧 T052 を新 base で再生成する。

- PLAN、lane result、coverage challenge、MANIFEST、FINAL を group artifact として保存する。
- completed process IDs と実 artifact digest を照合する。
- self-declared outcome だけでは barrier を通さない。

### Task EP01: review epoch lifecycle recovery

旧 T053 を新 base で再生成する。

- same-SHA lineage capacity
- failed/timeout/incomplete successor

### Task RM01: unified remediation transaction

- unrelated base-existing finding を task materialization から除外する。
- task artifact と parent directory の fsync 後に dispatched STATE を保存する。

### Task GT01: collision-free Git metadata probe

旧 T055 の Git probe 部分を新 base で再生成する。

- collision-free Git metadata probe

### Task IF01: role locality and independent final

各 task の依存、write surface、除外範囲、test matrix は [recovery task graph](2026-07-19-v0.5.3-recovery-task-graph.md) を正本とする。

## Phase 4: pre-review integration validation

同じ exact integration SHA で次を一度ずつ実行し、evidence catalog へ保存する。

1. changed-file targeted suites
2. full `unittest discover`
3. `hloop selftest`
4. skill quick validation
5. schema reference/public-wrapper parity
6. exact-SHA 21-scenario synthetic
7. migration prepared/rename/committed/rollback/corruption matrix
8. Git concurrency and fault-injection tests
9. `git diff --check`

失敗した validation を Reviewer に探させない。既知の test failure は review 開始前に一つの integration-fix task へまとめる。

## Phase 5: one broad discovery epoch

[Review convergence protocol](2026-07-19-review-convergence-protocol.md) に従う。

- Reviewer swarm と Gap swarm を同じ exact SHA で並行実行する。
- Reviewer は6 discovery lane と independent verifier を使う。
- Gap は4 acceptance lane、coverage challenge、independent verifier を使う。
- Coordinator は同じ agent を lane と verifier の両方に使わない。
- すべての lane が終わるまで fix を始めない。
- semantic fingerprint だけで重複を判断せず、failure class と affected invariant で統合する。

## Phase 6: bounded remediation

final discovery の finding を一度に triage し、原因別 batch にする。

### round 1

- confirmed
- in-scope
- fix-now
- release-blocking

の全 finding を一つまたは依存関係のある少数 task へまとめる。修正後に known-finding closure と mandatory regression challenge を同じ SHA で行う。

### round 2

round 1 の修正で新しく生じた in-scope regression だけを対象にする。元から存在する unrelated finding は follow-up に残し、自動 task 化しない。

### 上限後

新しい blocking finding が残る場合は release しない。次を保存してユーザーへ相談する。

- exact candidate SHA
- 未解決 finding と failure class
- round 1/2 の修正と test evidence
- rollback、追加 round、feature disable の選択肢
- 各選択肢の品質と時間への影響

requeue、task rename、successor task 作成で上限をリセットしない。

## Phase 7: release closeout

1. final integration SHA を固定する。
2. stale でない full validation evidence を再利用し、不足分だけ実行する。
3. independent manual final を fresh execution identity で実行する。
4. Codex/Claude install parity を確認する。
5. required companion の immutable distribution、version、digest、capability handshake を確認する。
6. 57受入条件を acceptance matrix で complete にする。
7. release notes、validation policy、migration guide を exact SHA に合わせる。
8. old run を successor namespace への handoff として terminalize する。
9. worktree、pane、session、credential、broker lease を cleanup する。
10. `hloop finish` の全 gate を通す。

## task 粒度の再評価

各 task 開始前に次を確認する。

- 変更する invariant は一つか。
- write surface が前後 task と重なりすぎていないか。
- targeted test と final regression を task contract に書けるか。
- 既知 finding を別 task へ押し出していないか。
- task を分けることで ACK、seal、Patch Review だけが増えていないか。
- task をまとめることで中央 CLI の複数 lifecycle を一度に変えていないか。

二つ以上の lifecycle を変える場合は分割する。単一の根本原因を複数 file で直す場合はまとめる。

## 推奨 role 設定

復旧中の code-touching task は高リスクとして扱う。

| role | provider/model | effort | 補足 |
| --- | --- | --- | --- |
| Worker | Codex `gpt-5.6-sol` | `xhigh` | 中央 runtime と migration を扱うため |
| Patch Reviewer | Codex `gpt-5.6-sol` | `xhigh` | task-local exact candidate |
| Reviewer Coordinator/lane/verifier | Codex `gpt-5.6-sol` | `xhigh` | planned identity と attestation 必須 |
| Gap Coordinator/lane/verifier | Codex `gpt-5.6-sol` | `xhigh` | acceptance ledger と独立 challenge |
| Advisor | Codex `gpt-5.6-luna` | `max` | decision support のみ。実装や gate 代替は禁止 |

この role 設定は recovery run に固定する。repository 外の global config を追加変更する場合は、別の user decision を必要とする。

## stop conditions

次のいずれかで自動進行を止める。

- runtime digest または run skill version が変わった。
- recovery manifest の source SHA/digest と実体が一致しない。
- active task の write scope conflict がある。
- start 後に contract を変える必要が出た。
- 同じ transport/lifecycle failure が2回発生した。
- Patch Review または remediation の task-lifetime 上限へ達した。
- user decision が必要な production companion identity がない。
- exact-SHA full suite が失敗する。
- Reviewer/Gap artifact の lane、verifier、challenge が欠ける。
- scope 外 finding を fix task に入れようとしている。

停止は失敗ではない。candidate と evidence を壊さず、ユーザーへ選択肢を返すための正常な状態である。
