# herdr-dev-loop 0.5.1 release hardening計画

- 作成日：2026-07-16
- 対象：herdr-dev-loop 0.5.1
- 基準ブランチ：`feat/herdr-dev-loop-v0.5.0`
- 基準HEAD：`034a1e4`
- release先：`master`
- 状態：実装前

## 目的

現行0.5.0を`master`へ統合し、0.5.1では既知のrelease riskだけを修正して、repository版、Codex版、Claude Code版を同じ固定SHAから安全に配布する。

0.5.1はreview運用全体を作り直すversionではない。有界review convergence、first-class follow-up、dispatch freezeの改善は0.5.2で扱う。0.5.1では、同一UIDの信頼境界、report配信のidempotency、release evidenceの欠落を閉じる。

## 現在の状態

repositoryの既定ブランチ名は`main`ではなく`master`である。`master`の`ff7d95f`は0.5.0ブランチのancestorなので、現時点では`--ff-only`で統合できる。

0.5.0ブランチの製品code最終HEADは`1dc0507`であり、follow-up文書を加えた現在HEADは`034a1e4`である。`1dc0507`では369 unit tests、synthetic E2E 9件、selftest、skill validator、Manager QAが成功した。`034a1e4`との差分はfollow-up文書だけである。

ただし、0.5.0 loopは次の理由からrelease完了ではない。

- loopは`paused`であり、`T047`と`T050`がqueuedのまま残っている。
- `D001`の同一UID trust boundaryが未決である。
- review、gap、validation、final gateは現在のGit HEADに対してstaleである。
- CodexとClaude Codeのinstalled copyは0.5.0を報告するが、repository版と多数の差分がある。
- installed copyは0.5.0実装途中のsnapshotであり、現在の0.5.0 release candidateとして扱えない。

0.4.0のbackupはCodexとClaude Codeの両方に残っている。0.5.1を配布するまで、installed 0.5.0を利用可能なreleaseとして扱わない。

## version境界

| version | 役割 | 配布方針 |
|---|---|---|
| 0.5.0 | 大規模実装を`master`へ着地させるintegration baseline | tag、install同期、stable releaseを行わない |
| 0.5.1 | 既知riskの修正とrelease evidenceの取得 | repository、Codex、Claude Codeへ配布する |
| 0.5.2 | review収束、scope制御、first-class follow-up | 0.5.1 release後に独立実装する |

0.5.0を`master`へ統合してから0.5.1を短期間で完成させる。0.5.0が`master`に存在する期間はrelease準備中として扱い、installed copyへ同期しない。

## follow-upの分類

### F001 同一UIDの信頼境界

- **分類**：0.5.1必須、release blocker
- **関連状態**：`D001`、`T047`
- **判断**：0.5.1では、同じOSユーザーで動くAgentを信頼済みの協調主体として扱う案を推奨する。
- **必要な処置**：credentialの保証を、誤配送、stale attempt、role identityの取り違え防止に限定する。同一UID Agent間の秘密分離、悪意あるstate改変耐性、暗号学的なManager認証を保証しないとREADME、report protocol、release noteへ明記する。
- **runtime側の処置**：subordinate role contextからManager consumer commandを誤って実行した場合は拒否し、監査記録を残す。ただし、この拒否を悪意ある同一UID processに対するsecurity boundaryとは説明しない。
- **完了条件**：利用者が`D001`の推奨案を承認し、文書、CLI guard、negative testが同じthreat modelを表す。

別UID、動的sandbox切替、Manager専用control planeを0.5.1へ入れない。これらは0.5.1の範囲と互換性を大きく変える。

### F002 Report配信のidempotency

- **分類**：0.5.1必須、release blocker
- **関連状態**：`T050`
- **判断**：broker commitとrole-local confirmed保存が成功した後、CLI成功応答前にprocessが停止する窓を閉じる。
- **必要な処置**：callerがretry間で維持するinvocation IDまたはidempotency keyをreport contractへ追加し、brokerとoutboxが最初に受理したevent IDと結果を再利用する。
- **区別する挙動**：crash retryは同じkeyを使い、正常終了後に送る同内容の別reportは新しいkeyを使う。payload一致だけで両者を推測しない。
- **完了条件**：broker commit後、confirmed保存後、CLI return直前の各crash testで、event、inbox、wakeが一件だけになる。異なるkeyを持つ同内容reportは別eventとして残る。

ACK、attention、completionはManagerの判断やtask状態へ影響する。狭いcrash windowでも、異なるevent IDで同じ論理reportが再登録される状態をstable releaseへ残さない。

### F003 ACK承認前の書込み防止

- **分類**：0.5.1対象外、後続のprovider isolation
- **release判定**：non-blocking。ただし既知制約として明記する。
- **理由**：現在のruntimeは未承認attemptのfinalize、harvest、mergeを拒否するため、未承認差分はintegrationへ入らない。残る影響はrole worktreeの汚染と手戻りである。
- **後続**：ACK承認前のread-only起動と承認後のwrite権限切替を、CodexとClaude Codeで同じfail-closed条件にできるかを別計画で検証する。0.5.2のreview収束計画へ混ぜず、provider isolationを扱うversionへ送る。

0.5.1のREADMEには、semantic ACKがintegration gateであり、最初のfilesystem writeをOS権限で防ぐ仕組みではないと記載する。

### F004 統合HEADのrelease gate更新

- **分類**：0.5.1のManager-owned release gate
- **release判定**：全証跡が同じ固定SHAへ揃うまでblocking
- **必要な証跡**：unit、synthetic E2E、Codex provider E2E、Claude provider E2E、Gap Audit、手動`codex-review-multi-v2`、selftest、skill validator、install parity、fresh-session discovery
- **禁止事項**：0.5.0 loopの古いreview、gap、install結果を0.5.1のpassとして再利用しない。

### F005 SQLite connectionの警告

- **分類**：0.5.1で処理するsmall cleanup
- **release判定**：full suiteで再現するため、修正と回帰testが完了するまでblocking
- **再現結果**：2026-07-16時点でbrokerのtargeted test 25件は`ResourceWarning`をerrorへ昇格して成功したが、369件のfull suiteでは`sqlite3.Connection`の未close warningが一件再現した。単一testではなくtest間のlifecycleまたは遅延finalizeを調べる必要がある。
- **理由**：単独ではrelease blockerではないが、brokerのidempotency testと同じ範囲で処理できる。長時間processを扱うreleaseで、既知のconnection lifecycle警告を残す利益がない。
- **完了条件**：明示的な`gc.collect()`を含む回帰testでwarningを決定的に検出し、full suiteのstderrに`ResourceWarning`とdatabase finalizer warningが存在せず、connectionまたはfixtureの所有関係が明示される。

## 0.5.0 baselineの統合

0.5.0の旧namespaceは再開しない。`T047`と`T050`を完了扱いにせず、0.5.1の新しいtask contractへ移す。旧namespaceはpause状態の証跡として保存する。

統合前に次を行う。

1. 既存の有界review収束計画の対象versionを0.5.2へ変更する。
2. 本計画を0.5.0ブランチへcommitする。
3. 0.5.0 code HEAD以降が文書変更だけであることを確認する。
4. `git diff --check`、selftest、skill validatorを実行する。
5. `origin/master`を取得し、local `master`と一致すること、`master`が0.5.0 HEADのancestorであることを再確認する。

確認後、0.5.0ブランチをoriginへbackup pushし、`master`へ`--ff-only`で統合してpushする。この時点ではversion tagを作らず、installed copyへ同期しない。このrepositoryには現在version tag運用がないため、0.5.1でも新しいtag方式を同時導入しない。

## installed copyのcontainment

0.5.1 releaseまで、現在のinstalled 0.5.0 snapshotを通常利用しない。0.5.0を`master`へ統合する前に、次のどちらかを実施する。

1. 推奨：CodexとClaude Codeのinstalled copyを既存の0.4.0 backupへ戻し、version、selftest、discoveryを確認する。
2. repo版0.5.0を検証目的で使う場合：installed copyではなく、repository内の`skills/herdr-dev-loop/scripts/hloop`を絶対pathで実行する。

0.5.1 release前にrepository版0.5.0をinstalled copyへ同期する案は採用しない。F001とF002を修正していないruntimeを、完成版として見える場所へ再配布することになるためである。

## 0.5.1 implementation branch

`master`への0.5.0統合後、`fix/herdr-dev-loop-v0.5.1`とnamespace`herdr-dev-loop-v0-5-1`を新規作成する。旧0.5.0 namespaceのqueued taskを直接dispatchしない。

新loopのMISSIONは次に限定する。

- 同一UIDの信頼境界を決定し、文書とaccidental misuse guardを一致させる。
- report deliveryへcaller-stable idempotency identityを追加する。
- SQLite warningを解消またはwarning-as-errorで非再現と証明する。
- version、release note、validation、review、provider E2E、install parityを0.5.1 SHAへ揃える。

新しいrole、別UID isolation、汎用capability framework、review scheduler変更、first-class follow-upはnon-goalとする。

## 実装task

### T501 Trust boundaryとManager consumer guard

`D001`の利用者回答を記録してから開始する。推奨案が承認された場合、同一UIDを一つのtrust boundaryとして定義する。

変更範囲は次へ限定する。

- README、SKILL、report protocol、decision policy、0.5.1 release note
- Manager consumer commandのrole-context preflightとaudit
- stale attempt、wrong role、subordinate contextのnegative test

このtaskは強いAgent間隔離を実装しない。mode 0600を「同じOSユーザーから読めない」と説明せず、「他のOSユーザーと意図しない公開から守る」と説明する。

### T502 Report invocation idempotencyとSQLite cleanup

T501の後に実行する。両taskは`hloop`とreport protocolへ触れるため、並列実行しない。

変更範囲は次へ限定する。

- report CLIのcaller-stable invocation IDまたはidempotency key
- role-local outboxとbrokerのkey conflict、retention、retry contract
- promptとreport protocolのretry手順
- broker commit後、confirmed保存後、CLI return前のfault-injection test
- warningを出すSQLite connectionまたはtest fixtureのclose
- `gc.collect()`とwarning captureによるdeterministicなconnection leak regression

既存のpending、confirmed、fallback spool、explicit event ID conflict、directory fsync、同内容別reportの保証を維持する。

### T503 Versionとrelease artifact

code変更が収束した後、Manager-owned integration taskとして実施する。

- `VERSION`、README、migration/install文書を0.5.1へ更新する。
- `docs/RELEASE-0.5.1.md`へthreat model、既知制約、validation command、rollbackを記載する。
- `docs/2026-07-15-v0.5.0-follow-ups.md`の各項目へ0.5.1での処置または後続versionを追記する。
- release evidenceの保存先をnamespaced local-only artifactへ固定する。

T503後は、review findingの修正以外でrepository HEADを変更しない。

## 実行時間とreview cadence

planned taskはT501からT503の三件だけとする。T501とT502は中核fileが重なるため順次実行し、T503はcode収束後に行う。

| 区間 | 目安 | 上限 |
|---|---:|---:|
| containmentと0.5.0 merge | 30分 | 60分 |
| T501 | 45分 | 90分 |
| T502 | 90分 | 180分 |
| T503 | 30分 | 60分 |
| validation、review、provider、install | 90分 | 180分 |
| 合計 | 4時間前後 | 8時間 |

mergeごとにfull Reviewerを起動しない。各Workerはtargeted testとself-reviewを行い、T501からT503の統合後にfull validation、Gap Audit、手動`codex-review-multi-v2`を一回ずつ実行する。

reviewから自動生成できるremediation batchは一回だけとする。current diffが導入した不具合、0.5.1 acceptance違反、到達可能なsecurityまたはdata lossだけを修正対象にする。それ以外は0.5.1 follow-upへ記録する。一回のremediation後もrelease blockerが残る場合は自動継続せず、releaseを停止して利用者へ報告する。

## validation gate

すべてのcommandを同じ固定SHAで実行する。

### repository validation

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m py_compile \
  skills/herdr-dev-loop/scripts/hloop \
  skills/herdr-dev-loop/tests/run_synthetic_e2e.py \
  skills/herdr-dev-loop/tests/run_provider_e2e.py
WARNING_LOG="$(mktemp)"
set -o pipefail
PYTHONDONTWRITEBYTECODE=1 PYTHONWARNINGS='always::ResourceWarning' \
  python3 -m unittest discover -s skills/herdr-dev-loop/tests -v \
  2>&1 | tee "$WARNING_LOG"
! rg -n 'ResourceWarning|Exception ignored while finalizing database connection' \
  "$WARNING_LOG"
rm -f "$WARNING_LOG"
python3 skills/herdr-dev-loop/scripts/hloop selftest
QUICK_VALIDATE="$(find "${CODEX_HOME:-$HOME/.codex}" "$HOME/.claude" \
  -iname quick_validate.py 2>/dev/null | head -n1)"
test -n "$QUICK_VALIDATE"
python3 "$QUICK_VALIDATE" skills/herdr-dev-loop
python3 skills/herdr-dev-loop/tests/run_synthetic_e2e.py --json
git diff --check master...HEAD
```

`PYTHONWARNINGS=error`だけでは、SQLite finalizer内の例外が`Exception ignored`となり、test processが0で終了する場合がある。このため、deterministicなunit regressionに加えて、release時はfull suiteのstderrも検査する。

### provider validation

CodexとClaude Codeのlive provider E2Eを同一SHAで実行する。`--allow-skip`は診断には使えるが、0.5.1 release passには使わない。各runはprovider、model、開始時刻、終了時刻、result JSONを保存する。

### specとcodeの整合性

Gap Auditorは0.5.0 plan、0.5.1 plan、release note、follow-up dispositionを現在SHAのcodeと照合する。0.5.1 acceptanceを満たさないgapが一件でもあればreleaseを止める。0.5.2のscope制御機能が未実装であること自体はgapにしない。

### 手動最終review

freshなCoordinator contextで`codex-review-multi-v2`を実行し、baseを0.5.0 baseline、HEADを0.5.1 candidateへ固定する。通常4 laneとし、次をfocusへ含める。

- same-UID threat modelとManager consumer guardの整合性
- report retry、idempotency key、outbox、broker、wakeのfault boundary
- SQLite lifecycleとresource cleanup
- migration、version、rollback、install parity

verified actionable finding 0件だけをpassとする。pre-existingまたは0.5.1 scope外の改善は根拠付きfollow-upへ送る。

## installとrelease gate

repository reviewを通過した0.5.1 candidateを`master`へ`--ff-only`で統合してpushし、その`master` SHAからinstalled copyを作る。

1. 0.5.1 candidate SHAと`master`へ統合後のSHAが一致することを確認する。
2. 現在のCodex版とClaude Code版をtimestamp付きでbackupする。
3. `master`のrepository版を両installed directoryへ`rsync -a --delete`で同期する。
4. repository、Codex、Claude Codeの`diff -qr`が0件であることを確認する。
5. 三copyの`hloop version --json`が0.5.1を報告することを確認する。
6. 両installed copyでselftestを実行する。
7. freshなCodex sessionとClaude Code sessionでskill discoveryと0.5.1 bannerを確認する。
8. 失敗時はinstalled copyを0.5.1直前のbackupまたは既存0.4.0 backupへ戻し、versionとselftestを再確認する。`master`はrelease失敗として扱い、原因修正用branchを切る。

## release判定

次をすべて満たした場合だけ0.5.1をrelease済みとする。

- `D001`が利用者回答付きでresolvedである。
- T501、T502、T503だけが実行され、未説明のscope追加がない。
- F002の三crash pointとsame-content/new-key testが成功する。
- F003の制約と後続先がREADMEとfollow-upへ記録されている。
- F005がwarning-as-errorで成功する。
- repository validation、Gap Audit、manual reviewが固定SHAでpassedである。
- manual reviewのverified actionable findingが0件である。
- CodexとClaude Codeのlive provider E2Eがpassedである。
- repository、Codex、Claude Codeのversion、selftest、byte parity、fresh discoveryが揃う。
- rollback backupと復元手順が確認できる。
- release後の`master` SHAとinstalled source SHAが一致する。

## 0.5.2への引継ぎ

0.5.1から0.5.2へ送るのは、有界review convergence、release scope lock、dispatch freeze、first-class follow-up、Manager observabilityである。0.5.1のrelease reviewで見つかった妥当な改善も、0.5.1 acceptanceと現在diffに関係しない場合は同じfollow-up ledgerへ追加する。

ACK承認前のOSレベルread-only化はprovider isolationの課題として別IDを持たせる。0.5.2のscope制御実装へ便乗させない。
