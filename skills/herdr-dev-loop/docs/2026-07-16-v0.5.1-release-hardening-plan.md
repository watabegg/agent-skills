# herdr-dev-loop 0.5.1 release hardening計画

- 作成日：2026-07-16
- 対象：herdr-dev-loop 0.5.1
- 基準ブランチ：`master`
- 基準HEAD：`631b360`
- 実装ブランチ：`fix/herdr-dev-loop-v0.5.1`
- T503 worktreeブランチ：`ai/v0.5.1-t503-release`
- release先：`master`
- 状態：0.5.0 integration、T501、T502、T503完了。candidate gate未完了

## 目的

0.5.0を`master`へ統合した`631b360`を基準とし、0.5.1では既知のrelease riskだけを修正して、repository版、Codex版、Claude Code版を同じ固定SHAから安全に配布する。

0.5.1はreview運用全体を作り直すversionではない。有界review convergence、first-class follow-up、dispatch freezeの改善は0.5.2で扱う。0.5.1では、同一UIDの信頼境界、report配信のidempotency、release evidenceの欠落を閉じる。

## 現在の状態

repositoryの既定ブランチ名は`main`ではなく`master`である。0.5.0 integrationは完了し、localと`origin/master`は`631b360`で一致している。このSHAを0.5.1のrelease baselineとする。

T501は`96aec39`でManager consumer誤用guardと同一UIDのcooperative threat modelを実装した。T502は`9169464`でcaller-stable invocation idempotency、outboxの64件保持上限、SQLite接続初期化失敗時のcloseを実装した。T503は、このworktreeでversionとrelease artifactを更新し、quick validation、repository selftest、working treeの`git diff --check`を完了した。

0.5.0 loopのpaused state、review、gap、install結果は、0.5.1 candidateのpassとして再利用しない。0.5.1のcandidate SHAはT503の変更をcommitした後に固定し、repository validation、review、provider、installの証跡をそのSHAへ揃える。T503のcommitとrelease gate実行は本Workerの範囲外である。

## follow-upの分類

### F001 同一UIDの信頼境界

- **分類**：0.5.1必須、release blocker
- **実装状態**：T501、`96aec39`で完了
- **関連状態**：`D001`、`T047`
- **判断**：利用者が`D001`の推奨案を承認した。0.5.1では、同じOSユーザーで動くAgentを信頼済みの協調主体として扱う。
- **必要な処置**：credentialの保証を、誤配送、stale attempt、role identityの取り違え防止に限定する。同一UID Agent間の秘密分離、悪意あるstate改変耐性、暗号学的なManager認証を保証しないとREADME、SKILL、report protocol、decision policyへ明記する。
- **runtime側の処置**：subordinate role contextからManager consumer commandを誤って実行した場合は拒否し、監査記録を残す。ただし、この拒否を悪意ある同一UID processに対するsecurity boundaryとは説明しない。
- **完了条件**：文書、CLI guard、negative testが承認済みの同じthreat modelを表す。

別UID、動的sandbox切替、Manager専用control planeを0.5.1へ入れない。これらは0.5.1の範囲と互換性を大きく変える。

### F002 Report配信のidempotency

- **分類**：0.5.1必須、release blocker
- **実装状態**：T502、`9169464`で完了
- **関連状態**：`T050`
- **判断**：broker commitとrole-local confirmed保存が成功した後、CLI成功応答前にprocessが停止する窓を閉じる。
- **必要な処置**：callerがretry間で維持するinvocation IDまたはidempotency keyをreport contractへ追加し、brokerとoutboxが最初に受理したevent IDと結果を再利用する。
- **区別する挙動**：crash retryは同じkeyを使い、正常終了後に送る同内容の別reportは新しいkeyを使う。payload一致だけで両者を推測しない。
- **完了条件**：broker commit後、confirmed保存後、CLI return直前の各crash testで、event、inbox、wakeが一件だけになる。異なるkeyを持つ同内容reportは別eventとして残る。

ACK、attention、completionはManagerの判断やtask状態へ影響する。狭いcrash windowでも、異なるevent IDで同じ論理reportが再登録される状態をstable releaseへ残さない。

### F003 ACK承認前の書込み防止

- **分類**：0.5.1対象外、後続のprovider isolation
- **実装状態**：deferred。0.5.2のreview scope controlとは別の後続計画で扱う
- **release判定**：non-blocking。ただし既知制約として明記する。
- **理由**：現在のruntimeは未承認attemptのfinalize、harvest、mergeを拒否するため、未承認差分はintegrationへ入らない。残る影響はrole worktreeの汚染と手戻りである。
- **後続**：ACK承認前のread-only起動と承認後のwrite権限切替を、CodexとClaude Codeで同じfail-closed条件にできるかを別計画で検証する。0.5.2のreview収束計画へ混ぜず、provider isolationを扱うversionへ送る。

0.5.1のREADMEには、semantic ACKがintegration gateであり、最初のfilesystem writeをOS権限で防ぐ仕組みではないと記載する。

### F004 統合HEADのrelease gate更新

- **分類**：0.5.1のManager-owned release gate
- **実装状態**：candidate gate完了後に確定
- **release判定**：全証跡が同じ固定SHAへ揃うまでblocking
- **必要な証跡**：unit、synthetic E2E、Codex live availability/read-only marker probe、Gap Audit、手動`codex-review-multi-v2`、selftest、skill validator、repositoryと両installed copyの静的parity、fresh Codex discovery
- **禁止事項**：0.5.0 loopの古いreview、gap、install結果を0.5.1のpassとして再利用しない。

利用者指示により、今回はCodexのlive availability/read-only marker probeだけを実施する。これはCodex CLIの起動と固定marker応答を確認するprobeであり、HLoop role起動、Herdr連携、rendered prompt、`agent report`経路のlive E2Eではない。Claude live provider E2Eとfresh Claude discoveryは未実施として記録し、成功を主張しない。一般的なClaude対応とClaude installed copyの静的parityおよびPython selftestは別の確認項目として維持する。

### F005 SQLite connectionの警告

- **分類**：0.5.1で処理するsmall cleanup
- **実装状態**：T502、`9169464`で完了
- **release判定**：full suiteで再現するため、修正と回帰testが完了するまでblocking
- **再現結果**：2026-07-16時点でbrokerのtargeted test 25件は`ResourceWarning`をerrorへ昇格して成功したが、369件のfull suiteでは`sqlite3.Connection`の未close warningが一件再現した。単一testではなくtest間のlifecycleまたは遅延finalizeを調べる必要がある。
- **理由**：単独ではrelease blockerではないが、brokerのidempotency testと同じ範囲で処理できる。長時間processを扱うreleaseで、既知のconnection lifecycle警告を残す利益がない。
- **完了条件**：明示的な`gc.collect()`を含む回帰testでwarningを決定的に検出し、full suiteのstderrに`ResourceWarning`とdatabase finalizer warningが存在せず、connectionまたはfixtureの所有関係が明示される。

## validation gate

すべてのcommandを同じ固定SHAで実行する。

### repository validation

```bash
set -euo pipefail
: "${EXPECTED_BASE_SHA:?set the externally reviewed full baseline SHA}"
: "${EXPECTED_CANDIDATE_SHA:?set the externally reviewed full candidate SHA}"
case "$EXPECTED_BASE_SHA" in
  *[!0-9a-f]*|'') exit 2 ;;
esac
case "$EXPECTED_CANDIDATE_SHA" in
  *[!0-9a-f]*|'') exit 2 ;;
esac
test "${#EXPECTED_BASE_SHA}" -eq 40
test "${#EXPECTED_CANDIDATE_SHA}" -eq 40
require_candidate_identity() {
  ACTUAL_CANDIDATE_SHA="$(git rev-parse HEAD)"
  test "$(git rev-parse --verify "${EXPECTED_BASE_SHA}^{commit}")" = "$EXPECTED_BASE_SHA"
  test "$(git rev-parse --verify "${EXPECTED_CANDIDATE_SHA}^{commit}")" = "$EXPECTED_CANDIDATE_SHA"
  test "$ACTUAL_CANDIDATE_SHA" = "$EXPECTED_CANDIDATE_SHA"
  test "$(git merge-base "$EXPECTED_BASE_SHA" "$ACTUAL_CANDIDATE_SHA")" = "$EXPECTED_BASE_SHA"
}
require_candidate_identity
EVIDENCE_PARENT="$(git rev-parse --git-common-dir)/herdr-dev-loop-release-evidence/0.5.1"
EVIDENCE_ROOT="$EVIDENCE_PARENT/$EXPECTED_CANDIDATE_SHA"
test "$(basename "$EVIDENCE_ROOT")" = "$ACTUAL_CANDIDATE_SHA"
mkdir -p "$EVIDENCE_PARENT"
test ! -L "$EVIDENCE_ROOT"
test ! -e "$EVIDENCE_ROOT"
mkdir -m 700 "$EVIDENCE_ROOT"
WARNING_LOG="$EVIDENCE_ROOT/unit.log"
umask 077
set -o noclobber
PYCACHE_DIR="$(mktemp -d)"
cleanup() {
  rm -rf "$PYCACHE_DIR"
}
trap cleanup EXIT
require_clean_worktree() {
  local worktree_status
  worktree_status="$(git status --porcelain --untracked-files=all)"
  test -z "$worktree_status"
}
require_clean_worktree

PYTHONPYCACHEPREFIX="$PYCACHE_DIR" python3 -m py_compile \
  skills/herdr-dev-loop/scripts/hloop \
  skills/herdr-dev-loop/tests/run_synthetic_e2e.py \
  skills/herdr-dev-loop/tests/run_provider_e2e.py \
  >"$EVIDENCE_ROOT/compile.stdout.log" \
  2>"$EVIDENCE_ROOT/compile.stderr.log"
printf 'passed\n' >"$EVIDENCE_ROOT/compile.status"
PYTHONDONTWRITEBYTECODE=1 PYTHONWARNINGS='always::ResourceWarning' \
  python3 -m unittest discover -s skills/herdr-dev-loop/tests -v \
  >"$WARNING_LOG" 2>&1
if rg -n 'ResourceWarning|Exception ignored while finalizing database connection' \
  "$WARNING_LOG"; then
  warning_scan_status=0
else
  warning_scan_status=$?
fi
case "$warning_scan_status" in
  0) exit 1 ;;
  1) ;;
  *) exit "$warning_scan_status" ;;
esac
PYTHONDONTWRITEBYTECODE=1 python3 skills/herdr-dev-loop/scripts/hloop version --json \
  >"$EVIDENCE_ROOT/version.json" \
  2>"$EVIDENCE_ROOT/version.stderr.log"
PYTHONDONTWRITEBYTECODE=1 python3 skills/herdr-dev-loop/scripts/hloop selftest \
  >"$EVIDENCE_ROOT/selftest.log" \
  2>"$EVIDENCE_ROOT/selftest.stderr.log"
QUICK_VALIDATE="$(find "${CODEX_HOME:-$HOME/.codex}" "$HOME/.claude" \
  -iname quick_validate.py -print -quit 2>/dev/null || true)"
test -n "$QUICK_VALIDATE"
PYTHONDONTWRITEBYTECODE=1 python3 "$QUICK_VALIDATE" skills/herdr-dev-loop \
  >"$EVIDENCE_ROOT/quick-validate.log" \
  2>"$EVIDENCE_ROOT/quick-validate.stderr.log"
PYTHONDONTWRITEBYTECODE=1 \
  python3 skills/herdr-dev-loop/tests/run_synthetic_e2e.py \
  --output "$EVIDENCE_ROOT/synthetic.json" \
  >"$EVIDENCE_ROOT/synthetic.stdout.log" \
  2>"$EVIDENCE_ROOT/synthetic.stderr.log"
git diff --check "$EXPECTED_BASE_SHA...$EXPECTED_CANDIDATE_SHA" \
  >"$EVIDENCE_ROOT/diff-check.log" \
  2>"$EVIDENCE_ROOT/diff-check.stderr.log"
require_candidate_identity
require_clean_worktree
printf 'passed\n' >"$EVIDENCE_ROOT/repository-gates.status"
```

`EXPECTED_BASE_SHA`と`EXPECTED_CANDIDATE_SHA`は、このblockを実行するcheckoutから導出せず、review対象として外部に固定したfull SHAを渡す。blockは開始時と終了時のHEAD、commit object、merge-base、固定SHA間のdiff、evidence directory名をその値と照合し、別のcleanなcheckoutや途中で移動したrefの結果をcandidate evidenceとして受理しない。candidate evidence directoryは既存file、directory、symlinkを受理しないone-shot directoryとして作成し、`noclobber`で既存または差し替えられた`unit.log`を上書きしない。再実行する場合は既存証跡を退避してから、空のpathに対して明示的に開始する。

`PYTHONWARNINGS=error`だけでは、SQLite finalizer内の例外が`Exception ignored`となり、test processが0で終了する場合がある。このため、deterministicなunit regressionに加えて、release時はfull suiteのstderrも検査する。

### provider validation

利用者指示により、0.5.1 candidateではCodexのlive availability/read-only marker probeだけを固定SHAで実行する。`--allow-skip`は診断には使えるが、0.5.1 release passには使わない。runはprovider、model、開始時刻、終了時刻、result JSONを保存する。このprobeはCodex CLIの起動とmarker応答を検査するだけで、HLoop role起動、Herdr、rendered prompt、report経路は検査しない。runnerのlegacy filenameには`e2e`が残るが、result JSONの`runner`、`probe_kind`、`coverage`、`excluded_coverage`はmarker probeの限定された証明範囲を明示する。

Claude live provider E2Eとfresh Claude discoveryは今回実施しないため、release evidenceでは`not run`とする。この限定はClaude provider設定、Claude install path、一般的なClaude対応記述を削除する判断ではない。Claude installed copyの`diff -qr`とPython selftestが成功しても、Claude CLIを使うlive E2Eまたはfresh discoveryの成功を意味しない。

### specとcodeの整合性

Gap Auditorは0.5.0 plan、0.5.1 plan、release note、follow-up dispositionを現在SHAのcodeと照合する。0.5.1 acceptanceを満たさないgapが一件でもあればreleaseを止める。0.5.2のscope制御機能が未実装であること自体はgapにしない。

### 手動最終review

freshなCoordinator contextで`codex-review-multi-v2`を実行し、baseを0.5.0 baseline、HEADを0.5.1 candidateへ固定する。通常4 laneとし、次をfocusへ含める。

- same-UID threat modelとManager consumer guardの整合性
- report retry、idempotency key、outbox、broker、wakeのfault boundary
- SQLite lifecycleとresource cleanup
- migration、version、rollback、install parity

verified actionable finding 0件だけをpassとする。pre-existingまたは0.5.1 scope外の改善は根拠付きfollow-upへ送る。

repository、Codex marker probe、install parity、installed selftest、fresh Codex discovery、Gap Audit、4 lane reviewの出力は、release noteのEvidence contractが定義するfile名で同じone-shot candidate directoryへ保存する。probe、install、finalizerは外部固定したbase/candidate full SHA、commit object、HEAD、merge-baseを照合する。Gapと各review verdictはbase/candidate SHAを含む3行形式で完全一致させ、説明文中の部分一致をpassにしない。全fileが揃う前にrelease済みとせず、release noteのfinalizerで内容を検証して`manifest.json`を原子的に確定する。Claude live provider E2Eとfresh Claude discoveryはfinalizerでも`not_run`のまま保持する。

## installとrelease gate

repository reviewを通過した0.5.1 candidateを`master`へ`--ff-only`で統合してpushし、その`master` SHAからinstalled copyを作る。

1. 0.5.1 candidate SHAと`master`へ統合後のSHAが一致することを確認する。
2. 現在のCodex版とClaude Code版をtimestamp付きでbackupする。
3. `master`のrepository版を両installed directoryへ`rsync -a --delete`で同期する。
4. repository、Codex、Claude Codeの`diff -qr`が0件であることを確認する。
5. 三copyの`hloop version --json`が0.5.1を報告することを確認する。
6. 両installed copyでselftestを実行する。
7. freshなCodex sessionでskill discoveryと0.5.1 bannerを確認する。fresh Claude discoveryは`not run`として別記する。
8. 失敗時はinstalled copyを0.5.1直前のbackupまたは既存0.4.0 backupへ戻し、versionとselftestを再確認する。`master`はrelease失敗として扱い、原因修正用branchを切る。

## release判定

次をすべて満たした場合だけ0.5.1をrelease済みとする。

- `D001`が利用者回答付きでresolvedである。
- T501、T502、T503だけが実行され、未説明のscope追加がない。
- F002の三crash pointとsame-content/new-key testが成功する。
- F003の制約と後続先がREADMEとfollow-upへ記録されている。
- F005がwarning-as-errorで成功する。
- repository validation、Gap Audit、manual reviewが固定SHAでpassedである。
- manual reviewのverified actionable findingが0件である。
- Codexのlive availability/read-only marker probeがpassedである。HLoop role経路のlive E2Eを実施したとは主張せず、Claude live provider E2Eは`not run`として明記されている。
- repository、Codex、Claude Codeのversion、Python selftest、byte parityがそれぞれpassedである。
- fresh Codex discoveryがpassedである。fresh Claude discoveryは`not run`として明記され、成功扱いされていない。
- rollback backupと復元手順が確認できる。
- release後の`master` SHAとinstalled source SHAが一致する。

## 0.5.2への引継ぎ

0.5.1から0.5.2へ送るのは、有界review convergence、release scope lock、dispatch freeze、first-class follow-up、Manager observabilityである。0.5.1のrelease reviewで見つかった妥当な改善も、0.5.1 acceptanceと現在diffに関係しない場合は同じfollow-up ledgerへ追加する。

ACK承認前のOSレベルread-only化はprovider isolationの課題として別IDを持たせる。0.5.2のscope制御実装へ便乗させない。
