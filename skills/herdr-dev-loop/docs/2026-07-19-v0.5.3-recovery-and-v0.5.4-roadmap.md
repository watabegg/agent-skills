# herdr-dev-loop 0.5.3 復旧と 0.5.4 以降のロードマップ

Status: recovery execution authorized; release decisions remain gated

この文書群は、停止中の 0.5.3 実装を安全に畳み、その反省を 0.5.4 以降へつなぐための実行計画である。2026-07-19 のユーザー指示により、推奨順での recovery bootstrap と慎重な task 分割は承認された。旧 run の role state は再開せず、release 時の外部依存や追加 remediation は別の gate で判断する。

## 結論

次の三段階に分ける。

1. 0.5.3 を再開する前に、小さい fast fix と運用上の遮断策を入れる。
2. 旧 run の状態機械は再利用しない。T051 候補を recovery branch の未承認 baseline とし、T050 候補と全レビュー証跡を exact identity 付きで後から統合する。
3. repository 固有 memory、Manager の長時間運転対策、中央 CLI の分割は 0.5.4 以降で製品化する。

ACK は廃止しない。ACK は、Codex TUI へ送った最初の prompt が Enter のタイミング問題で実行されず、入力欄の改行になった事故を material work 前に検知するために必要である。今回の設計上の問題は、ACK の承認通知まで同じ TUI 送信経路へ戻し、検知器が検知対象へ依存する循環を作った点にある。

fast fix では、最初の prompt 送信だけを TUI の可視確認対象として残す。role が ACK を送った後の承認待ちと承認取得は broker と STATE だけで完結させる。TUI への追加送信は、人が契約変更や補足指示を行う場合に限定する。

また、作業が進むにつれて Manager が skill の規範を取りこぼす問題には、すぐ使える運用策と 0.5.4 の製品機能を分けて対応する。0.5.3 の復旧中は、短い Manager セッション、毎回の deterministic brief、同じ運用エラーを二度繰り返した時点での circuit break を使う。0.5.4 では、これを repository 固有 memory と強制可能な state transition にする。

## scope の境界

### 0.5.3 で完了させるもの

- 元計画の未実装または不完全な受入条件
- R005、G053、T050 Patch Review、T051 Patch Review で確認済みの in-scope finding
- task を requeue しても Patch Review 履歴と一回限りの追加許可を失わないこと
- ACK 承認後に pane の Enter 送信へ依存せず role が再開できること
- pause、supersede、requeue を含む 0.5.3 outcome metrics の最低限の正確化
- exact SHA に結び付いた full suite、synthetic、migration、release evidence

これらは元計画の受入条件 13、46、47、50 と release gate の未達であり、新しい便利機能として 0.5.4 へ先送りしない。

### 0.5.3 の復旧運用として使うが、製品化は 0.5.4 で行うもの

- Manager セッションを batch 境界で交代する手順
- deterministic Manager brief
- 同じ transport または lifecycle 失敗を二度検知したときの dispatch freeze
- 旧 run を read-only evidence として保ち、fresh canary namespace へ移す手順

0.5.3 中は runbook と小さい guard で使う。汎用 CLI、schema、永続 store としての完成は 0.5.4 に含める。

### 0.5.4 以降へ送るもの

- XDG state directory に置く repository 固有 memory
- Git common directory 由来の repository UUID と clone alias の管理
- verified、refuted、stale を持つ incident ledger
- token budget 付き Manager/Worker projection
- successor task 系列を横断する修正予算
- Manager rotation と handoff capsule の製品機能
- 中央 `hloop` の command module 分割
- review、validation、release evidence の exact-SHA cache

## 推奨する実行順

```text
旧 run を凍結
  -> 候補と証跡の recovery manifest を作成
  -> T051 candidate から recovery branch を作成
  -> 043eb92 の固定 runtime で TUI・1 Worker の bootstrap を開始
  -> ACK transport だけを seed task として統合
  -> fresh canary namespace を ACK 修正済み runtime で開始
  -> pre-mutation guard を統合
  -> T050 候補を取り込み、既知 finding を原因別に修正
  -> T052 から T055 を新しい base で再生成して実装
  -> exact-SHA full validation
  -> Reviewer swarm と Gap swarm を同じ SHA で一度ずつ実行
  -> finding を一括 triage し、最大2回の bounded remediation
  -> closure review と必須 regression challenge
  -> install parity と release gate
```

bootstrap namespace で `exec` runner は使わない。現行 prompt は role に ACK 後の停止を要求する一方、`exec` は一回の provider process で終わるため、承認後の同じ process turn を保証できないからである。

bootstrap は TUI の1 Workerだけを起動し、初回 prompt の submit を semantic ACK で確認する。ACK 承認通知は現行経路を一度だけ使い、同じ配送失敗を再送しない。seed task が blocking broker exchange と pane notification 不要の再開を実証した時点で bootstrap を終了し、その SHA から fresh canary namespace を作る。

T051 候補を branch の起点にすることは、候補の review 合格を意味しない。制御用 runtime と product baseline を分け、7件の finding、candidate artifact、Patch Review 履歴を recovery manifest の未解決項目として引き継ぐ。
