# herdr-dev-loop 0.5.3 release note

## Release identity

- Skill version：`0.5.3`
- State format：`3`
- Schema revision：`3`
- Current task/result contract revision：`3`
- Minimum Python：`3.11`
- Legacy `.ai/loop`：ignored
- External protocol dependency：`release-dependencies.json`で固定した`codex-review-multi-v2`と`externally-planned-v1`

0.5.3はsession時間を短縮するために検査を省略するreleaseではない。planning evidence、Worker candidate、Patch Review、review epoch、共通remediation ledgerにより、同じ前提の読み直しと小分けの修正roundを減らしながら、0.5.2のrelease scope、follow-up、accepted risk、manual final、semantic ACK、handoff safetyを保持する。

## PlanningとWorker gate

Worker dispatch前に、Repository Impact Map、Task Risk Graph、coverage ledger、Plan Gap artifactが一つのplanning identityを共有する。plan、requirements、release scope、sourceのrevisionまたはdigestが変われば、古いplanning evidenceはstaleになりdispatchを止める。

revision-3 Workerは最終resultの前にnonterminal implementation candidateをsubmitする。candidateはattempt、task contract、semantic ACK、completion mode、base、exact product tree、validationと5分類のQA evidenceへ固定される。初回ACKのGit metadata probeがattemptをcommitまたはhandoffへ束縛し、contract re-ACKはそのmodeを変更しない。

taskがPatch Reviewを要求する場合、finalize、harvest、mergeはexact candidateのpassing reviewを要求する。candidateまたはcontractが変われば古いreviewはstaleになる。通常のPatch Reviewは最大2 roundであり、上限後にtask外の自動修正を作らない。

## Review epochとremediation

ReviewerとGap Auditorは同じtarget SHAのimmutable epochに属する。Reviewerの既定は1 Coordinatorと6 externally planned lane、Gapの既定は1 Coordinator、4 requirement-audit lane、1 coverage challengeである。Coordinator、lane、verifier、Patch Reviewerはepoch共通のAgent budget 12へ予約する。timeoutしたprocessは終了またはforced abortを確認するまでquarantineとしてcapacityを保持する。

同じSHAへの追加passはsuccessor revisionとしてlineageと既存artifact digestを継承する。target SHAが変われば新しいepochを作る。必須executionのfailure、未完了、identity mismatch、capacity shortfallをzero-finding成功として扱わない。

remediationはReviewerとGapのcollection barrierが閉じてから始まる。全candidateをcanonical fingerprintで登録し、classification conflictを解消した後、一つのbatchを一度だけ承認する。task materializationはwrite-ahead planを保存してから実行し、crash後のretryは同じtask identityとdigestを照合する。通常のfix roundは最大2回であり、追加roundには未使用の明示user inputが必要である。

## Validation、requirements、outcome

L1、L2、L3のvalidation evidenceはtarget SHA、command、toolchain、lockfile、resolved config、identity digestが一致する場合だけ再利用できる。特殊domainは`verification record`で別に記録する。Managerはevidence draftを作成し、`requirements reconcile`のdry-runを確認してから明示applyする。completion reportだけでrequirementを実装済みにしない。

outcomeはwall、active、wait、Agent、yield、escaped finding、validation reuseを分けて記録する。blocked goalは通常の成功reportへ混ぜず、blocking authorityと未完了scopeを残す。

## Schema 3.3 migration

migrationは次のchainを使う。

```text
format-1.revision-0
  -> format-2.revision-0
  -> format-3.revision-0
  -> format-3.revision-1
  -> format-3.revision-2
  -> format-3.revision-3
```

`migrate --dry-run`は書き込まない。`--apply`はsource/planned artifact digest、archive、prepared markerを保存し、各artifactをatomicに置換してからcommitted markerを確定する。中断後は`--resume`が記録済みtransactionを照合して続行する。`--rollback`には、prepared/runningのpartial replacementを保存済みarchiveへ戻すrecovery rollbackと、committed後かつ最初の0.5.3 mutation前だけのrollbackがある。どちらもmarker、archive、全artifact digestの一致が必要で、`rollback-prepared`の中断は`--resume`で継続する。

revision-2 task/resultはlegacy unionとして内容を保持する。migrationは`contract_schema_revision: 2`を付けられるが、invariant、regression、self-review、residual risk、unrun checkを過去に実行した証拠として追加しない。historical QAの別artifactは[Worker QA証拠再構築](2026-07-17-v0.5.3-worker-qa-reconstruction.md)に固定した。

## Companion dependency

`codex-review-multi-v2`はHLoop本体と分離したsibling skillとして同じrepositoryへsnapshotする。[`release-dependencies.json`](../release-dependencies.json)は配布元、immutable fork commit、exact adapter version、minimum compatible version、`sha256-tree-v1` payload digest、capability manifest path、`externally-planned-v1`を固定するrelease authorityである。0.5.3のrecordは`availability: available`、`release_ready: true`であり、upstream `49fd08742f7666efa1fd4775989317d2da73f077`をhardeningしたfork commit `de40e11747edde38684f2e75f94c773b6b086ccc`とadapter version `2.1.1`へ固定する。installed mutable copyから値を補完してはならない。

external Reviewerの起動直前には、PLAN内の各process providerが実際にdiscoverするcompanion rootを`CODEX_HOME`または`CLAUDE_CONFIG_DIR`から解決し、payload digestとmanifestをrelease pinへ再照合する。検証済み絶対path、adapter record、provider環境はReviewer実行stateへ保存し、同じconfig rootを起動commandへ明示してlogin shellの設定変更を上書きする。sibling copyだけが正しくprovider側copyがstaleな場合は起動しない。Codex invocationはuser config由来の追加workspace-write rootを空に固定し、HLoopが明示するworktree/git pathだけを書込可能にする。

payload digestは、digestを内包するcapability manifestだけを除外し、残りのregular distribution fileをlexicographic relative-path順にhashする。manifestは別途canonical schemaとrelease pinへ完全一致させる。payload、manifest、source、versionのどれか一つでもdriftすればselftestとruntime validationはfail-closedで停止する。

external Reviewer開始時は`external_review_protocol_adapter` recordをepochへ渡す。manifest欠落、unknown field、protocol/source/version/digest不一致、required capability欠落はfail-closedである。lane数を4へ減らす、companionに別Coordinatorを起動させる、nativeへ暗黙fallbackする挙動はない。

epoch create/successorは毎回canonical dependency recordを読み、`release_ready: false`または`availability: unavailable`なら外部executionを保存する前に停止する。available時もdistribution versionがminimum compatible version以上であること、repository URLとpayload digestから作るcontent-addressed adapter source、exact version、content digest、capability集合がrelease pinと完全一致することを要求する。Git commitはadapter sourceと分離したfetchable distribution pinとして検証する。

manual finalのPLAN/MANIFESTは、`independent`または`reuse_epoch_reviewer`のexecution policy、execution/source ID、source artifact ref/digest、固定target、同じpinned adapterを共有する。independentはcompleteなpre-final sourceと別execution、reuseは成功済みfixed-target epoch Reviewerと同じexecutionだけを許す。duplicate/synthetic source、artifact drift、adapter drift、review ID driftはcomplete-zero claimより先に失敗する。

## Release gates

repository candidate SHAを固定した後、次のcheckを同じSHAで記録する。

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest \
  skills.herdr-dev-loop.tests.test_release_v053
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s skills/herdr-dev-loop/tests -p 'test_*.py' -q
PYTHONDONTWRITEBYTECODE=1 python3 skills/herdr-dev-loop/scripts/hloop \
  selftest --skill-dir skills/herdr-dev-loop --json
PYTHONDONTWRITEBYTECODE=1 python3 \
  "${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-creator/scripts/quick_validate.py" \
  skills/herdr-dev-loop
PYTHONDONTWRITEBYTECODE=1 python3 \
  skills/herdr-dev-loop/tests/run_synthetic_e2e.py --json
git diff --check
```

Migration crash matrixはprepared、各atomic replacement、committed、resume、rollback、first mutationを対象にし、3.2と3.3のmixed stateを成功扱いしない。

repository testが通ってもreleaseは完了しない。[Migration And Install Parity](../references/migration-install.md)に従ってHLoopとpinned companionをCodex/Claudeへ同期し、次の独立gateをすべて記録する。

| Gate | 必須証拠 |
| --- | --- |
| HLoop static parity | repository、Codex、Claude copyの差分なし |
| HLoop runtime parity | 両installed copyの`version --json`が0.5.3、selftest成功 |
| Companion content parity | 両installed treeの`sha256-tree-v1`がdependency pinと一致 |
| Capability manifest parity | source、version、digest、`externally-planned-v1`が両providerで一致 |
| Codex fresh session | replacement sessionがHLoop 0.5.3とpinned companionをdiscoverしてhandshake成功 |
| Claude fresh session | replacement sessionがHLoop 0.5.3とpinned companionをdiscoverしてhandshake成功 |

missing install、旧sessionのcache、skip、片方だけの成功、unversioned companion、digest不一致をpassedへ読み替えない。

## Compatibility boundary

0.5.3は0.5.2の同一UID cooperative trust modelを維持する。attempt credentialは誤配送、stale attempt、role identity mix-upを防ぐが、悪意あるsame-UID processから秘密を分離するsecurity boundaryではない。0.6.0のhuman review room、汎用issue tracker、Herdr serverの再設計はこのreleaseに含まれない。
