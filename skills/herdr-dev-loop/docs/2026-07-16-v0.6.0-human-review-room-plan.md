# herdr-dev-loop 0.6.0 Human Review Room設計

- Status: Draft（基本方針採用済み、実装詳細を詰める段階）
- Date: 2026-07-16
- Target: herdr-dev-loop 0.6.0
- Baseline: herdr-dev-loop 0.5.2
- Follow-up: 日本語Human Console TUIは0.6.1

## 背景

0.5.2は、固定したintegration SHAに対するreview candidateの発見、独立検証、findingの分類、boundedな修正ラウンド、独立した最終AI認証を扱う。Reviewerは事実と証拠を報告し、Managerはfindingの処置を決める。Review artifactが存在するだけではgateを閉じず、manifest completenessとverified actionable findingの件数を再計算する。

この構造には、人間がreview内容を理解し、AI Agentと壁打ちし、過去の経験、ドメイン知識、リポジトリ全体の知識、複雑さを減らす判断を与える工程がない。現行のDecision Liaisonは、一つの未決事項を二つか三つの選択肢へ変換し、明示的な回答を受け取る。AdvisorはManager向けのAI相談役である。複数のfindingを理解し、反論し、追加証拠を求め、判断へ収束させる人間向けのreview protocolは、どちらの役割にも含まれない。

0.6.0では、AI reviewとManager triageのあいだにHuman Review Roomを追加する。人間をコード上の事実を再検証するReviewerとして扱わない。AI Reviewerが事実確認を担当し、人間は、リポジトリ固有の文脈、製品判断、複雑さの許容範囲、risk受容、scope判断を与える。

0.5.2で`manual final review`と呼んでいる工程は、人間によるreviewではなく、手動で起動する独立AI認証である。0.6.0の利用者向け表示では`independent AI certification`または「独立AI認証」と呼び、人間との対話工程と区別する。既存state fieldの改名はmigration costを確認して別途決める。

## 目的

0.6.0は次の結果を目指す。

1. 人間がraw review manifestを読み込まなくても、判断が必要な論点を理解できる。
2. 人間がReview Liaisonへ質問、反論、単純化案を返し、複数turnで判断できる。
3. 人間の反論が事実判定を直接上書きせず、必要な場合は追加検証へ戻る。
4. 人間の入力を、decision、requirement、fix task、follow-up、accepted risk、context candidateのいずれかへ追跡できる。
5. Review Room後に対象SHAまたはscopeが変わった場合、古いreview判断を安全に失効または再確認できる。
6. 人間の明示的な回答とAI Agentの推奨を混同しない。
7. すべてのproduct taskを、task-localなgap checkとhandoff reviewに通し、統合後のfindingを減らす。
8. Managerがintegration branchを自ら俯瞰し、findingをリポジトリ全体との整合、横断的な影響、最も単純な代替案から採択できる。
9. 人間が現在どの種類の相談へ対応できるかをintegration branchのManager checkoutにあるnamespaced fileへ登録し、AI Agentと人間が同じ状態を確認できる。

## 非目標

0.6.0は次の能力を保証しない。

- 人間にコード上の発生経路やtest evidenceの再検証を求めること
- 人間の沈黙、paneの閲覧、semantic ACK、AI Agentの推奨を同意として扱うこと
- 人間の自由記述からfix task、scope変更、risk受容を自動確定すること
- Review Liaisonへmerge、task作成、gate closureの権限を与えること
- rawな会話全文をGit管理artifactとして保存すること
- 会話内容を自動的にrepository-wideな永続知識へ昇格すること
- すべてのtaskまたはすべてのfindingで人間との対話を必須にすること
- taskごとに`codex-impl`相当の複数sub-agent実装、full multi-review、browser QAを起動すること
- ReviewerまたはTask Auditorへ、findingの正式な採択とrepository-wideな処置判断を委ねること
- pane focus、応答速度、Agentの観測から人間の稼働状態や同意を推測すること
- 人間の稼働状態を操作するHerdr tabまたはTUIを0.6.0へ含めること
- 0.5.2のAI review convergenceまたは独立AI認証を置き換えること

## 用語

- **Human Review Room**：一つの固定target SHAとreview manifestに対して、人間がAI Agentと対話する論理的なreview session。
- **Review Session**：Human Review Roomの一回の実行単位。`H001`のような安定IDを持つ。
- **Review Liaison**：review evidenceを人間向けに説明し、質問と反論を受け、確認済みの回答をartifactへ記録するAgent role。
- **Review Brief**：session開始時に生成する、人間向けの短い論点一覧。
- **Review Card**：一つのfindingまたは密接に関係するfinding群を、人間が判断できる単位へ変換した表示。
- **Task Completion Gate**：Worker taskをManagerへ渡す前に、task-localな欠落と受け渡し可能性を独立に確認する軽量gate。
- **Task Auditor**：固定したtask candidate SHAをread-onlyで確認し、Task Gap CheckとTask Handoff Reviewを行うAgent role。
- **Repository Evidence Context**：ReviewerまたはTask Auditorが、局所diffやfindingを関連subsystem、caller、既存慣例、類似実装へ接続した証拠情報。正式な処置判断は含めない。
- **Manager Repository Decision Brief**：Managerがintegration branch、release scope、既存decision、複数findingを自ら確認し、採択候補と最も単純な代替案をまとめた判断材料。
- **Human Contribution**：人間が会話中に与えた判断、ドメイン事実、過去の経験、簡素化方針、risk選好、scope指示の候補。
- **Human Availability Record**：integration branchのManager checkoutに置く、人間のavailability、interaction mode、interrupt policy、対応可能な相談種別の正本file。
- **Human Console**：Human Availability Recordを日本語で操作する0.6.1予定のHerdr TUI。0.6.0のscopeには含めない。
- **Availability Lease**：一時的な人間の稼働宣言に期限を持たせ、期限切れを`unknown`へ戻す仕組み。
- **Independent AI Certification**：収束済みの固定target SHAをfresh contextで再確認する最終AI review。人間のReview Sessionとは別のgateである。

## 判断主体

| 対象 | 主な判断主体 | Review Roomでの扱い |
|---|---|---|
| findingの発生経路 | Reviewerまたは独立Verifier | 人間から反論があれば再検証する |
| validation evidenceの十分性 | ReviewerとManager | 不足証拠と残るriskを説明する |
| 過去の事故と運用上の制約 | 人間 | Human Contributionとして記録する |
| ドメイン不変条件 | 人間 | 適用範囲を確認して記録する |
| リポジトリ全体の方向性 | 人間 | sourceと影響範囲を確認する |
| 複雑さに見合うか | 人間 | 最も単純な代替案と比較する |
| findingの正式なdisposition | Manager | 人間入力を根拠にManagerが確定する |
| task acceptanceの充足 | Task AuditorとManager | 不足が判断事項なら早期Review Roomへ送る |
| task diffのhandoff可否 | Task Auditor | 固定candidate SHAに対して独立判定する |
| findingのrepository fitと処置 | Manager | ReviewerとTask Auditorの証拠を使い、integration branchを自ら確認する |
| task作成とmerge | Manager | Review Liaisonは提案だけを返す |
| risk受容とscope変更 | 権限を持つ人間とManager | 明示的なuser inputとprovenanceを要求する |

## Task Completion Gate

現行のnative Worker protocolは、Worker自身のdiff self-reviewとvalidationを要求する。`worker_protocol: codex-impl`のcompatibility modeも、通常はtask branchに対するgap checkを一回行い、明示されない限りreview/fix loopを省略する。0.6.0ではどちらにも依存せず、すべてのproduct taskをManagerがharvestまたはmergeする前に、独立した軽量gateへ通す。

Task Completion Gateは一つのTask Auditorが、固定したcandidate SHAに対して次の二つのlaneを順に確認する。

1. **Task Gap Check**：MISSION、PLAN、requirement、task acceptance、Workerの完了主張をcandidate diffと照合する。未実装の挙動、test不足、生成物の更新漏れ、QA evidence不足、task内で閉じるべき残件を探す。
2. **Task Handoff Review**：「この差分をそのままManagerへ渡してよいか」を判定する。write scope、validation evidence、近接するcallerと契約、repository convention、統合時の影響、rollback risk、不要な複雑さを確認する。

Task Auditorはproduct codeを変更しない。結果は次のいずれかとする。

- `pass`：両laneを満たし、Managerへ受け渡せる。
- `fix-required`：同じtaskのacceptanceまたはhandoff品質に不足があり、Workerへ戻す。
- `human-judgment`：複数の妥当な設計、domain context、riskまたはscope判断が必要である。
- `blocked`：証拠不足、実行環境不足、identity不一致などで判定できない。

`fix-required`は同じWorker taskへ戻し、candidate SHAが変わった後にgateを再実行する。candidate SHAが同じままの再実行は許可しない。Managerは両laneの`pass`、または権限を持つ人間とManagerによる明示的なdecision・accepted riskがない限り、taskをharvestまたはmergeしない。

Task Handoff ReviewはRepository Evidence Contextも生成する。最低限、次を含める。

- 影響するsubsystem、caller、公開契約
- 関連するrepository conventionと近接する類似実装
- 既存のdecision、follow-up、過去の制約
- 局所修正で閉じるか、横断的な変更を生むか
- 最も単純で一貫した代替案
- `fix-now`、`defer`、`disable`それぞれのcostとrisk

これはtaskごとの`codex-impl`ではない。実装sub-agent群、full `codex-review-multi-v2`、taskごとのbrowser QAを標準起動せず、一つの独立read-only Agentで受け渡し品質を安価に上げる。fix taskを含むproduct taskへ適用し、`operational` taskだけはManagerが理由を記録してwaiveできる。

Task Completion Gateの正本は`task-gates/<task-id>/<attempt-id>/`に置き、candidate SHAとtask contract digestを持つ`CANDIDATE.json`、両laneの判定とRepository Evidence Contextを持つ`REPORT.md`を保存する。Workerの自己申告だけで`pass`を合成せず、Task Auditorの独立artifactとsemantic completion reportをharvest時に照合する。

gate statusは`prepared -> running -> reported -> passed|fix-required|human-judgment|blocked`とする。candidate identityが変わったattemptは`superseded`にし、以前の`passed`を再利用しない。

### Manager Repository Decision Brief

ordinary review、bounded convergence、独立AI認証では、Reviewerが各actionable findingへRepository Evidence Contextを付ける。Reviewerは局所的なbugとして閉じられる根拠、他のsubsystemへの波及、類似実装、既存契約を報告するが、repository-wideな処置は確定しない。

Managerはtriage前にintegration branchの固定target SHAを自ら読み、複数findingを横断してManager Repository Decision Briefを作る。Briefには次を含める。

- findingの事実と、Reviewerが提示したRepository Evidence Context
- 影響するsubsystem、caller、設定、運用
- repository内の類似実装、従うべき慣例、既存decision
- 同じ原因または設計方針に関係する他のfinding
- 現在のrelease scopeで修正する場合とfollow-upへ送る場合の差
- `fix-now`、`defer`、`disable`、`accepted-risk`、`not-applicable`の候補
- 製品仕様の単純化、削除、無効化、共通化を含む最も単純な代替案

ManagerはBriefを根拠に正式なdispositionを選び、`repository_rationale`と`simpler_alternative_considered`をtriage recordへ残す。証拠が不足する場合はReviewerへ処置判断を返さず、targeted context調査を追加する。別roleが必要な場合だけContext ScoutまたはAdvisorをopt-inで使い、製品判断、risk受容、scope変更が必要ならReview Roomへ送る。

Manager Repository Decision Briefの正本は`reviews/manager/<review-set-id>/DECISION-BRIEF.md`へ置き、対象review manifest digest、target SHA、参照したfinding、repository evidence、Manager dispositionを結び付ける。Reviewer artifactを書き換えてManager判断を混在させない。

初期実装では、固定target SHAのreview manifestが揃い、Managerがremediation taskを作成する前を標準のReview Room checkpointとする。明確な事実と既存契約だけで処置できるfindingは、人間との対話を待たずにtriageできる。人間判断が必要なfinding、risk受容、scope変更、複雑性判断をReview Briefへ優先して載せる。

### 早期Review Roomを開く条件

全taskで人間を待たない。標準checkpointより前にReview Roomを開くのは、Workerのsemantic ACKまたはTask Completion Gateで次のいずれかを検出した場合に限る。

- 複数の設計が妥当で、既存契約だけでは一つに決められない
- public interface、schema、migration、互換性、rollback costが大きい
- 実装の複雑さが高く、より単純な製品・運用上の選択肢があり得る
- repository全体の慣例、過去の事故、domain knowledgeが判断を左右する
- `human-judgment`または`human-judgment-candidate`が報告された
- Workerがtask contractまたはacceptanceの曖昧さをACKで報告した

早期Review Roomは影響するtaskだけを止める。write scopeとdependencyが独立したtaskは継続できる。人間がlive対応できない場合は対話paneを起動せずagendaをqueueし、明示的な人間判断が不要なtaskとAI reviewを進める。

## Review Brief

Review Briefはraw manifestの短縮版ではない。人間が何を判断すべきかを示すagendaである。標準では、同時に提示するReview Cardを最大5件とする。残りは件数と分類だけを表示し、人間が要求した場合に展開する。

Review Briefには次を含める。

- 今回の変更を一段落で説明したsummary
- target SHA、base SHA、release scope revision
- AI reviewが確認済みの範囲と未確認の範囲
- 人間判断が必要なReview Card
- Managerが作成したCardごとのRepository Decision Brief
- AI側で処置できるfindingの件数と処置案
- 前回のReview Sessionから変わった内容
- sessionを終えるために必要な回答

## Review Card

Review Cardは次の順序で表示する。

1. 一文で表した問題または判断対象
2. 実際に起きるscenario
3. 製品、利用者、運用、保守への影響
4. findingのfact statusと証拠の状態
5. AI Agentが推奨する処置と理由
6. ReviewerのRepository Evidence Context
7. 最も単純な代替案
8. `fix-now`、`defer`、`disable`の比較
9. Managerの暫定dispositionとrepository rationale
10. 人間の判断が必要な理由
11. 詳細を読むためのartifact、path、symbol参照

Review Cardには`judgment_kind`を持たせる。

- `fact-challenge`：人間がAI reviewの事実認定へ反論している。追加検証が必要になる可能性がある。
- `domain-context`：コードや既存specにないドメイン事実を人間が補う。
- `product-tradeoff`：製品挙動または利用者体験の選択を行う。
- `complexity-budget`：安全性、保守性、実装量の釣り合いを判断する。
- `risk-acceptance`：残る具体的なriskを受容するか判断する。
- `scope`：今回のrelease contractを変更するか判断する。

一つのCardへ複数の`judgment_kind`が必要な場合は、回答欄を分ける。事実への反論とrisk受容を一つの選択肢へまとめない。

## Review Liaison protocol

Review Liaisonは固定target SHA、Review Brief、Review Card、review manifest、release scope、既存decisionを読む。Review Liaison自身がfindingをconfirmedまたはrefutedへ変更しない。

対話は次の状態を通る。

1. `presented`：問題、証拠、推奨、単純な代替案、必要な回答を提示する。
2. `dialoguing`：人間の質問、反論、自由記述へ回答する。
3. `needs_evidence`：回答に追加のコード検証、再現、別Verifierが必要である。
4. `proposed`：人間の発言から読み取った判断を、Review Liaisonが確認文として提示する。
5. `confirmed`：人間が確認文へ明示的に同意または修正を返す。
6. `reported`：確認済み内容とprovenanceをartifactへ記録し、Managerへcompletion reportを送る。

Review Liaisonは、質問への回答に必要な証拠がない場合、推測で会話を閉じない。`needs_evidence`を報告し、対象Cardと必要な検証をManagerへ返す。Managerは同じSHAに対するtargeted verificationを起動し、結果を同じReview Sessionへ追加する。

Review Liaisonが人間の自由記述を構造化するときは、確認文を返してから待つ。Review Liaison自身の要約、推奨、Manager message、system出力、tool出力、semantic ACK、無応答は、人間の確認ではない。同じpaneで確認文を提示した後に届いた明示的な人間入力だけを`confirmed`の根拠にする。

## Review RoomのHerdr UI

一つのReview Sessionにつき、HLoopが専用Herdr tabを一つ作る。標準layoutは2列3行で、Lobby paneを一つ、finding-specificなReview Liaison paneを最大5つ置く。

```text
Human Review H001
┌──────────────────────┬──────────────────────┐
│ Lobby / Brief        │ F001 Review Liaison  │
├──────────────────────┼──────────────────────┤
│ F002 Review Liaison  │ F003 Review Liaison  │
├──────────────────────┼──────────────────────┤
│ F004 Review Liaison  │ F005 Review Liaison  │
└──────────────────────┴──────────────────────┘
```

grid表示は全体のagendaと状態を俯瞰するために使い、長い対話を行うfinding paneはzoomして読む。一度に人間へ能動的に質問するpaneは一つだけとし、他のpaneは`ready`または`waiting`で待つ。5件を超えるCardは次のwaveへqueueする。

各paneは同じsession identity、target SHA、scope revision、manifest digestを固定し、finding paneは一つのCardだけを主対象にする。論理IDは`H001`、`F001`、`RL-H001-F001`のようにHLoop stateへ保存する。Herdrのlive tab IDとpane IDはclose後に変わり得るため、永続identityとして使わず、再開時にtab、label、role identityから再発見する。

HLoopがtab作成、pane split、rename、layout、zoom、cleanupを管理する。terminalが狭く2x3で読めない場合は、Lobbyとactive findingの2-pane layoutへ縮退し、残りをqueueする。paneを手動で並べ替えてもartifact identityは変わらない。

## Artifact

Review Sessionの正本は次のdirectoryに置く。

```text
.ai/herdr-dev-loop/loops/<namespace>/reviews/human/H001/
├── SESSION.json
├── BRIEF.md
├── CONTEXT.jsonl
├── findings/
│   ├── F001/
│   │   ├── CARD.md
│   │   ├── THREAD.md
│   │   └── RESPONSE.md
│   └── F002/
│       ├── CARD.md
│       ├── THREAD.md
│       └── RESPONSE.md
└── OUTCOME.json
```

`inputs/`はrawまたはredactedなuser inputのlocal-only保存先として使う。Review Session artifactへ生の会話全文を複製しない。後続findingへ自動注入するのは`CONTEXT.jsonl`だけであり、全`THREAD.md`ではない。

### SESSION.json

Sessionのidentityとlifecycleを記録する。

- session ID
- run ID
- skill version
- base SHAとtarget SHA
- release scope revisionとsource snapshot revision
- source review planとmanifest digest
- policy
- status
- logical room、finding、liaison IDとlive Herdr tab・pane mapping
- started、confirmed、applied、supersededの時刻
- Review Liaisonのrole identity、attempt、pane、worktree

### BRIEF.md

人間向けagendaを記録する。BRIEFはAI Agentが生成した説明であり、人間の同意やManager dispositionを表さない。source manifestまたはtarget SHAが変わった場合はstaleとして扱う。

### findings/FNNN/CARD.md

一つのReview Cardと、Cardに必要な証拠参照を記録する。Card IDはsession内の表示IDであり、finding fingerprintを置き換えない。Cardは一つまたは複数のsource finding fingerprintを参照する。

### findings/FNNN/THREAD.md

同じfinding paneで行った対話の加工済み履歴をappend-onlyで記録する。raw transcriptではなく、各turnの質問、回答、反論、提示した証拠、未解決点を、source input IDと時刻付きで要約する。後続turnで同じfindingを議論するときは自動的に利用できる。

`THREAD.md`の内容は、他のfindingへ自動的に渡さない。必要な場合、Review Liaisonは特定のthreadを明示的に取得できるが、取得しただけではcontext promotionにならない。

### findings/FNNN/RESPONSE.md

人間がread-backで確認した、そのfindingに対する最終回答を記録する。会話全文や途中の仮説ではない。次を含める。

- Cardごとの確認済み回答
- 人間が与えたdomain contextと適用範囲
- 単純化案または代替案
- 明示的に拒否した提案
- 未解決の質問
- source input ID
- `explicit-user-input`、`same-pane`、`after-confirmation`を含むprovenance

### CONTEXT.jsonl

後続findingへ再利用してよいと明示的にpromotionされたHuman Contributionだけを記録する。各entryはkind、要約、source finding、source response、適用範囲、promotion scope、確認した人間入力、Manager disposition、失効条件を持つ。

再利用規則は次のとおりとする。

- finding-local：同じ`FNNN`の`THREAD.md`と`RESPONSE.md`を自動利用できる。
- room-local：人間が「このReview Room内で使ってよい」と確認した内容だけを`CONTEXT.jsonl`へ追加する。
- loopまたはrepository：人間の確認に加え、Managerが適用範囲と正本の保存先を決めてpromotionする。

後続finding paneは`CONTEXT.jsonl`の適用可能なentryだけをpreloadする。会話を利用しすぎないため、source findingと適用範囲を表示し、Cardと無関係なentryは注入しない。

### OUTCOME.json

Managerが確認済み回答をloop stateへ反映した結果を記録する機械可読台帳である。会話ログではない。各Cardについて次を記録する。

- source finding fingerprint
- human response input ID
- response status
- Manager disposition
- repository rationale
- 検討した最も単純な代替案
- release effect
- 作成または更新したdecision、requirement、task、follow-up、accepted-risk record
- 反映しなかったHuman Contributionと理由
- applied target SHAとscope revision
- appliedまたはsupersededの状態

`OUTCOME.json`を使い、確認済みのHuman Contributionがどこにも反映されないままsessionをcloseすることを拒否する。反映先がない場合は、`no_action`と根拠を明示する。

## Human Contributionの扱い

Human Contributionは、会話から得た文をそのまま恒久的な事実として扱わない。次の属性を付ける。

- `kind`：history、domain-rule、repo-convention、simplification、risk-preference、scope-instruction
- `source_input_id`
- `source_card_id`
- `applies_to`
- `valid_until`または`reconsider_when`
- `status`：proposed、confirmed、applied、retired
- `promotion_scope`：session、loop、repository

初期値は`promotion_scope: session`とする。loopまたはrepositoryへ昇格するときは、Managerが適用範囲と保存先を示し、人間の確認を記録する。過去の会話を後続findingへ無条件に注入しない。

session内でも、同じfindingを越えて再利用するにはroom-local promotionを要求する。repository promotionはReview Room artifactをそのまま将来の正本にせず、既存spec、DECISIONS、AGENTS.md、repository固有の運用文書などへManagerが反映した時点で`applied`とする。

## Stateとgate

Review Sessionは次のstatusを持つ。

```text
prepared
  -> running
  -> needs_evidence
  -> proposed
  -> confirmed
  -> applied
  -> closed
```

異常終了は`blocked`または`failed`、対象変更は`superseded`とする。`needs_evidence`からtargeted verification後に`running`へ戻れる。`confirmed`は人間の回答が記録された状態であり、Managerがloop stateへ投影したことを意味しない。`applied`は`OUTCOME.json`の全項目が正本artifactへ対応した状態である。

Review policyがHuman Review Roomを要求する場合、次を満たすまでfinishを拒否する。

- required Review Sessionが`applied`または明示的に`waived`である
- waiverに権限を持つuser inputと理由がある
- target SHAとrelease scope snapshotが一致する
- 未反映のconfirmed Human Contributionがない
- 人間判断を要求する未解決Cardがない
- Review Session後の変更に必要なdelta acknowledgementが完了している

Task Completion Gateを要求するproduct taskは、次を満たすまでManager harvestとmergeを拒否する。

- Task Auditorが固定candidate SHAを確認している
- Task Gap CheckとTask Handoff Reviewがともに`pass`である
- `human-judgment`を経た場合、対応するdecisionまたはaccepted riskがcandidate identityへ結び付いている
- gate後にcandidate SHA、task contract digest、acceptance、write scopeが変わっていない
- operational waiverの場合、Managerの理由と適用範囲が記録されている

## 人間稼働状態のSSoT

0.6.0では、人間の稼働状態をintegration branchのManager checkoutにある次のfileへ保存する。

```text
.ai/herdr-dev-loop/loops/<namespace>/participants/HUMAN.json
```

現行runtimeはlegacyの`.ai/loop`を意図的に無視するため、そこへ新しいstateを置かない。ここでいう「repo内のloop file」は、現行のnamespacedな正本directoryを指す。custom branch strategyでも、`PLAN.md`と`PROFILE.md`が定めるManager-owned canonical checkoutに同じpathを置く。

`HUMAN.json`は次を持つ。

```json
{
  "schema_revision": 1,
  "participant_id": "human",
  "revision": 12,
  "updated_at": "2026-07-16T12:00:00+09:00",
  "updated_by": "explicit-user-input",
  "availability": "active",
  "interaction_mode": "live",
  "interrupt_policy": "review-checkpoint",
  "capabilities": {
    "task_consultation": true,
    "review_room": true,
    "blocking_decision": true,
    "risk_scope_approval": false,
    "final_acknowledgement": true
  },
  "lease_until": "2026-07-16T16:00:00+09:00"
}
```

availabilityは`active`、`away`、`offline`、`unknown`、interaction modeは`live`、`async`、`unattended`、interrupt policyは`all`、`review-checkpoint`、`blocking-only`、`none`を使う。人間の明示操作だけが値を変更でき、Agentの観測から推測しない。leaseが切れた場合、schedulerはeffective availabilityを`unknown`として扱い、その遷移をfileへ記録する。

HLoopのすべてのinterfaceはrepositoryとnamespaceのlockを取り、revisionを比較して`HUMAN.json`をatomicに置き換える。人間またはAgentがfileを直接編集する運用は正規interfaceにせず、CLIと将来のTUIが同じtransactionを使う。role worktreeへ複製された古いfileを読ませず、`hloop participant status`がManager checkoutの正本を参照するread-only commandを全roleへ提供する。

`local-only`ではfileをManager checkoutに永続化するがGitへcommitしない。`branch-history`でも、人間の生活時間や稼働状況を公開履歴へ残さないため、`participants/HUMAN.json`をcheckpoint対象から除外する。Review Sessionには判断時のeffective state、record revision、lease statusだけをsnapshotし、availabilityの変更履歴全体は複製しない。

`unattended`では、安全に進められるWorker、Task Completion Gate、AI review、validationを継続する。Review Room agendaはqueueするがinteractive paneを起動せず、人間の沈黙を同意としない。人間が必須のdecision、accepted risk、scope変更、final acknowledgementに到達したtaskまたはgateだけを止める。

## 失効規則

次の変更はReview Brief、Cardのfact evidence、disposition projectionを失効させる。

- integration target SHAの変更
- base SHAの変更
- release scope revisionの変更
- source snapshot amendment
- source review manifestの変更
- source findingのfact statusまたはfingerprintの変更

失効時も、確認済みHuman Contributionを自動削除しない。対象コードに依存するContributionは`superseded`へ移し、ドメイン事実やrepository方針は適用範囲を再確認する。新しいsessionは、前sessionの判断を再利用した箇所と再確認が必要な箇所をdeltaとして表示する。

## Policy

設定は次の四つを候補とする。

```toml
human_review_policy = "checkpoint"
# off | decisions-only | checkpoint | required-final
```

- `off`：Human Review Roomをgateにしない。明示的な手動起動は許可する。
- `decisions-only`：`decision_requirement: user`、scope変更、risk受容だけを対話対象にする。
- `checkpoint`：初回のfixed-target review後に一度Review Roomを開き、最終時はdeltaだけを確認する。
- `required-final`：checkpointに加え、finish前の明示的な人間確認を要求する。

policyにかかわらず、早期Review Roomはrisk triggerと人間のcapabilityが一致するときだけ開く。`off`では自動起動せずagenda候補だけを表示する。人間が対応不能または`unattended`の場合、必要な相談をqueueし、影響するtaskだけを待機させる。

新規loopのdefaultは、実利用のdogfood後に決める。0.5.xからmigrationしたloopへHuman Review Room gateまたはTask Completion Gateを暗黙に追加しない。

## CLI案

```bash
hloop task-gate prepare T001 --candidate-sha <sha>
hloop task-gate start T001
hloop task-gate status T001 --json
hloop task-gate harvest T001
hloop task-gate waive T001 --reason '<operational task reason>'

hloop review-room prepare --source reviews/convergence/MANIFEST.json
hloop review-room start H001
hloop review-room layout H001 --mode 2x3
hloop review-room focus H001 F001
hloop review-room status H001 --json
hloop review-room watch H001
hloop review-room message H001 --finding F001 --file prompt.md
hloop review-room harvest H001
hloop review-room apply H001
hloop review-room close H001
hloop review-room supersede H001 --reason 'target SHA changed'

hloop participant set human --availability active --interaction live \
  --interrupt-policy review-checkpoint --lease 4h
hloop participant status human --json
```

`task-gate prepare`はtask contract digestとcandidate SHAを固定する。Review Roomの`prepare`はtarget identity、manifest digest、Review Brief、Cardを固定する。`start`は`HUMAN.json`のeffective availability、capability、leaseを確認し、専用tabと必要なReview Liaison paneを起動する。`harvest`は明示的な人間入力のprovenanceとrole write scopeを検証する。`apply`はManagerが選んだprojectionを一つのstate transactionで適用し、`OUTCOME.json`を生成する。`close`は未反映のconfirmed contributionと未解決Cardがないことを確認する。

## Role境界

Task Auditorは次を行える。

- 固定candidate SHA、task contract、result artifact、validation evidenceをread-onlyで確認する
- Task Gap Check、Task Handoff Review、Repository Evidence Contextを作成する
- `pass`、`fix-required`、`human-judgment`、`blocked`を報告する
- 人間判断が必要な理由をearly Review Room agenda候補として返す

Task Auditorはproduct code、task contract、Manager stateを変更できず、自分で修正して`pass`へ変えることもできない。

Review Liaisonは次を行える。

- Review BriefとCardを説明する
- source code、review artifact、validation evidenceを読み、質問へ回答する
- 人間の反論をtargeted verification requestへ変換する
- 人間の自由記述を確認文へ変換する
- RESPONSE.mdを作成する
- semantic reportを送る

Review Liaisonは次を行えない。

- product codeを変更する
- source findingのfact statusを変更する
- task、decision、requirement、follow-upを作成する
- accepted riskまたはscope変更を確定する
- review、gap、QA、merge、finish gateを閉じる
- confirmed前の会話要約を人間の回答として記録する

ReviewerとTask AuditorはRepository Evidence Contextまでを担当し、正式なdisposition、release effect、repository rationaleを決めない。

ManagerはTask Completion Gateを通ったdiffだけをharvestする。Reviewer findingのtriageではintegration branchを自ら確認してManager Repository Decision Briefを作り、finding別のdisposition、`repository_rationale`、`simpler_alternative_considered`を記録する。その後、Review Liaisonのfinding別`RESPONSE.md`を検証して正本stateへprojectionを適用する。ManagerはRESPONSE.mdを書き換えて未確認の回答を追加しない。

## Privacyと公開範囲

raw user input、pane transcript、secret、個人情報をGit管理artifactへ含めない。local-only persistenceでも、Review Brief、THREAD、RESPONSE、CONTEXTには判断に必要な最小限の内容だけを残す。`THREAD.md`は加工済み要約であってもraw inputへの参照を持つため、public-repo-safety上はReview Session artifactとして検査する。`branch-history` modeでcheckpointする場合、public-repo-safety preflightがTask Completion GateとReview Sessionを検査し、`participants/HUMAN.json`がstaging対象に入っていれば拒否する。

repositoryへ残すべき方針が会話から得られた場合は、Review Session transcriptを正本にしない。既存spec、DECISIONS、AGENTS.md、repository固有の運用文書など、将来のAgentが通常読む正本へ明示的に反映する。

## Migration

0.6.0はHuman Review Session、Review Liaison、outcome projectionを表すschema revisionを追加する。既存formatでadditive migrationを表現できる場合はformatを上げずschema revisionを進める。既存stateの意味を変更し、旧runtimeが安全にread-only inspectionできない場合だけformat versionを上げる。

Migrationは次を守る。

- 既存loopのreview cadence、manual final status、task、finding、decisionを保持する
- 既存loopのhuman review policyとtask completion policyを`off`または`legacy-not-required`にする
- 既存loopには`participants/HUMAN.json`を`availability: unknown`、capability未確認、leaseなしで追加する
- 0.5.2のmanual final artifactをHuman Review Sessionへ変換しない
- 0.5.xのDecision Liaison responseをReview Session responseへ変換しない
- unknown future revisionへのmutationを拒否する
