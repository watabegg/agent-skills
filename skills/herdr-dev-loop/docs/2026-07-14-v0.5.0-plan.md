# herdr-dev-loop 0.5.0 実装計画

- 作成日：2026-07-14
- 現行版：0.4.0
- 目標版：0.5.0
- 状態：方針合意および設計レビュー反映済み、実装待ち

## 目的

0.5.0では、完了状態の信頼性を修復したうえで、設定、レビュー、仕様判断、Agent主導の報連相、要件進捗、最終報告を一つの状態機械へ統合する。

0.4.0は、Workerの試行分離、統合検証、Manager QAによる停止では機能した。しかし、完了後のbranch drift、セッションcleanup、Advisor親子状態、引き継ぎ、message、model preflightに未解決の問題がある。ReviewerもP0からP3、コード参照、`decision_needed`を出せるが、単独エージェントが発見と事実確認を兼ねるため、見落としと自己追認を減らせない。

0.5.0は次の四つを満たしたときに完成とする。

1. `done`と`blocked`が、現在のGit、cleanup、判断状態と一致する。
2. 利用者がmodelやproviderを毎回指定せず、directory単位の設定を安全に再利用できる。
3. Reviewerが複数の独立調査と二次確認を経て、事実、重大度、修正可否、仕様判断の要否を分離して報告する。
4. Agentが着手、節目、相談、完了を自分から報告し、Managerが利用者の元要件を正本として進捗、判断、最終出力を説明できる。

## 現行実装から見た設計上の判断

### `.ai/loop`へ戻さない

利用者入力、要件台帳、進捗、最終出力は`.ai`配下で管理する。ただし、保存先は旧式の`.ai/loop/`ではなく、現在の正本である`.ai/herdr-dev-loop/loops/<namespace>/`を維持する。旧パスへ戻すと、複数ランの状態が混ざり、0.4.0で導入したnamespace分離を失うためである。

### Review sub-agentはCoordinatorに管理させる

Review sub-agent一体ずつのpane、worktree、sessionをHLoopが管理する必要はない。レビュー品質を判定するために必要なのは、Coordinatorが何本をどのlaneへ割り当て、全laneの結果と二次確認を回収し、対象SHAに結び付いた最終artifactを返した事実である。

0.5.0では、CodexまたはClaude CodeのReviewer Coordinatorがprovider-native sub-agentを4本から8本起動する。HLoopはCoordinator pane、対象SHA、sub-agent manifest、最終artifactだけを追跡する。sub-agent IDをproviderが返す場合はmanifestへ残すが、個別paneをHLoopのrole stateへ昇格させない。

### 仕様判断と実装の停止範囲を分ける

仕様判断が見つかっただけではgoal全体をblockedにしない。影響するtaskの依存部分だけを止め、独立して進められるtask、調査、検証準備は続ける。判断の影響が大きく、かつ安全に進められる作業がなくなった時点で、loopを`blocked_user_decision`へ移し、Managerが外部goalをblockedとして報告する。

### Managerに作業を捏造しない

ManagerはAgentの進捗を取りに行かない。各Agentが意味のある状態変化を自分から報告し、Managerは理解違い、相談、完了など、対応が必要なreportを受けたときだけ起きる。Managerに対応事項がなければ、追加作業を捏造せず、HLoopへwake leaseを登録して休止する。

### 報連相をrole contractにする

Agentの自由な善意へ報告を任せるとproviderやmodelによって粒度が変わる。0.5.0では、着手ACK、material milestone、attention、completionの四種類を全long-running roleの契約へ入れる。定期的な「まだ作業中」は送らず、理解、方針、成果、riskが変わった時だけ報告する。

### 2026-07-14時点の実行基盤

ローカル環境ではCodex CLI 0.144.1、Claude Code 2.1.207、Herdr 0.7.1を確認した。Codexはmulti-agentとhooksがstableで、`SubagentStop`と`Stop`を持つが、非同期command hookは未対応である。Claude Codeはsub-agent、background agent、`SubagentStop`、`Stop`、`TaskCompleted`、`TeammateIdle`を持ち、`asyncRewake`でidle sessionを再開できる。Herdrは`agent wait`と`wait output`によるblocking wait、paneとagentの状態報告を提供する。

この差から、provider hookだけで共通待機を実装しない。HLoopのreport brokerとManager inboxを共通層とし、Herdr blocking waitを無言終了のfallback、provider hookを終了guardと高速なwake adapterへ限定する。

## 0.5.0の全体構成

0.5.0の状態は次の流れで進む。

```text

    |
    v
requirements ledger -----> specification scout
    |                              |
    |                              v
    |                       decision queue
    |                         |          |
    |                         |          v
    |                         |    decision liaison pane
    |                         v
    |                    progressable scope
    v
Worker tasks -> integration validation -> review discovery swarm
      |                                     |
      | ack / milestone / attention         v
      +----------------------------> finding verification
      |                                     |
      | completion                          v
      +----------------------------> Manager inbox
                                            |
                                            v
                                    Manager triage
                                            |
                     +----------------------+------------------+
                     |                      |                  |
                     v                      v                  v
                  fix task          deferred decision    accepted risk
                     |
                     v
            requirement progress -> final QA -> outcome report
```

## 利用者設定

### 設定ファイルの位置

LinuxとmacOSでは、次の順で設定ファイルを探す。

1. `$HLOOP_CONFIG_HOME/config.toml`
2. `$XDG_CONFIG_HOME/herdr-dev-loop/config.toml`
3. `~/.config/herdr-dev-loop/config.toml`

Windowsは0.5.0の対象外とする。複数の設定ファイルを重ねず、最初に見つかった一つだけを読む。これにより、どの値が有効かを追跡しやすくする。

### 設定のscope

`config.toml`はglobal defaultとdirectory scopeを持つ。既定の照合対象はrepository rootとし、同じrepositoryをどのsubdirectoryから実行しても設定結果を変えない。cwd基準が必要なscopeだけ`match = "cwd"`を明示する。scopeの`path`は`~`を展開し、symlinkを解決したabsolute real pathとして比較する。対象pathのancestorになっているscopeを浅いdirectoryから深いdirectoryの順に上書きし、同じ`match`とcanonical pathを複数回定義した場合は設定エラーとする。`config explain`は照合対象、canonical path、採用scopeを表示する。

```toml
version = 1

[defaults]
max_workers = 3
session_cleanup = "archive"

[defaults.worker]
provider = "codex"
model = "auto"
effort = "auto"

[defaults.reviewer]
mode = "swarm"
provider = "codex"
model = "auto"
probe_count = 6

[[scope]]
path = "~/workspace"

[scope.worker]
provider = "claude"
model = "sonnet"

[[scope]]
path = "~/workspace/vdr"

[scope.reviewer]
mode = "dual-swarm"
providers = ["codex", "claude"]
probes_per_provider = 4
```

### 設定値の優先順位

値は次の順で上書きする。

```text
built-in default
< config.toml [defaults]
< matching directory scopes from shallow to deep
< existing loop PROFILE.md and STATE.json snapshot
< task override
< start command override
```

`init`時に解決した値はSTATEとPROFILEへsnapshotする。既存loopはglobal configの変更で勝手に挙動を変えない。設定を既存loopへ反映する場合は、`hloop config apply --dry-run`で差分を確認し、running roleとactive mergeがない状態で`--apply`する。

argparseの既定値は、config対象項目に限って`None`へ変更する。現状のようにparserが`codex`や`auto`を先に埋めると、利用者がCLI引数を省略したのか、明示したのかを区別できないためである。

### 設定CLI

次のcommandを追加する。

- `hloop config path`：利用する設定ファイルを表示する。
- `hloop config validate`：TOML、型、enum、scope重複、危険な値を検査する。
- `hloop config explain [--repo <path>]`：各値の最終値と出典を表示する。
- `hloop config init`：秘密情報を含まない最小templateを作る。
- `hloop config apply --dry-run|--apply`：既存loopへ明示的に再解決結果を反映する。

provider credential、API key、tokenはconfigへ保存しない。setup commandのように任意shellを実行する値も0.5.0のglobal config対象外とし、repository側のPROFILEまたは明示CLIへ残す。

### model capability preflight

`doctor`は、解決後のprovider、model、effort、permission mode、runnerをrole別に検査する。利用不能なmodelはworktree、branch、paneを作る前に失敗させる。

model一覧をCLIから確実に取得できないproviderでは、既知のmodel名をHLoopへ固定しない。provider CLIが提供する検証command、dry-run、または起動前の引数検証を利用し、検証不能なら`capability: unknown`として明示する。暗黙のmodel fallbackは行わない。

## 厳格なReview Swarm

### review mode

0.5.0は次のmodeを持つ。

| mode | 構成 | 用途 |
|---|---|---|
| `single` | 従来型Reviewer 1本 | 小さいdiff、低コスト運用 |
| `swarm` | Coordinator 1本、provider-native sub-agent 4本から8本、Finding Verifier | 通常の厳格レビュー |
| `dual` | Codex ReviewerとClaude Reviewerを1本ずつ | 小さいdiffのcross-model確認 |
| `dual-swarm` | providerごとにCoordinator 1本とsub-agent 4本から8本、cross-model verifier | 高リスクまたは最終レビュー |

`swarm`の既定sub-agent数は6本とする。`dual-swarm`はproviderごとに4本、合計8本を下限とする。最大はproviderごとに8本、合計16本とし、明示的に選ぶ高コストmodeとする。`doctor`はCodexのagent thread上限やClaude Codeのsub-agent利用可否を確認し、要求数を起動できない場合はCoordinator開始前に止める。

discovery数とは別にVerifier poolの最大並行数、review group全体の時間上限、provider別利用量上限をprofileで持つ。Verifierは候補ごとに無制限起動せず、bounded poolが候補batchを処理する。上限到達時は候補を黙って棄却せず`insufficient_evidence`として残す。通常cadenceでは低コストmodeを選べるが、final targetにはprofileが要求するstrict swarmを必須化する。

Codex Coordinatorにはprocess-localな`agents.max_threads`と`agents.max_depth: 1`を渡し、global Codex設定を書き換えない。上限はdiscovery sub-agent、Verifier、Coordinatorの同時実行数から計算する。Claude Code Coordinatorもsession-localなagent定義と上限を使い、利用者のglobal agent設定を変更しない。

### discovery stage

Coordinatorはdiff inventoryを作成し、変更内容に応じてsub-agentへ重複を含む調査laneを割り当てる。重複を完全になくすと同一問題の独立一致を測れないため、重大なlaneは二つ以上のsub-agentに割り当てる。

既定laneは次のとおりである。

- integration contractとwrite scope
- product correctnessとedge case
- security、privacy、auth、tenant scope
- data integrity、migration、concurrency、idempotency
- performance、resource、failure recovery、observability
- validation、test、QA evidence
- UI変更時のUX、accessibility、copy
- repository固有のcustom lane

各sub-agentは、他sub-agentの出力を読まずに調査する。diffだけで結論を出さず、必要なcaller、callee、test、schema、migration、workflowを読む。Coordinatorは全sub-agentの完了を待ち、失敗またはtimeoutしたlaneを黙って省略しない。発見候補には次の項目を必須とする。

- finding ID
- P0からP3のseverity
- confidence
- 短いtitle
- fileとline、symbol
- trigger scenario
- product impact
- introduced、diff-expanded pre-existing、unrelated pre-existingの区分
- proposed fix
- user specification decisionの候補か

### finding normalization

Coordinatorはsub-agentの候補を、titleの文字列一致ではなく、変更箇所、trigger、影響、推奨修正から作るfingerprintで束ねる。

同じ候補をCodexとClaudeが独立に報告した場合は`cross_model_consensus: true`とする。ただし、一致は信頼度を上げる証拠であり、事実確認の代わりにはしない。独自候補も二次確認へ送る。

### verification stage

すべての候補を、発見したsub-agentとは別のFinding Verifier sub-agentが再確認する。P0、P1、仕様判断候補は二つのVerifierが独立に確認する。P2とP3も最低一つのVerifierが確認する。`dual`または`dual-swarm`では、P0、P1、仕様判断候補をCodexとClaudeの双方が確認する。

Verifierは元の説明を要約するだけではなく、対象SHAのコードを開き、trigger path、到達可能性、既存guard、test coverage、仕様根拠を再構築する。出力は次の軸を分離する。

- `fact_status`：`confirmed`、`refuted`、`needs_spec`、`insufficient_evidence`
- `ignore_status`：`must_not_ignore`、`may_defer`、`no_action`
- `decision_status`：`none`、`localized_user_choice`、`blocking_user_choice`
- `progress_without_decision`：`yes`、`partial`、`no`
- `severity`：P0からP3。影響度だけを表し、確信度や判断要否と混ぜない。
- `recommended_action`：`fix_task`、`ask_user`、`accepted_risk_candidate`、`discard`

Verifier間で結論が割れた候補は、Managerが根拠を読み、`insufficient_evidence`または追加調査へ送る。多数決だけで事実にしない。

### review artifact

review gate `R001`はdirectory artifactへ拡張する。

```text
reviews/R001/
  MANIFEST.json
  providers/
    codex.md
    claude.md
  FINAL.md
```

`MANIFEST.json`は、Coordinatorごとにprovider、model、対象SHA、要求sub-agent数、各laneの目的、providerが返したagent IDまたはlabel、完了状態、finding数、Verifier割当を記録する。raw sub-agent transcriptや個別artifactの永続化は必須にしない。調査の詳細はprovider sessionに残し、HLoop gateはmanifestとCoordinatorの報告から、必要なlaneと二次確認が欠けていないことを検査する。

`providers/codex.md`と`providers/claude.md`は該当providerを使うmodeだけ生成する。各Coordinatorは自分のsub-agent群を回収し、provider単位の候補、棄却、未完laneを記録する。`single`と`swarm`では一方だけが存在してよい。`dual`と`dual-swarm`では両方を必須にする。

`FINAL.md`には次を記録する。

- audited baseとhead SHA
- provider、model、sub-agent数、Verifier数、lane一覧
- confirmed findingsをseverity順に並べた一覧
- 各findingのtitle、詳細、コード参照、trigger、改善案
- cross-model consensusと独自発見の区分
- refuted findingと棄却理由
- user specification decision候補
- fix task候補
- 残る不確実性

0.4.0の`reviews/R001.md`はmigration時にlegacy single reviewとして読み取る。0.5.0のgate判定は`FINAL.md`だけを参照し、sub-agentの中間出力を直接gateへ流用しない。

## 仕様判断の処理

### Specification Scout

`specification_scout = "auto"|"always"|"off"`をprofileへ追加し、既定を`auto`とする。`auto`はuser-visible behavior、security、data、public contract、高rollback cost、複数要件の相互依存がある場合に、`init`後かつimplementation task dispatch前に**Specification Scout**を一度起動する。明白な小修正やread-only調査では起動を省略できるが、final gateで未解決仕様判断の検査は常に行う。

Scoutは設計を勝手に決めず、次を報告する。

- 未決事項の質問
- 判断が必要な理由
- 影響する要件とtask候補
- 選択肢
- 各選択肢の利点、欠点、rollback cost
- repository evidenceから推奨できる選択肢
- 判断なしで進められる範囲
- 判断を遅らせた場合に失う作業

Scoutは候補を出すだけでloopをblockedにしない。Managerが事実と影響範囲を確認してdecision queueへ入れる。

Scoutは既定で1本とする。`dual-swarm`のような高保証profileではCodexとClaudeを1本ずつ起動できるが、常時二本を必須にはしない。

### decision class

判断は次の三種類へ分類する。

| class | 条件 | loopの動作 |
|---|---|---|
| `advisory` | reversibleで利用者仕様を変えない | Managerが根拠付きで決める |
| `deferred-user` | 利用者判断は必要だが、独立部分を進められる | 影響taskだけ保留し、他を続行する |
| `blocking-user` | 高影響で、判断なしに安全な次作業がない | Decision Liaisonを起動し、loopをblockedへ移す |

severityが高いだけで`blocking-user`にはしない。たとえばP1でも明確なbugで小さく修正できるならfix taskへ送る。P2でも製品の意図を変える選択しかなく、全taskが依存するならblockingになり得る。

### Decision Liaison pane

利用者に判断を求める場合、Managerとは別に**Decision Liaison** paneを起動できるようにする。Liaisonは仕様を決めるAgentではなく、問題を平易な日本語へ変換し、回答をManagerへ戻す対話役である。

Liaisonの表示には次を含める。

- 何が決まっていないか
- 今決める必要がある理由
- 二つか三つの選択肢
- 各選択肢の利点と欠点
- 推奨案と、その根拠
- 判断を後回しにした場合に進められる範囲
- 自由入力欄

論理式、state machine用語、internal IDは利用者向け本文に出さない。artifactにはdecision IDとsource findingを保持する。

利用者の回答は`decisions/DNNN/RESPONSE.md`へ保存し、Managerが受領確認して`DECISIONS.md`へ反映する。canonical question artifactを作成した時点でHerdr tab attentionとManager paneへdecision ID付き通知を出す。回答はLiaisonとManagerのどちらからでも同じdecision IDへ収束し、重複質問を抑止する。paneの送受信には0.5.0のmessage ACKを利用する。pane起動に失敗した場合はManager paneで同じ質問を表示できるfallbackを持つ。

### blockedの条件

次の条件がすべて成立した場合だけ、loopを`blocked_user_decision`へ移す。

1. 判断がuser-visible behavior、security、data、public contract、破壊的操作、または高いrollback costへ影響する。
2. 元仕様、repository evidence、既存decisionから答えを確定できない。
3. 判断に依存しないqueued task、調査、QA準備が残っていない。
4. Decision LiaisonまたはManager経由で質問を提示し、回答待ちである。

軽度の未回答事項は、Managerがreversible defaultを選び、その理由と残余リスクを最終報告へ記録できる。判断を隠して完了扱いにはしない。

## Agent主導の報連相

### reportの種類

長時間動く全roleは、自由文の善意ではなく共通のreport契約を持つ。reportは次の4種類とする。

| type | 送る時点 | 必須内容 |
|---|---|---|
| `ack` | 指示、role契約、repositoryを読み、実作業へ入る直前 | 理解したgoal、対象と対象外、進め方、検証方法、不明点、次の節目 |
| `milestone` | 調査結論、主要実装、検証開始、検証結果など、理解または次の行動が変わった時 | 完了した成果、証拠、現在のrisk、次に行うこと |
| `attention` | 理解違い、予想外の差分、判断、権限、失敗など、Managerの対応が必要な時 | 問題、影響範囲、既に試したこと、選択肢、推奨、止まる範囲 |
| `completion` | roleの成果物と検証が揃った時 | artifact、head SHA、検証結果、残余risk、後続への引き継ぎ |

`ack`は毎工程の承認gateにせず、role開始時と契約変更時だけ使う一回限りのbarrierとする。Agentはrepositoryをread-onlyで調査し、task contract digest、理解したgoal、scope、acceptance、approachを`ack`で返した後、`awaiting_ack_approval`で待つ。Managerはtask契約とsemantic ACKを比較し、`hloop agent ack approve|reject`で進行または訂正する。承認後は`milestone`ごとの許可を求めず自律的に進む。timeout、Manager session終了、reject後の再ACK、abort、requeueを状態遷移へ含める。

後続messageがgoal、scope、acceptance、public behaviorを変える場合も、transport ACKとは別にsemantic ACKを要求し、適用前に同じbarrierを通す。誤字修正や状態照会など、契約を変えないmessageはtransport ACKだけで処理できる。

Reviewer Coordinatorも同じ契約を使う。`ack`ではlane構成とsub-agent数、最初の`milestone`では一次調査の回収状況、次の`milestone`ではVerifier結果、`completion`ではmanifestと最終review artifactを報告する。HLoopがprovider-native sub-agentを個別管理する必要はない。

### 報告の粒度

reportは時刻ではなく状態変化を基準に送る。「まだ作業中」というheartbeatは送らない。短いtaskは`ack`と`completion`だけでよい。`milestone`はManagerまたは利用者の理解、risk、次の行動のいずれかが変わる場合に限る。同じrole、attempt、stage、summaryの重複は抑止し、`attention`だけは抑止対象外とする。

これによりAgentの自律性は維持しつつ、長時間無言、誤ったpromptのままの進行、完了だけを突然知らせる挙動を減らす。報告回数をtask数や経過時間のquotaにはしない。

### commandとevent schema

Agentはrole promptへ埋め込まれたabsolute helper pathを使い、JSON fileまたはstdinでreportを送る。shell引数へ長い要約を直接展開する方式は、quotingとprovider permissionの差が大きいため正規経路にしない。

```bash
python3 <absolute-skill-path>/scripts/hloop \
  --namespace <namespace> \
  agent report \
  --role-id <role-id> --attempt-id <attempt-id> --run-id <run-id> \
  --task-contract-digest <task-contract-digest> \
  --report-credential-file \
    <git-common-dir>/herdr-dev-loop-broker/<namespace>/credentials/<attempt-credential>.json \
  --file <report.json>
```

clientは送信前にUUIDの`event_id`とpayload digestをrole-local outboxへatomicに保存する。eventは`event_id`、`run_id`、`role_id`、`attempt_id`、`task_contract_digest`、brokerが採番する単調増加の`sequence`、`type`、`stage`、`summary`、`understood_goal`、`scope`、`acceptance`、`approach`、`next`、`needs_manager`、`evidence_refs`、`created_at`を持つ。同じIDとdigestの再送は成功済み結果を返し、同じIDでdigestが異なる場合は拒否する。構造化fieldと平易な要約を併記し、report本文をshell commandやManagerへの直接promptとして実行してはならない。

role起動時に、Git common directory配下のlocal-only領域へattempt-scopedのreport credential fileをatomicに作成する。fileはcurrent user所有かつmode `0600`とし、role promptにはcredentialとしてそのabsolute pathだけを埋め込み、token本体はprompt、provider command、checkpoint、state diagnosticのいずれにも含めない。clientはfile内のnamespace、run、role、attemptがcommandのidentityと一致することを検証し、brokerはtask contract digestとtokenも検証する。roleのharvest、abort、requeueなどのlifecycle transitionでidentityをrevokeしてcredential fileを削除することで、別roleや新attemptからの再利用をfail closedに拒否する。

### event配送とinbox

HLoopはnamespaceとrunに紐付くUnix domain socketのevent brokerをLinuxとmacOS向けに起動する。socketは長いrepository pathを避けるため、runtime directory配下へrun digestを使って作成する。role promptにはrun、role、attempt、task contract digestと、Git common directory配下の`0600` report credential file pathを渡す。token本体は環境変数やpromptで渡さない。

brokerは現行HLoopと同じrepo-local Git lockを取得し、append-only event、roleのlast sequence、Manager inbox projection、wake outboxを一つのtransactionで更新する。Herdrへのmessage送信はlock内で行わず、commit済みwake outboxを別処理で配信する。`inputs/**`、`inbox/**`、credential file、token、socket、PID、spool metadataはlocal-only artifact classとし、`branch-history`のcheckpoint、rollup、product commitから既定で除外する。

brokerは常駐daemonを持たない。foregroundの`ManagerSleepSupervisor`（`hloop manager sleep`）がsleep実行中だけbroker socketとowner epochを保持するcanonicalな所有者であり、PID、runtime version、single-owner lock、socket permission、stale socketを検証し、sleep終了ごとに即時cleanupする。同じsupervisorがsleep呼び出しのたびにspoolをdrainするため、別途daemon start/stopの手続きは不要である。管理operationは`hloop broker status|recover`のみを提供する。brokerへ接続できない場合、clientはGit common directory配下のrun専用spoolへreportをatomicに退避する。古いrun、終了済みattempt、revoked済みidentity、またはcredentialのidentity、task contract digest、tokenが一致しないreportは受理しない。

`ack`、`attention`、`completion`はManagerまたはschedulerを起こす。通常の`milestone`は既定でinbox-onlyとし、Manager対応が必要な状態変化は`attention`として送る。同一roleの未読milestoneとcross-role burstは短時間にまとめる。wake messageにはrun ID、event ID、lease generation、role ID、type、固定の`hloop inbox show <event-id>`だけを含め、Agentの自由文は転送しない。

Managerは`hloop inbox list|show|ack`で未読reportを処理する。`ack`ではtask理解を確認し、ずれがある場合だけ訂正する。`milestone`では要件進捗とriskを更新し、介入が必要な場合だけ指示する。`attention`では判断、再指示、利用者への相談を行う。`completion`ではartifactとSHAを独立に検証してharvestへ進む。Agentの自己申告は通信であり、完了の証拠そのものではない。

`hloop manager next`は未読reportと、それによって生じた具体的な対応だけを返す。inboxが空なら作業を捏造せず`wait`を返す。

## Managerの待機

Managerに対応事項がなければ、同期的な`hloop wait next --harvest`または休止用の`hloop manager sleep --wake-on report`を使う。promptで待機をお願いするだけにはしない。

`hloop manager sleep`は、Manager pane、run ID、待機対象、期限、lease generationを持つ**wake lease**をGit lock内で登録し、同じtransactionで未読inboxを再検査する。未読eventがあればleaseを取り消して即時returnする。これにより、`manager next`とsleepの間にreportが届くlost-wake windowを閉じる。

brokerはAgent reportを受けると、Manager paneが同じsessionでidleであることを確認してwake outboxへ記録する。Managerがworking、利用者入力中、paused、done、別runへ移行済みの場合は送信せず、eventをinboxへ保持する。配信保証は`at-least-once`とし、Managerがevent IDとlease generationで重複wakeを無視して一度だけ処理する。Herdr送信とdurable記録を跨ぐ`at-most-once`は保証しない。

Herdrのblocking waitは、Agentがreportを送らずにpane終了、idle、blocked、またはcrashした場合のfallback監視に限って使う。pane出力から進捗を推測したり、短い間隔で`pane read`を繰り返したりしない。複数roleのfallbackを待つ場合は最初の終端変化だけを採用し、synthetic terminal eventとしてinboxへ入れる。

### provider hook adapter

hookはreport検出本体にせず、Managerがactive roleを残したままwake leaseなしで終了することを防ぐguardとして使う。これにより、Claude CodeとCodexのhook能力差をHLoopの状態機械へ漏らさない。

Claude Codeでは、`Stop` hookでactive roleとwake leaseを確認できる。`asyncRewake`も利用できるが、HLoopのreport brokerとinboxを正本とし、Claude固有機能はwake latencyを下げるadapterとして扱う。

Codexにも`Stop`と`SubagentStop` hookがあるが、非同期command hookは現行仕様で動かない。0.5.0の実装前に、Stop hookがManagerへ継続指示を返す挙動を実CLIでprobeする。継続を安全に強制できる場合は「`hloop manager sleep`を実行してから終了する」という固定contextを返す。強制できない版では、Herdr watcherによるidle Managerへのwake messageをfallbackとする。

hookはrole進捗や完了を推測せず、wake leaseの有無だけを検査する。完了判定はcompletion report、sentinel、artifact、SHAをHLoopが照合して行う。hookが無効でも正しく動き、hookが有効ならManagerの終了漏れを早く検知できる設計にする。

hook adapterは`hloop hooks status|install|uninstall --provider codex|claude`で管理する。installは既存設定をbackupし、HLoop所有markerの付いたentryだけを追加する。既存の利用者hookを上書きしない。Codexではinstall後にhook trust確認が必要なことを表示し、信頼回避flagを自動使用しない。Claude Codeでも設定reloadまたはsession再起動の要否をdoctorで表示する。hook未導入は警告にとどめ、report brokerとHerdr fallback経路を利用可能にする。

`hloop manager next`が`wait`を返した後は、Agent report、fallbackの終端event、利用者入力、期限到達のいずれかまで待つ。期限到達後も状態が変わらなければ、同じ「まだ実行中」という進捗を利用者へ繰り返さない。

## 要件基準の進捗報告

task IDの列挙だけでは、利用者の目的に対する達成度を説明できない。0.5.0は各要件を次の状態で追跡する。

- `not_started`
- `in_progress`
- `implemented_unverified`
- `verified`
- `blocked`
- `deferred`
- `superseded`

`STATUS.md`は、要件、現在状態、対応task、証拠SHAまたはQA artifact、残作業を一行で示す。全要件を同じ重さとして単純な百分率にしない。利用者向けの先頭には、たとえば「8要件中5件を検証済み、2件は実装済みで最終QA待ち、1件は仕様回答待ち」と書く。重みが明示された場合だけweighted percentageを表示する。

進捗snapshotは次の時点で生成する。

- `ack`で明らかになったscopeが要件またはtask対応を変える時
- `milestone`の証拠によって要件状態が変わる時
- `attention`によって要件が判断待ちまたはblockedになる時
- `completion`の検証後
- pause、blocked、ready_to_finish、doneへの遷移前
- Managerが利用者へ進捗を返す前

`hloop progress record`は`progress/Pxxxx.md`を追加し、`LATEST.md`を更新する。進捗にはtask数ではなく、元要件ごとの達成、未検証、判断待ち、次の一手を簡潔に記載する。Agent reportだけで`verified`にはせず、artifact、SHA、test結果をManagerまたはHLoopが確認してから状態を上げる。

## finishとblockedの最終出力

### outcome artifact

`reports/FINAL.md`と`reports/BLOCKED.md`の構成をschemaで固定する。

共通項目は次のとおりである。

- goalとrun identity
- 元要件ごとの最終状態
- 実装した利用者向け変更
- validationとQAの証拠
- review swarmのconfirmed finding、修正、accepted risk
- 利用者判断と採用結果
- 軽度の未解決事項
- cleanupとsession保存状態
- integration targetと現在branch SHA
- 次に利用者が行うこと

`FINAL.md`はすべてのfinish gateを通過した場合だけ生成する。`BLOCKED.md`は一時的なdecision待ちごとには生成せず、Managerが外部goalをblockedとして返す段階で生成する。途中状態は`USER_ACTION_REQUIRED.md`と`progress/LATEST.md`へ記録する。

`hloop report`は現在状態のdraftを生成できるが、phaseを変えない。`hloop finish`と`hloop outcome blocked --reason ...`だけが、それぞれの終端reportを確定する。

### 外部goalとの連携

HLoop CLI自体はCodex製品側のgoal APIを直接呼べない。Manager promptへ次の契約を追加する。

- `hloop finish`成功後、`reports/FINAL.md`を読み、利用者向け最終出力を返して外部goalをcompleteにする。
- `hloop outcome blocked`成功後、`reports/BLOCKED.md`を読み、同じblocking conditionが必要な基準を満たした場合だけ外部goalをblockedにする。
- 一時的な仕様質問では外部goalをblockedにせず、Decision Liaisonまたは通常の利用者対話を続ける。

## ポストモーテムで確認したruntime修正

### attempt baseの不変性

attempt開始時のbase SHA、branch、worktree、task contract digestを可変なrole stateとは別のappend-only attempt recordへ保存する。`worker finalize`、harvest、mergeはこの記録を正本とし、active attemptのbase変更をstate save時に拒否する。Manager側とrole worktree側のcopyが異なる場合は、どちらかへ追従せず`attempt-state-diverged`で停止する。

branch pointを変える必要がある場合はfresh requeueまたは専用resume transactionを使い、同じattempt IDのまま続行しない。古いbranchに未統合commitがあればattempt history用branchへarchiveする。

### merge transactionの復旧

merge開始前にtask、attempt、integration HEAD、Worker HEAD、index状態、changed pathをtransactionとして保存する。content conflictとenvironment failureを別状態へ分ける。conflict中は`watch`、`--continue`、`--abort`、`--retry`だけを許可し、通常pump、再merge、対象taskのfinalizeを拒否する。

`--continue`はManager checkout上で競合を解消する手順を表示し、成功時にpre-merge HEAD、index、Worker HEAD、result HEAD、write scopeを再検査する。transaction外のreset、手動commit、Worker branchへのintegration mergeを検出した場合は`manual-integration-trace`として停止する。

### paused runの再開条件

`status`、`dashboard`、`conductor`はpause中もlive integration HEADとvalidation、review、gap、Manager QAの対象SHAを比較し、`resume_requirements`として再実行が必要なgateを列挙する。`resume`は不足gate、active blocker、dirty state、running roleを再検査し、古い証拠をcurrent HEADへ付け替えない。

### harvest後のartifact表示

active roleはworktree artifactを参照し、harvest済みroleはManager側artifactまたはSTATE snapshotを参照する。`cleaned-after-harvest`と`unexpectedly-missing`を区別し、merged taskへactive readinessを表示しない。

### final gateの安定条件

`all_tasks_merged`だけでは最終reviewとgapを起動しない。current batch close、review triage完了、未処理fix-task draftなし、Managerによる`hloop final-gates arm`を条件とする。final gateから新taskが生まれた場合はarmを解除して通常cadenceへ戻す。同一SHAの有効なreview結果は再利用し、逐次fix taskごとにstrict swarmとfinal gapを反復しない。

### Manager QA evidence path

PROFILEでManager-owned evidence pathを指定できるようにする。dispatch、watch、harvestでは許可path内のdirtyを認めるが、merge、validation、finishではcleanまたは明示checkpointを要求する。product pathと未許可pathのdirtyは従来どおり拒否する。

### done target drift

`status`、`dashboard`、`conductor`は、`phase=done`でも`final_target_sha`とintegration branchの現在SHAを比較する。不一致は`done-target-drift`としてP0を返す。

診断にはfinal target、現在SHA、進行commit数を含める。drift中の再finishは拒否する。意図的な後続commitを受容する場合は、`hloop completion supersede --head-sha <sha> --reason <text>`で旧runを`superseded`へ移す。既存のdone証拠を新しいSHAへ付け替えない。

### 全role cleanup gate

finishはWorkerだけでなく、Reviewer Coordinator、Gap Auditor、Advisor、Specification Scout、Decision Liaisonのpane、worktree、provider session cleanupを検査する。provider-native review sub-agentはCoordinator sessionの内部要素として扱い、manifest上で全laneが終端状態になっていることを確認する。個別sub-agent sessionのarchiveをHLoop gateにはしない。

未解消の`agent_session_cleanup_error`はfinishを止める。providerが機能を持たない場合は`unsupported`とする。Managerが例外受容する場合は、`hloop cleanup resolve <role-id> --status cleaned|accepted-risk --reason <text>`だけを遷移経路とし、対象run、role、attempt、理由、時刻、Manager identityを保存する。conductorは未解消、unsupported、accepted riskを区別する。

### cleanup状態の履歴化

active errorと過去履歴を分ける。cleanup成功時はactive errorを消し、`cleanup_history`へ移す。同一error fingerprintの連続失敗は一件へ集約し、`attempt_count`と最終発生時刻を更新する。再試行には上限とbackoffを設ける。

### Advisor closeの冪等性

親Advisor requestをcloseしたとき、全participantを`consumed`または明示的な終端状態へ移す。閉じた親のparticipant `reported`をconductor issueにしない。同一artifactのharvestと同一verdictのcloseは時刻を上書きせず、成功済みとして返す。

### handoffとsuperseded

`handoff`、`superseded`、`abandoned_by_user`を終端phaseへ追加する。後続namespace、handoff SHA、理由を記録し、conductorは旧runのreviewやgap開始を提案しない。後続runのdoctorは起点namespaceとSHAがhandoff recordに一致することを検査する。

### message ACK

messageにはID、run、role、attempt、digest、送信時刻、ACK時刻、適用結果を持たせる。`delivered`、`acknowledged`、`applied`、`undelivered`、`unknown`、`superseded`を区別する。

受信Agentは処理開始時にtransport ACKし、処理後にapplied resultを返す。契約変更messageはsemantic ACK barrierを通す。`hloop message drain`は`undelivered`だけを自動再送し、`unknown`を自動再送しない。`unknown`はACK確認、pane確認、明示retry、resolveのいずれかを要求する。timeout後はconductorがretry、abort、fresh requeueを提示する。pause、pane再起動、attempt終了をまたぐmessageを新attemptへ暗黙転送しない。

## state format 3と移行

0.5.0は`state_format_version: 3`と単調増加の`schema_revision`を使用する。format 3の最終schemaをPhase 0で凍結し、Phase途中の開発版STATEにはrevisionを付ける。同じformat 3内でもrevisionが古ければ順番にmigrationを適用し、runtime以上の未知revisionはread-only inspection以外を拒否する。主な追加項目は次のとおりである。

- config sourceとresolved snapshot
- review mode、Coordinator、sub-agent manifest、Verifier、consensus
- specification scoutとdecision liaison
- requirementsとprogress snapshot
- report protocol設定とroleごとのlast report sequence、type、時刻
- Manager inbox、既読event、wake policy
- report broker identity、fallback spool、wake lease、Manager pane identity
- append-only attempt identity、active merge transaction、resume requirements
- final gate arm、review budget、Manager QA evidence path
- artifact classとcheckpoint inclusion policy
- 全role cleanup statusとcleanup history
- terminal outcomeとsuperseded run
- message ACKとapplication result

`hloop migrate --dry-run`はformat 2から3とformat 3内revisionの変更を表示し、`--apply`前にbackupを作る。running role、active merge、dirty worktreeがある場合は移行を拒否する。各Phaseの開発版STATEを次のrevisionで読み込むupgrade fixtureを保持する。

0.4.0の単独reviewは`mode: single`として取り込む。既存`DECISIONS.md`と`USER_ACTION_REQUIRED.md`は維持する。過去の利用者promptは存在しないため自動生成せず、migration noteへ`input history unavailable`と記録する。

## 実装構造

現行の`scripts/hloop`は約1万行あり、unit testは6件である。0.5.0の機能を同じfileへ追加すると、状態遷移の回帰を局所化しにくい。CLI entry pointは維持し、新機能から次のmoduleへ分ける。

```text
scripts/hloop
scripts/hloop_lib/
  broker.py
  config.py
  events.py
  migration.py
  state.py
  lifecycle.py
  review.py
  decisions.py
  requirements.py
  reports.py
  providers.py
```

最初に主要read commandとmutating commandのargv、exit code、STATE差分、JOURNAL差分をcharacterization testとして固定し、その後にpure functionをmoduleへ移す。module抽出だけのcommitと挙動変更のcommitを分け、一度に全CLIを書き換えない。

## 実装フェーズ

### Phase 0：回帰fixtureとmodule境界

- 0.4.0の代表的なSTATEを匿名化fixtureとして追加する。
- attempt base改変、merge transaction逸脱、done drift、cleanup error、Advisor重複close、unfinished handoff、paused resume、harvest後artifact missing、final gate反復、message失敗を再現するtestを先に失敗させる。
- 主要CLIのargv、exit code、STATE、JOURNALを実Git repositoryとfake Herdr、Codex、Claudeでgolden化する。
- state format 3の最終schema、schema revision chain、artifact classを確定する。
- `scripts/hloop`のentry point互換を維持したまま、config、state、reportのpure function用moduleを作る。

完了条件は、0.4.0の既存command helpとselftestを壊さず、両ポストモーテムの全項目がfixture、実装Phase、release evidence、または理由付きdeferへ対応付くことである。

### Phase 1：runtime不変条件とlifecycle修正

- append-only attempt record、state divergence検出、fresh requeueを実装する。
- merge transaction、continue、abort、retry、manual integration traceを実装する。
- done target driftを全read surfaceと再finishで検出する。
- 全role cleanup、監査可能なaccepted risk、retryとactive/history分離を実装する。
- Advisor冪等性、handoff、superseded、paused resume、harvest後artifact表示を修正する。
- final gate armとdisarm、Manager QA evidence path、command別dirty policyを実装する。
- Git runtime identityの脅威モデルを再確認し、採用する場合はtrust更新transactionを実装する。

## 主要なリスク

### review cost

`swarm`は4本から8本、`dual-swarm`は8本から16本のdiscovery sub-agentにVerifierを加えるため、時間と利用量が増える。modeを明示選択にし、diff sizeとriskに応じた推奨を`config explain`とdashboardへ出す。Verifier pool、時間、利用量をboundedにし、final gate安定条件を満たすまでstrict swarmを反復しない。途中でsub-agent数を減らしても、開始済みreview groupの構成は変更しない。

### finding量の増加

sub-agentを増やすだけでは、低品質な指摘も増える。二次確認を全候補へ必須化し、`confirmed`以外をfix taskへ自動変換しない。P3も事実確認を省略しない。

### 利用者対話の見落とし

Decision Liaison paneだけでは、利用者がpaneに気付かない場合がある。軽度判断はprogressとfinal reportへ残し、重度判断はManager paneにも同じ質問を表示する。dashboardは未回答時間と影響範囲を表示する。

### artifact増加

review manifest、provider report、prompt、progress snapshotによりlocal artifactが増える。raw sub-agent出力をHLoop artifactへ複製せず、Coordinatorのprovider sessionと要約へ集約する。中間artifactはrun単位で保持し、`hloop cleanup archive-run`で圧縮できるようにする。監査に必要なFINAL、decision、requirement evidenceは削除しない。

### report過多とreport不足

細かい作業ごとに`milestone`を送ると、Managerの見回りを通知処理へ置き換えただけになる。経過時間やtask数ではなく、理解、成果、risk、次の行動の変化を送信条件にする。同じstageの未読milestoneはまとめ、重複を抑止する。一方で、短いtaskにも最低限`ack`と`completion`を要求し、`attention`はcoalescingしない。

### 自己申告と実態のずれ

Agentが「完了」と報告しても、artifact欠落、古いSHA、test未実行の可能性がある。reportは報連相の入力として扱い、lifecycle gateはsentinel、artifact、SHA、test、manifestを独立に検証する。虚偽または古いcompletion reportだけでtaskをcloseしない。

### broker停止とreport遅延

brokerが停止するとManagerを即時に起こせない。Agent側はGit common directoryのrun専用spoolへreportをatomic保存し、独立supervisorがbrokerを再起動してspoolをdrainする。supervisor自体の異常はHerdr fallback eventとして通知する。pane終了やcrashはHerdr blocking waitで補足するが、通常進捗の推測には使わない。

### Managerの誤wake

brokerまたはfallback watcherが古いrunや利用者入力中のManagerを起こすと、誤ったnamespaceを進める危険がある。wake leaseをrun ID、Manager session ID、pane ID、generation、期限へ結び付ける。wakeは重複し得るため、Managerがevent IDで一度だけ処理する。Managerがidleでない場合は入力を送信せず、dashboardへqueued eventを表示する。固定wake message以外を送らず、role出力をManager promptとして転送しない。

## 受け入れ基準

0.5.0のrelease候補は、次をすべて満たす。

1. configなし、global config、repo基準と明示cwd基準のnested scope、CLI overrideを`config explain`で説明できる。
2. providerが検証可能な利用不能modelをrole worktree作成前に拒否し、検証不能時は`unknown`と最終argvを記録して暗黙fallbackしない。
3. active attemptのbase改変とManager、role間のstate divergenceを拒否し、fresh requeueだけが新baseへ移れる。
4. merge conflictをSTATE手編集なしでcontinue、abort、retryでき、transaction外のGit操作を`manual-integration-trace`として止める。
5. done target drift、全role cleanup、Advisor冪等性、handoff、paused resume、harvest後artifact表示をsynthetic fixtureで再現し、修正後の状態を検証できる。
6. cleanup accepted riskが専用commandを通り、対象attempt、理由、時刻、Manager identityを残す。
7. Review SwarmのCoordinatorが4本から8本の独立sub-agentとbounded Verifier poolを起動し、manifestと最終artifactを返して全findingを二次確認する。
8. strict reviewとfinal gapがbatch安定条件とfinal-gates armに従い、逐次fix taskごとに反復しない。
9. CodexとClaudeのdual modeが同一SHAを独立reviewし、consensusとunique findingを区別する。
10. 仕様判断が必要でも独立作業が残る間は依存部分だけを止め、全面停止時だけ平易な質問を提示してblockedへ移る。
11. 全long-running roleと契約変更messageがsemantic ACK barrierを通り、誤ったgoalまたはscopeをmaterial edit前に停止できる。
12. 通常milestoneはinbox-only、attentionとcompletionはwake対象となり、Managerはpaneを見回らずsleepできる。
13. report brokerがrepo-local lock、durable outbox、supervisorを使い、sleep直前report、crash、restart、duplicate wakeでもeventを失わず一度だけ処理する。
14. messageのACK、unknown、undelivered、drain、retry、abortまたはrequeue提案をCodexとClaudeの双方で再現できる。
15. `inputs/**`、`inbox/**`、broker credential file、tokenがbranch-history checkpointとproduct commitへ入らず、token本体はrole promptとprovider commandにも入らない。
16. Agentのcompletionを鵜呑みにせず、artifact、SHA、testを検証してから要件状態とtaskを完了へ進める。
17. 進捗、finish、blockedの出力がnamespaced artifactから生成され、元要件ごとの状態と証拠を示す。
18. format 2と古いformat 3 revisionをbackup付きで移行し、未知revisionのmutationを拒否する。
19. synthetic E2E、Codex実run、Claude実run、install parity、skill discoveryがrelease evidenceとして保存される。
